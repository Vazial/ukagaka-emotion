# step定義lint — 実現手段の調査

> 対象: verification.md L4詳細(1)の規約を機械強制する手段。meta/guardrails.md 1節「禁止事項を書きたくなったらまずlint・構造検証で強制できないか検討する」(P-04)に基づく調査。
> 状態: 調査のみ完了。**ツール確定はADR-0001(アーキテクチャ選定)でのスタック確定後**。本ファイルはその判断材料。

## 強制したい規約(verification.md より)

1. 分岐・ループ・例外握りつぶし禁止(step定義内に `if` / `for` / `while` / `try-catch` 等が出現しない)
2. 1 step定義 = DSL呼び出し + 検証のみ。行数上限(目安10行)
3. DB直接操作の禁止(Given専用seam以外)
4. 既存stepの再利用優先(類似検出)

## 方式の選択肢

### A. 汎用ASTベースの自作チェッカー
- 言語のパーサ(Tree-sitter等)でstepファイルを解析し、分岐ノード・行数を機械的に検出する独自スクリプト
- 長所: スタックを問わず同じ設計思想で作れる。CIへの組み込みが単純(exit code)
- 短所: 自作コストがかかる。パーサ導入の分だけ依存が増える

### B. 既存lintツールのカスタムルール
スタック別の候補:
| スタック | 候補 | 備考 |
|---|---|---|
| TypeScript/JavaScript | ESLint カスタムルール(`no-restricted-syntax`でif/for/while/try文を禁止するstepディレクトリ限定config) | 追加実装コスト最小。ディレクトリ限定overridesが容易 |
| Python | flake8プラグイン自作 or `ast`モジュールで簡易チェックスクリプト | flake8の`max-complexity`(mccabe)で分岐検出を代替できる可能性 |
| Java | Checkstyle/PMDのカスタムルール(`CyclomaticComplexity`をstepsパッケージのみ1に制限) | PMDの`ExcessiveMethodLength`で行数上限も同時に強制可 |

### C. 行数上限のみ簡易チェック(暫定)
- スタック確定前でも導入可能な最小策として、`steps/`配下のファイルを対象に「1関数あたりの行数」をgrep/wc相当の簡易スクリプトでCIチェックすることは今すぐ可能
- ただし分岐禁止の検出は言語構文の理解が要るため、この簡易策だけでは規約2しか満たせない

## 類似step検出(規約4)

- stepの一覧を自動生成(定義済みstep文字列の一覧をビルド時にダンプ)し、reviewerの監査項目に「一覧を見て類似がないか」を明記する運用(verification.md L4詳細(1)で既定)。文字列類似度による自動検出は初期スライスでは過剰と判断し、まずは一覧生成 + 人間/reviewerの目視から始める

## 推奨

- スタック確定後は **B(既存lintツールのカスタムルール)** を第一候補とする。自作(A)よりメンテコストが低く、開発者に馴染みのあるツールチェーンに乗る
- 確定は architect が ADR-0001 のスタック選定と合わせて提案し、人間が承認する
- 暫定として、CIの `L2: 構造の健全性` ジョブに C(行数上限の簡易チェック)を先に組み込み、分岐禁止チェックはスタック確定後にBへ差し替える(P-10: 段階的に強化)
