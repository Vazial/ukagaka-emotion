## 0. 設計上の守り(ADR-0001)

- この仕様は ADR-0001 の決定を変えない。HTTPやAPIの依存は持ち込まない。読むだけのファイルを扱い、
  ファイル・環境への書き込みは無い(決定2)
- **9分類の名前の一覧と、台詞欠落・評価データの感情名の妥当性の判定は、核が持つ**(決定1・5)。
  CLIはファイルを読んで核へ渡し、核の判定結果を終了コードと標準エラーに写すだけにする
- 入力が空でも、分類不能でも、例外や別扱いの経路は作らない(決定1)

## 1. 入口

```
python -m ukagaka_emotion classify <文> [--data <データ置き場>]
python -m ukagaka_emotion evaluate <評価データ> [--data <データ置き場>]
```

- `<文>` は1個の引数。空文字(`""`)も有効な入力で、UKE-A-02 の「何も書かずに入力する」に当たる
- `--data` を省けば、同梱の仮データ(仮の台詞・見本の文)を使う。省略時の置き場の実体は仕様で固定しない
- **「入力を始めようとする」(UKE-E-01)とは、`classify` または `evaluate` を起動すること**を指す。
  別の「開始」操作は設けない。台詞の欠落の確認は、両方の起動時に、入力の処理に入る前に必ず行う

## 2. データの形式

文字コードはどれもUTF-8。9分類の名前は「喜び / 信頼 / 恐れ / 驚き / 悲しみ / 嫌悪 / 怒り / 期待 / どれでもない」。

### 2.1 データ置き場(`--data`)

ディレクトリで、次の2ファイルを持つ。tester は、同梱の仮データを複製して一部を欠かせば、
UKE-E-01 の前提(「怒り」の台詞が無い)を作れる。

| ファイル | 内容 |
|---|---|
| `lines.json` | 台詞。キーが分類名、値が台詞の文字列の配列。`{"喜び": ["…", "…"], "怒り": ["…"], …}` |
| `samples.json` | 見本の文。形は `lines.json` と同じ(分類名 → 文の配列) |

- キーが9分類の名前以外なら、データの誤り(終了コード2)
- `lines.json` で、あるキーが無い、または配列が空なら、その分類は「台詞が無い」(UKE-E-01、終了コード1)
- `samples.json` の欠落は本仕様では扱わない(第1段の契約に、見本が無い場合のシナリオは無い)

### 2.2 評価データ(`evaluate` の引数)

**見本の文(`samples.json`)とは別のファイル**である。評価は、見本とは別の文で測る。
JSON Lines(1行1件)で、各行は次の形。

```
{"text": "今日は本当に嬉しい、最高の一日だった", "emotion": "喜び"}
```

- `text` は文字列(空文字も有効。「どれでもない」の評価に使える)。`emotion` は9分類の名前のどれか
- 空行は無視する。それ以外で形が崩れた行、9分類に無い `emotion` は、評価データの誤り(終了コード2)
- 0件(有効な行が1つも無い)は、評価データの誤り(終了コード2)
- 評価データの作り方(AI生成+人間選別。activeContext 参照)は、この仕様の対象外。出所は仕様で縛らない

## 3. 終了コードと標準エラー

| 終了コード | 意味 | 標準出力 | 標準エラー |
|---|---|---|---|
| 0 | 正常 | 4節の出力 | 空である必要は無い(警告を出してよい) |
| 1 | **台詞の無い分類があり、始められない(UKE-E-01)** | **空** | 下記 |
| 2 | 使い方・データの誤り(引数の不足、読めないファイル、形式の崩れ、9分類に無い名前) | 空 | 原因が分かる1行以上の文。内容は固定しない |

優先順位: 引数の誤り(2) → データ置き場の誤り(2) → **台詞の欠落(1)** → 評価データの誤り(2)。

### 3.1 終了コード1(UKE-E-01)の標準エラー

検証できる粒度で、次の3点を求める。文言と書式は固定しない。

1. **台詞が無い分類の名前を、すべて含む**。「怒り」だけが欠けていれば「怒り」を含む
2. **台詞が有る分類の名前を含まない**。「怒り」だけが欠けている時、ほかの8分類の名前は出さない。
   「その分類の名前を示して」「その理由で」始められない、をテストで言えるようにするため
3. 台詞が無いことを示す語を含む(「台詞」の語)

あわせて、標準出力は空で、分類も評価も行わない(結果が一部でも出ない)。`classify`、`evaluate` の両方で同じ。

終了コード2は、本スライスのL4シナリオの対象にしない(業務の約束ではなく、使い方の誤りへの応答のため)。
CLI境界の検証(L3)で確かめる。

## 4. 標準出力(終了コード0のとき)

### 4.1 `classify`

次の2項目を表示する。**項目の取り出しのため、行頭のラベルだけを固定する**(台詞の中に感情の名前が
出てもテストが取り違えないように)。ラベルの後ろの装飾、空白、行の順は固定しない。

| 行頭ラベル | 内容 | 検証 |
|---|---|---|
| `分類:` | 分類名。9分類のうちちょうど1つ | 9分類のどれかである。UKE-B、UKE-A-02、UKE-C-01 は、この値を見る |
| `台詞:` | 台詞のちょうど1つ | `lines.json` の、**表示された分類の配列**に含まれる文字列である(UKE-A-01・A-02) |

台詞の選び方(複数あるとき)は決めない。テストは「その分類の台詞のどれか」だけを見る。
同じ文は同じ分類になること(UKE-C-01)は、分類名だけを比べる。台詞の一致は求めない。

### 4.2 `evaluate`

次を表示する。**行頭のラベルだけを固定する**。

| 行頭ラベル | 内容 | 検証 |
|---|---|---|
| `評価件数:` | 評価データの有効件数(整数) | 評価データの行数と一致する |
| `全体正解率:` | 正解数と件数(整数の組)、および率 | 整数の組が評価データと分類結果から導ける値と一致する。率の桁数と単位は固定しない |
| `分類別正解率 <分類名>:` | 9分類それぞれに1行。その分類を正解とする文について、正解数と件数(整数の組)、および率 | 9行が出ること。件数の合計が `評価件数` と一致する。件数が0の分類は、率の代わりに「対象なし」を示す(0除算を避ける) |
| `応答時間(1件あたり):` | 1件あたりの平均応答時間。単位はミリ秒(`ms`) | 数値と単位が出る。正の数である。値の大小は検証しない(合格基準は無い) |
| `見本と同一の文:` | 評価データのうち、`samples.json` に同じ文がある件数(整数) | 見本とは別の文だけの評価データでは0である |

- **応答時間の対象範囲**: 1件の文を受け取って、分類し、台詞を選ぶまで。埋め込み部の読み込みなどの
  起動準備は含めない。起動準備にかかった時間を別の行で出してもよいが、必須としない
- 「正解」の定義: 評価データの `emotion` と、`classify` が同じ文に返す分類名が同じ
- 検証の拠り所(tester 向け): 正解率は、評価データの各文を `classify` にかけた分類名と `emotion` を
  突き合わせて数えた値と、**公開境界の外から再計算して一致する**。実装を読まずに期待値を作れる
- 見本と同一の文があっても、評価は止めない(終了コード0)。値を水増しされた評価に気づけるよう、件数を知らせるだけ

## 5. シナリオとの対応

| シナリオ | 見る境界 |
|---|---|
| UKE-A-01・A-02 | `classify` の `分類:` と `台詞:`(4.1)。A-02 は引数が空文字 |
| UKE-B-01〜04 | `classify` の `分類:` |
| UKE-C-01 | `classify` を2回。`分類:` が同じ |
| UKE-D-01 | `evaluate` の `全体正解率:` と `分類別正解率 …:` 9行(4.2) |
| UKE-D-02 | `evaluate` の `応答時間(1件あたり):`(4.2) |
| UKE-E-01 | データ置き場の複製から「怒り」の台詞を除き、`classify`(と`evaluate`)を起動。終了コード1、標準出力が空、標準エラー(3.1) |

## 6. シナリオ(.feature)への追記案

`s1-emotion-reply.feature` は承認済みのため、**このファイルでは変更しない**。人間が承認したら、
次の差分を適用する。**既存のシナリオIDは変えない。欠番の再利用もしない。新規は UKE-D-03 のみ**。
技術用語(ファイル、JSON、終了コード、標準エラー)は入れていない。

```diff
   Background:
     Given 8つの感情と「どれでもない」の9分類それぞれに、仮の台詞が1つ以上用意されている
     And 9分類それぞれに、その分類だと分かっている見本の文が用意されている
+    And 見本の文とは別に、9分類それぞれに、その分類だと分かっている評価用の文が用意されている
@@
     # UKE-D-01
     Scenario: 見本の文の集まりに対する正解率が報告される
-      Given 感情が分かっている文の集まりがある
+      Given 見本の文とは別の、感情が分かっている文の集まりがある
       When その集まりをまとめて評価する
@@
     # UKE-D-02
     Scenario: 1件あたりの応答時間が報告される
-      Given 感情が分かっている文の集まりがある
+      Given 見本の文とは別の、感情が分かっている文の集まりがある
       When その集まりをまとめて評価する
       Then 1件あたりの応答時間が表示される
+
+    # UKE-D-03: 見本と同じ文で測ると正解率が水増しされる。気づけるようにする(4.2「見本と同一の文」)
+    Scenario: 見本と同じ文が評価に混ざっていると、その件数が知らされる
+      Given 見本の文を2件含む、感情が分かっている文の集まりがある
+      When その集まりをまとめて評価する
+      Then 見本と同じ文が2件含まれていると表示される
```

- UKE-D-01 のシナリオ名「見本の文の集まりに対する正解率」は、見本と評価用を分ける趣旨と食い違う。
  **名前の言い換えを承認時に決めてほしい**(例: 「感情が分かっている文の集まりに対する正解率」)。IDは変えない
- UKE-E-01 の本文は変えない。「入力を始めようとする」は、1節の定義で `classify`/`evaluate` の起動と読む

## 7. 承認時に決めてほしい点

1. **データ置き場(`--data`)を公開境界に加える**。UKE-E-01 の前提を外から作る唯一の手段であり、
   なければ tester は同梱データを書き換えるしかない。代案: 環境変数での指定(私は引数を推す)
2. データの形(`lines.json` / `samples.json` / JSON Lines)。**既存実装のデータの形とは突き合わせていない**
   (実装を読まないため)。食い違う場合は、developer が本仕様に合わせるか、人間が本仕様を直す
3. 終了コード3種(0/1/2)。E-01 を使い方の誤りと見分けるために1を分けた
4. 応答時間の対象範囲(起動準備を含めない)と、単位をミリ秒に固定すること。ADR-0001 の
   「速度の指標の細部は実装時に決める」を、この文書で決めることになる
5. UKE-D-03 の追加(任意。却下しても、他は成り立つ。その場合は4.2の `見本と同一の文:` も削る)
6. 本仕様はADRを新設しない。ADR-0001 の決定と禁じる依存の範囲内に収まるため
