# ADR-0002: Jev本体との比較実験に限り、外部通信を例外として許す

> **承認者向けサマリ**
>
> ADR-0001 決定3は、プロジェクト全体で外部APIの利用を禁じている（Jev本体のAPIを含む）。
> Linear KEN-66「Jev本体と埋め込み分類を比べる」を行うには、Jevへ文を送る必要がある。
> そこで、禁止を残したまま「比較実験に限る例外」を1つだけ設ける。
>
> 決めること(5点)。
>
> 1. 通信してよい範囲: Jevの比較コマンドを人が明示して実行した時だけ。既定のCLI動作・テスト・CIは通信しない
> 2. 送ってよい文: `data/evaluation.jsonl` の27件だけ。実際のゴーストの台詞は送らない（送るなら別ADR）
> 3. APIキー: 環境変数だけ。リポジトリに置かない
> 4. 実行は手動。結果は `model-benchmark.md` に追記する
> 5. 設計上の置き場: 差し替え可能な分類部品の1実装として置く。核は変えない
>
> 払うもの: 外部への送信を許す穴が1つ空く。穴を狭く保つため、構造検証に「通信してよい場所は比較用の1か所だけ」という確認が増える。

## 文脈

ADR-0001 は第1段をローカルの埋め込み方式で組み、分類部を差し替え可能に保った。
差し替えの目的は、後でJev本体などと同じ評価データで比べることである（ADR-0001 文脈・案A）。
その比較がKEN-66で始まる。ADR-0001 決定3の禁止（「HTTPクライアントや外部APIのSDKを使わない」）は、
このままだと比較用のコードも書けない。

禁止を外すのではなく、理由と範囲を明示した例外を置く。ADR-0001 本体は書き換えない。
決定3の禁止は、この例外が定める範囲を除いて有効なままである。

Jevの具体的なAPI形式（送信先、認証方式、応答の形）は、本ADRの時点で未確認の前提である。
この点は決定の対象にせず、実装時に分かった事実で本ADRの範囲に収まるかを確かめる（下の「確認すること」）。

## 決定

### 決定1. 外部通信は、Jevの比較コマンドを明示実行した時だけ許す

- 比較コマンドは、通常の分類・応答のコマンドとは別の入口とする。人が明示して呼んだ時だけ通信する
- 既定のCLI動作、自動テスト、CIは外部へ通信しない。比較コマンドの自動テストは、通信部分を差し替えた
  偽物で行い、実際の通信を行わない
- ADR-0001 決定3の「ネットワークには出ない」は、比較コマンド以外の全てについて有効なまま

根拠: 通信を「人の明示操作」に結びつけると、気付かないうちに外へ文が出ることがなくなる。

禁じる依存:
- 核、既定の分類部（ローカルの埋め込み部）、既定のCLIの入口は、HTTPクライアントや外部APIのSDKを参照しない
- テストとCIの経路から、Jevの通信部分を実物で呼ばない

### 決定2. Jevへ送る文は、評価データの27件に限る

- 送ってよいのは `data/evaluation.jsonl` の文のみ（9分類×3件の27件）
- `data/lines.json`（仮の台詞）、`data/samples.json`（見本文）は送らない。実際のゴーストの台詞は含めない
- 実ゴーストの台詞をJevへ送る場合は、権利・外部送信の扱いを含めて別のADRで決める

根拠: 評価データはAIが生成し人間が選別した仮データであり、外部へ出ても失うものが無い。
実ゴーストの台詞は第三者の著作物を含み得るため、本ADRでは扱わない。

禁じる依存:
- 比較コマンドは、評価データのファイル以外から文を読まない（入力は固定。任意の文を受け付けない）

### 決定3. APIキーは環境変数だけに置く

- キーは環境変数から読む。変数名は実装時に決め、READMEまたは `model-benchmark.md` に書く
- リポジトリ（コード、設定ファイル、データ、テスト、ログ、結果の記録）にキーを置かない。出力にも表示しない
- 環境変数が無い場合、比較コマンドは通信せずに「キーが無い」と知らせて止まる

根拠: キーを持ち込む経路を1つに絞れば、漏えいの確認も1つで済む。

禁じる依存:
- キーの値をファイルへ書き込まない（ADR-0001 決定2の書き込み禁止とも整合する）

### 決定4. 実行は手動、結果は model-benchmark.md に追記する

- 比較は人が手で実行する。定期実行・常駐・CIでの実行は行わない（ADR-0001 決定6と整合）
- 結果（正解数/件数、正解率、1件あたりの応答時間、実行日、Jevの版や条件）は
  `model-benchmark.md` に追記する。ローカルの埋め込み方式との比較表に並べる
- 応答時間は通信を含む。ローカル方式の値と同じ尺度ではない旨を併記する
- 精度・速度の合格基準は設けない（契約どおり、測って報告するまで）

根拠: 比較は1回の実験であり、継続運用ではない。結果は文書として残せば足りる。

### 決定5. 6軸(ADR-0001)での置き場: 差し替え可能な分類部品として置く。核は変えない

| 軸 | この例外の扱い |
|---|---|
| 1 業務ルール | 変更なし。核は分類結果を受け取って台詞を選ぶ関数のまま |
| 2 状態 | 変更なし。何も保存しない |
| 3 外部との境界 | 例外の本体。ADR-0001 が「ベクトル化の1か所」とした外部との境界に、Jev用の通信を足す。足すのはこの1か所だけ |
| 4 層の厚み | 部品は3つのまま。Jev用の実装は、差し替え可能な分類の部品の中の1実装として置く |
| 5 UI | 比較コマンドを別の入口として足す。CLIは呼んで表示するだけで、判定や通信の詳細を持たない |
| 6 駆動 | 手動のまま |

- Jevは「文を分類（または分類に使える値）にして返す」窓口の1実装として扱う。核はその窓口の外側にしか
  触れず、Jev固有の形式を持たない
- 窓口が「ベクトルを返す」形のままでは、Jevの応答（分類そのものを返す場合）を表せない可能性がある。
  その場合は窓口を「文から9分類のどれかを返す」形に広げる。この広げ方は、実装前に本ADRまたは追補で
  人間に確認する（部品の数は増やさない。増やす場合は ADR-0001 決定4のとおり新しいADRが要る）

禁じる依存:
- 核は、Jev用の通信部分とその形式を参照しない
- 通信してよい場所は、Jev用の実装の1か所だけとする
- 構造検証（L2）に、次の2点を足す。(a) 核と既定の分類部がHTTP・外部SDKを参照しないこと
  (b) 通信部分の参照が、Jev用の実装と比較コマンドの入口の外へ出ていないこと。ルールの具体形は実装側で書く（本ADRでは書かない）

## 検討した代替案

- 案A: ADR-0001 決定3を改訂して、外部APIの禁止を外す / 不採用の理由: 禁止の目的（第1段の既定動作を
  ローカルに保つ）は今も有効。範囲を限った例外の方が、変える量が少なく、取り消しも容易
- 案B: Jevの応答を人が手で集め、ファイルとして取り込む（通信は人が別に行う） / 不採用の理由:
  27件の手作業は再現性が低く、応答時間も測れない。ただし、通信できない環境でのフォールバックとして
  残す余地はある（本ADRの範囲外）
- 案C: 実ゴーストの台詞も比較に含める / 不採用の理由: 外部送信と権利の扱いが別問題になる。
  必要になった時点で別ADRにする（決定2）

## 帰結

- 良い影響: 同じ27件・同じ評価でJevとローカル方式を並べて比べられる。例外の範囲が文書とL2で確認でき、
  通常の経路は引き続き外へ出ない
- 払うもの: 構造検証の追加。Jev用の実装と比較コマンドという保守対象が増える。
  応答時間の比較は通信を含むため、そのままでは同列に比べられない
- 波及する作業: Jev用の実装、比較コマンド、構造検証ルールの追加（developer）。
  `model-benchmark.md` への追記。比較コマンドの仕様を `contracts/` に足すかは承認後に判断する
  （公開境界が増えるため、契約の追補が要る見込み。起草は承認後）

## 確認すること(承認前または実装前)

- Jevの実際のAPI形式（送信先、認証、応答の形）と利用条件が、決定1〜3の範囲に収まるか。収まらなければ
  本ADRを改訂して再承認を取る
- 決定5の窓口を広げる件（ベクトルから分類へ）の可否
- 評価データ27件を外部サービスへ送ることに、人間として問題が無いか（決定2の前提）
