# ADR-0054: 検証ツールの保護を deny から ask に変える。うっかりは止め、正当な変更は承認1回で通す

> **承認者向けサマリ**
>
> 検証ツール（`meta/tools/` 配下のチェッカと `build.gradle`）は、AIが編集できないよう権限設定の
> 拒否リストに載せてある。この保護を入れたADR-0046は「変更が必要なら人間が拒否リストから外す
> コミットを打つ」という運用を定めた。19日たって、そのコミットは一度も打たれていない。かわりに
> 検証ツールへの変更が6件たまり、うち2件は「開錠が要るなら別の場所に置こう」という形で設計を
> 曲げている。人間からも3セッション続けて開錠依頼が飛んでいる。
>
> 拒否リスト（deny）を確認リスト（ask）に変える。ask に載せたパスへの書き込みは、実行前に人間へ
> 確認プロンプトが出る。ADR-0046が「唯一の実効果」と認めた「手が出た瞬間に合図が返る」性質は
> そのまま残り、正当な変更は承認1回で通るようになる。設計前に実測し、サブエージェントからの
> 書き込みでも確認プロンプトが親セッションの人間に届くことを確認した。
>
> 決定は4点。
>
> 1. 4項目を `permissions.deny` から `permissions.ask` へ移す
> 2. 施錠の確認を行うgovlintの検査を、`ask` 配列を見る形に変える
> 3. ADR-0046の決定4（権限設定そのものは保護しない）を、実測に基づいて書き直す
> 4. Bash経由の抜け道とCodexに届かない件は、限界としてそのまま引き継ぐ
>
> 払うもの: 検証ツールを触るたびに確認プロンプトが1回出る。従来の「開錠コミット・実装・施錠
> コミット」という3手が、プロンプト1回に縮む。

## 文脈

### 1. 何が起きたか

人間から問いが出た。「`meta/tools/**` の Edit と Write を拒否リストに入れているが、これは妥当か。
開錠してほしいという依頼が3セッションくらい続けて飛んできている」

拒否リストを入れたのはADR-0046である。同ADRは、orchestrator（作業を各役割に振り分ける役）が
「検証インフラは自分で直さずdeveloperに委譲する」という明文の禁止を4回破ったことを受けて、
禁止を文章から権限設定へ移した決定だった。4回目の記録がFR-022である。

ADR-0046の帰結節には、後退条件があらかじめ書いてある。「検証ツールの変更に人間の操作が1つ
増える。実績ベースで直近2週間に3回であり、頻度としては軽くない。過剰と分かれば案Cへ後退する」

### 2. 開錠は19日間、一度も起きていない

施錠したのは2026-08-03（コミット `401621f`）である。それ以降、`.claude/settings.json` に触れた
コミットは無い。予測されていた「2週間に3回」の開錠は、19日で0回だった。

そのあいだに、検証ツールへの変更が6件たまっている。

| 塞がれている変更 | 出典 | 性質 |
|---|---|---|
| シナリオIDの正規表現が `TDR-CS-01`・`TDR-AUTH-01` に一致しない | `projects/dining-radar/activeContext.md` | dining-radarの19本のシナリオIDが、契約検査（L0）で一度も検査されていない |
| ADR本文の承認宣言とfrontmatterの `status` の照合 | dining-radar FR-017 | 承認記録の更新に2本目のPRが要る問題（7回目）を止める検査 |
| ADR採番の衝突検出 | ADR-0052 | 採番衝突（FR-023）の再発防止 |
| `commission_design_api.py` の削除 | ADR-0050 | 外部設計AIの廃止で死蔵コードになった |
| ADRの文体3項目の計数 | ADR-0053 決定3 | 「実装は本PRに含まれない。開錠は人間の操作である」と明記されている |
| UI検証ハーネスのmeta層への一般化 | `projects/dining-radar/activeContext.md` | 判断材料が揃っても着手できない |

このうち1件目は、単なる待ち行列ではない。契約検査が19本のシナリオIDを検査していない状態が、
施錠のあいだ続いている。**ゲートを守るための施錠が、ゲートの穴を塞げなくしている。**

### 3. 施錠が設計判断を曲げている

より重いのはこちらである。開錠手続きを避けるために、検査の置き場そのものが動いている。

- ADR-0052は採番衝突の検出をgovlintに足さず、GitHub Actionsに置いた。理由は2つ挙げられており、
  その一方が「`meta/tools/**` は施錠されており変更に人間の開錠を要する」である
- ADR-0051は「却下した選択肢の記載をgovlintで必須化する」案を退けた。理由の一部が「施錠されて
  おり変更に人間の開錠が要る。判定の確度が低い検査にその手続を課す理由がない」である

どちらも判断としては筋が通っている。しかし積み上がると、統治文書のチェッカに新しい検査が
入らなくなる。信条P-04は「ルール化できるものを文章で書かない。機械が確定できるものは機械に
確定させる」と要求している。施錠は、その機械を増やす経路に摩擦を置いた。

### 4. 止めたかった行動は、実際に止まっている

公平のために記録する。ADR-0046が狙った効果は出ている。

原因キー `orchestrator-as-substantive-source`（orchestratorが実質的成果物を自分で作る、という
繰り返し観測された失敗の型）の5回目は、施錠後に起きていない。摩擦ログの最後の出現はFR-022の
ままである。

規範としても働いた。dining-radarで検証ツールの欠陥（変異テストのスコアが古い値のまま残る）を
見つけたとき、orchestratorはそのファイルが施錠対象外であるにもかかわらず、ADR-0046の理屈を
引いてdeveloperへ委譲している。

つまり問題は「保護したこと」ではなく「保護の強さの選び方」である。

### 5. なぜ強すぎたか

FR-022の失敗は帰属の問題だった。developerが書くべきものを、orchestratorが書いた。書いたこと
自体が悪いのではなく、書いた主体が違った。

ところがパスに基づく拒否リストは、誰が書こうとしているかを区別できない。ADR-0046はこれを
実測で確認しており、「orchestratorだけを拒否する」という当初案を成立しないものとして退けている。

そこで同ADRの決定2は、developerも止まることを「副作用ではなく規程の段差を正す本筋である」と
位置づけた。ここが分かれ目である。区別できないという機構の限界が、「正当な書き手も人間の承認を
要する」という規程に写し取られた。19日間ゼロ開錠は、その規程が実際には回らなかったことを示して
いる。

必要なのは、区別できないことを認めたうえで、区別する役を人間のプロンプトに渡すことである。

## 実測（証跡）

ADR-0040が確立した先例（権限機構の性質は推測せず実測して証跡を残す）に従い、決定前に測定した。
測定日は2026-08-22、Claude Codeのauto modeで実施した。

| 実行主体 | 経路 | 対象 | 結果 |
|---|---|---|---|
| orchestrator | Write | `meta/tools/` 配下の新規ファイル | 確認プロンプトが人間に出た。承認して通過 |
| developer（サブエージェント） | Write | `meta/tools/` 配下の新規ファイル | 確認プロンプトが親セッションの人間に出た。承認して通過 |
| orchestrator | Bash（`>` リダイレクト） | `meta/tools/` 配下の新規ファイル | 確認なしで通過 |
| orchestrator | Edit | `settings.json` に `ask` を追加 | 通過 |
| orchestrator | Edit | `settings.json` から `deny` の4項目を削除 | 拒否。auto modeの分類器による |
| orchestrator | Bash（python） | `settings.json` の読み取りと書き換え | いずれも拒否。auto modeの分類器による |
| govlint | — | `ask` へ移した後の `settings.json` | ERROR・終了コード1。4項目すべてをmissingとして名指し |

最も重要な結果は2行目である。**確認プロンプトはサブエージェントからも親セッションの人間に届く。**
これが成立しなければask案は成り立たなかった。developerが検証ツールを書こうとしたとき、人間は
その場で1回承認するだけでよく、開錠コミットも施錠コミットも要らない。

3行目は、ADR-0046の決定5が「未解決の穴」として記録したBash経由の迂回が、今も開いていることの
確認である。ただしこの穴は deny でも ask でも同じく開いている。したがって本ADRの変更で失われる
守りではない。

5行目と6行目は、ADR-0046の決定4が置いた前提を崩す。同決定は「権限設定ファイル自体は保護しない。
保護すればorchestratorは自分でロックを外せなくなるが、それは採らない」と述べていた。しかし実際に
は、auto modeの分類器という別の層が、AIによる拒否リストの緩和をBashからもEditからも止めている。
`ask` の追加は通したので、この層は守りを弱める方向だけを選択的に拒んでいる。

## 決定

### 決定1. 4項目を `permissions.deny` から `permissions.ask` へ移す

`.claude/settings.json` の `permissions` に `ask` を置き、次の4項目をそこへ移す。`deny` からは
外す。

```json
"ask": [
  "Edit(./meta/tools/**)",
  "Write(./meta/tools/**)",
  "Edit(./**/build.gradle*)",
  "Write(./**/build.gradle*)"
]
```

対象パスはADR-0046の決定1から変えない。信条P-05（要るようになってから足す）に従い、他スタックの
同等物はまだ含めない。

`Read` は引き続き対象外である。読めなければ委譲先への事実の供給もレビューもできない。

ADR-0046の決定2（`meta/permissions.md` の権限表で、検証ツールをゲートとして扱う）は維持する。
検証ツールの変更に人間が関与するという性質は変わらない。変わるのは関与の形だけで、コミット2本
から確認プロンプト1回になる。

作業の流れは次のようになる。

- 従来: 人間が開錠コミット → developerが実装（この間L0は赤）→ 人間が施錠コミット → L0が緑
- 以後: developerが実装しようとする → 人間が確認プロンプトで承認 → 実装 → L0は最初から緑

### 決定2. govlintの検査を `ask` 配列に向ける

統治文書のチェッカ（`meta/tools/govlint.py`）は現在、`permissions.deny` に4項目が揃っている
ことをERRORで確認している。これを `permissions.ask` を見る形に変える。

検査の性質は変わらない。「指定の文字列が配列に存在するか」という、機械が確定できる事実判定で
ある。ERRORのままでよい理由もADR-0046の決定3と同じで、保護が外れたままマージできない状態を
保つ。

**実装はdeveloperが行う**（テスト付き）。orchestratorは書かない。決定1により`ask`になったので、
developerは人間の承認1回でその場で書ける。新方式の最初の適用対象が新方式自身の実装になる、
という構図はADR-0046と同じである。

なお本PRをマージするまでのあいだ、L0はこの検査で赤になる。これはADR-0046の決定3が想定した
「開錠中のワークツリー」と同じ状態であり、マージゲートが見るのは最終状態だけである。

### 決定3. ADR-0046の決定4を、実測に基づいて書き直す

`.claude/settings.json` 自体は引き続き `deny` にも `ask` にも入れない。結論はADR-0046と同じ
だが、根拠を差し替える。

ADR-0046の根拠は「保護すればAIが自分でロックを外せなくなるが、権限設定はAIが設計に参加すべき
対象だから採らない」だった。実測（5行目・6行目）が示すのは、auto modeの分類器がすでにAIによる
拒否リストの緩和を止めているという事実である。つまり「AIは自分で保護を外せない」状態は、権限
設定ファイルを保護しなくてもすでに成立している。

したがって権限設定ファイルを保護対象に加える理由は無い。加えれば、分類器と重複する守りを1つ
増やしたうえで、ADR-0040のようなガードレール設計そのものを実行不能にするだけである。

ただしこの分類器はauto modeの挙動であり、リポジトリの設定ではない。モードが変われば消える
可能性がある。本ADRはこれを守りとして数えず、観測された事実として記録するに留める。

### 決定4. 限界の記述はそのまま引き継ぐ

ADR-0046の決定5が明示した2つの限界は、本ADRでも変わらない。

- Bash経由でファイルを書き換える経路は開いている。実測3行目で確認した。止められるのは
  「うっかり」だけである
- `.claude/settings.json` はClaude Codeの権限機構であり、Codexには届かない。したがって決定1の
  効果はClaudeにしか出ない。決定2の効果（保護が外れたままマージできない）は、L0が共通の必須
  ゲートであるため両方に効く

塞いだ穴と塞いでいない穴を取り違えることがガードレールの最大の失敗である、というADR-0046の
指摘をそのまま引き継ぐ。

## 検討した代替案

- **案A: 現状維持（deny のまま、開錠の運用を改善する）** / 不採用: 開錠が重いのではなく、開錠の
  判断が人間の別セッションを要求することが問題である。文脈2のとおり19日で0回であり、運用の
  改善で回復する見込みが立たない。文脈3が示すように、待ち行列を減らす方向ではなく検査を別の
  場所へ逃がす方向に圧力がかかっている
- **案B: ADR-0046が後退先として予約した案C（保護を外し、govlintのREPORTで可視化する）** /
  不採用: ADR-0046自身が案Cを退けた理由が今も正しい。FR-022の失敗の中身は「気づかなかった」で
  あり、「見えれば止まる」という前提と噛み合わない。ask はREPORTより強く、denyより軽い。予約
  されていた後退先より良い選択肢が実測で見つかった、というのが本ADRの位置づけである
- **案C: PreToolUseフックで呼び出し元を識別し、orchestratorだけを止める** / 不採用: ADR-0046が
  案Bとして退けたのと同じ理由による。フックのスクリプトはロジックを持つ検証インフラであり、
  それ自体がdeveloperの領分になる。解こうとしている問題を1段深いところで作り直す
- **案D: 保護対象を絞る（govlint本体だけ deny、テストや他ファイルは自由）** / 不採用: 塞がれて
  いる6件のうち5件がgovlint本体への変更であり、絞っても摩擦はほとんど減らない
- **案E（採用）: deny を ask に置き換える** / 採用: 手が出た瞬間に合図が返るという唯一の実効果を
  保ったまま、正当な変更の待ち時間を消す。サブエージェントからも人間に届くことを実測で確認済み

## 帰結

- 検証ツールを触るたび、人間に確認プロンプトが1回出る。従来の3手（開錠コミット・実装・施錠
  コミット）がプロンプト1回に縮む
- 文脈2の6件が着手可能になる。とくにdining-radarの19本のシナリオIDがL0の検査対象に入る
- 文脈3の圧力が消える。検査をgovlintに置くか別の場所に置くかを、開錠手続きの重さではなく検査
  自体の性質で決められるようになる
- orchestratorが手を出した瞬間に確認が返るという合図は残る。ただし承認するのは人間なので、
  「orchestratorが書こうとしている」ことに人間が気づける形になった。denyのときは誰が書こうと
  していたかがプロンプトに出ず、拒否だけが返っていた
- 承認疲れのリスクを負う。プロンプトが増えれば人間が中身を見ずに通すようになる。対象パスを
  4項目に絞ったままにするのはこのためである。頻度が問題になったら対象を狭める方向で見直す
- ADR-0046はsupersededになる。同ADRが記録した実測（denyはサブエージェントに継承される）と
  文脈分析（FR-022の4回、`meta/permissions.md` の段差）は、本ADRでも有効な前提である
- 未解決のまま残るもの: Bashの迂回、Codexに届かないこと、原因キーの再出現検出が摩擦ログの
  ファイル単位である穴。いずれもactiveContextに記録を維持する

## 確認事項（人間に確認されたい）

**確認プロンプトの頻度が許容範囲かどうかは、運用してみないと分からない。** 本ADRは「19日で0回の
開錠」という実績から、プロンプト方式のほうが軽いと判断している。しかし検証ツールへの変更が
たまっている現状では、承認直後にプロンプトが集中する可能性がある。

判断材料として、選択肢を3つ挙げる。

1. **本ADRのまま進める。** 溜まった6件を消化しながら頻度を観測し、重ければ対象パスを狭める
2. **対象を `meta/tools/govlint.py` とそのテストに絞る。** `build.gradle` は摩擦の実績が
   ADR-0046起草時の1回だけであり、外しても失うものは小さい
3. **溜まった6件を消化するあいだだけ許可し、その後 ask に戻す。** 承認疲れを避けられるが、
   「一時的に外す」という運用がADR-0046の開錠コミットと同じ理由で回らない恐れがある

起草者としては1を推す。2は摩擦が出ていないものを先回りで外す点でP-05と逆向きであり、3は本ADRが
問題視した運用そのものだからである。
