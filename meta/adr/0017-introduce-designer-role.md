# ADR-0017: agent役割にdesignerを新設する

> 改訂: 2026-07-19（同日中の追加決定）人間がorchestratorとの詰めで3点の追加決定を行った:
> (1) designerをarchitectの下流でなく**並行**（契約とUI/UXモックを同時に起こし、突き合わせで食い違いを
> 表面化させる）に位置づけ直す、(2) designerは視覚の土台をゼロから自作せず**採用済みデザインシステムに
> 載せる**ことを役割原則にする、(3) designerの出力を洗練する**refinementループ**と、実用水準に届かない
> 場合の**escape hatch**を先に定義する。初版（下流モデル）からの変更点は本文中に反映し、「検討した
> 代替案」に旧モデルを不採用として記録した。本ADRはまだ承認されていない（実質は提案中。承認済み表記は
> meta ADRの慣行=meta/adr/0006）ため、P-06の「承認後の編集禁止」には抵触しない。

## 文脈

フロントエンド（projects/reservation-frontend）のADR-0004（画面モック承認プロセス）改訂の過程で、
architectがモックの忠実度を人間フィードバックに応じて引き上げた（低忠実度ASCIIワイヤーフレーム →
実際にレンダリングされる静的HTML/CSS）。この過程で、モックの作成者を引き続きarchitect（契約とモデルの
番人、実装コード禁止）に置くか、視覚・UI/UXデザインの翻訳を専任で担う役割に分離するかが論点になった。

人間はorchestratorとの詰めにより、新しいagent役割**designer**を新設することを決定した。本ADRはこの
決定を、テンプレートの正式なアーティファクト（agent役割規程・subagent定義）として明文化するものである。
仕様の内容自体は人間決定であり、architectはこれを再導出・再検討しない（meta/adr/0011: orchestratorの
ディスパッチはroutingに限り、実質的内容を注入しない。今回はorchestratorが人間決定をそのまま運んでいる）。

**当初は下流モデルで運用を開始した**: architect（契約）→人間承認→designer（モック）という順序。
しかしこのモデルには構造的な問題があった。契約が凍結された後にdesignerが着手するため、UI/UXの要求が
契約の設計に反映される機会がない。reservation-frontendの実例（会議室一覧を取得するAPIが無く、画面が
会議室IDを既知とすることを強いられる「room-list」摩擦）は、まさにこの構造が生む摩擦の典型である。この
摩擦はarchitectが単独で契約を起こした結果であり、designerが並行して同じユースケースからUI/UX要求を
起こしていれば、契約の凍結前に会議室一覧の必要性が表面化した可能性が高い。

人間はこれを踏まえ、追加で3点を決定した（本ADRに統合する）。

## 決定

新しいagent役割**designer**を新設する。

### 責務
ユースケースから、architectと並行してUI/UXデザインへの翻訳を起こす（下記「1. 並行モデル」参照）。
成果物は、高忠実度の画面モック（各プロジェクトのモック承認プロセスが定める形式。例:
projects/reservation-frontend/adr/0004は当面、静的HTML/CSSのデザインコンプと定める）と、操作・遷移・
状態の設計。モックには**下書きのコピー**（ラベル・空状態文・エラー文言等）を含めるが、確定コピーでは
ない（最終確定は実装／L5に残す）。業務言語シナリオ（architectの領分）とは別の層である。視覚の土台は
採用済みのデザインシステムに載せる（下記「3. デザインシステム」参照）。

### 持たないもの（保証のための分離）
1. 出荷実装コードを書かない
2. 契約・シナリオを変更しない（矛盾を検知したらエスカレーション。permissions.mdのプロトコルに従う）
3. **実装コード（src/）を読まない**（実装都合にデザインが引きずられるのを防ぐ。testerのコンテキスト
   遮断＝agents.md 3節と同型の分離だが、理由は異なる。誤解の自己申告防止ではなく、実装都合のバイアス
   排除が目的）

### 読むもの
1. meta/PRINCIPLES.md（信条）
2. 自分の役割定義
3. activeContext.md（現在の状態）
4. 対象スライスの契約・受け入れシナリオ、API契約 — **ドラフト（承認前）を含む。読み取り専用**
   （下記「1. 並行モデル」の帰結。承認済みでなければ動けない、という制約は無い）

### ツール・モデル
- tools: Read, Grep, Glob, Write（architectと同一。実装コードは書けない）
- model: **opus**（他4agent＝architect / developer / tester / reviewerはsonnetのまま）。meta/adr/0004
  「agent定義の原本にモデル指定を持たせる」運用に倣い、原本（meta/agents/designer.md）とデプロイ側
  （.claude/agents/designer.md）の双方に`model: opus`を記載する

### 1. designerをarchitectと同階層（並行モデル）に置く

**旧モデル（下流。本ADR初版）**: architect（契約起草）→ 人間承認 → designer（モック作成）→ 人間:
設計骨格承認 → developer/tester

**新モデル（並行）**:
1. **orchestrator＋人間がユースケースを整理する**（何を・誰が・なぜ、業務の言葉での輪郭）
2. **architect（契約: シナリオ・API仕様）とdesigner（UI/UXモック）が、同じユースケースから並行して
   起こす**。どちらも相手の確定成果物を待たない。designerは**ドラフト（承認前）の契約・API仕様**を
   参照してよい（承認待ちで停止しない）
3. **突き合わせ（reconciliation）**: UIの要求と契約を突き合わせる。食い違い（例: UIが必要とする
   操作に対応するAPIが無い＝room-list型の欠落）は、契約が凍結される前に表面化させる。食い違いを検知
   したら、architectまたはdesignerがpermissions.mdのエスカレーションプロトコルに従い、矛盾分析
   レポート相当で人間の裁定を仰ぐ（推測で一方に合わせて先に進まない）
4. **人間が契約と設計骨格（モック）を一緒に承認する**（別々のタイミングでなく、reconciliation後に
   まとめて）
5. developer / tester（承認後、これまで通り並行作業）

**狙い**: 下流モデルでは、デザインが凍結済みの契約に制約され、UXの要求が契約側にフィードバックされない
（room-list摩擦がその実例）。同階層・並行にすることで、UXの要求を契約の設計そのものに反映させる経路
を作る。

**reconciliation工程の所在**: meta/agents.md §4の標準フローに明示する。designerとarchitectの食い違い
は、permissions.mdのエスカレーションプロトコルに従い人間が裁定する。

UI/UXを持たないプロジェクト（バックエンドのみ等）では、designerもreconciliationも登場せず、architect
の契約ドラフト→人間承認、という従来通りの経路になる。

### 2. designerが読むもの・コンテキスト遮断の変更

designerは、承認済みの契約だけでなく**ドラフト（承認前）の契約・API仕様も読む**（並行モデルの帰結。
承認待ちで停止しない）。ただし**実装コード（src/）を読まない**というコンテキスト遮断は変更しない
（実装都合のバイアス排除という目的は契約の承認状態と無関係のため）。designer.md（原本・デプロイ側
双方）の「起動時に読むもの」「コンテキスト遮断」の記述を、この変更に合わせて更新する。

### 3. 視覚の土台はデザインシステムに載せる（「ダサい」問題の根治）

designerはゼロから視覚（配色・余白・タイポグラフィ等）を自作しない。**採用済みのデザインシステム／
コンポーネントライブラリの上で構成する**ことを役割原則にする。designerはレイアウト・構成・フロー・
状態の設計に集中し、ピクセルレベルの美的判断をスクラッチで負わない。

**デザインシステムの選定自体はプロジェクト決定**である。architectとdesignerが候補を提案し、人間が
ADRで承認する（本ADRでは決定しない）。デザインシステムはフロントエンドのB層パック候補になりうる
（architecture-selection.md 4節「フロント主体パック＝コンポーネント設計規約」、6節「B層は同スタック・
同型の2本目のプロジェクトが現れた時に昇格」の原則と整合する）。現状B層カタログは空であり、各プロジェクト
はinlineでデザインシステムを選定してよい（採用にADRは要るが、B層への昇格は2本目の実証を待つ）。

### 4. 洗練フェーズ（refinementループ）とescape hatch

designerの一発の出力が実用水準に届かないことを前提に、明示の工程を定める。具体化は各プロジェクトの
モック承認プロセスADR（例: projects/reservation-frontend/adr/0004）が行う。

**refinementループ**: designer提出 → 人間クリティーク（デザインヒューリスティクスのチェックリスト:
一貫性・視覚階層・アフォーダンス・アクセシビリティ等）→ designer洗練 → 反復。設計骨格承認の前段に
位置する、名前のある工程として扱う（黙って何度もやり直すのではなく、各反復を記録する）。

**escape hatch**: 洗練をN回重ねても実用水準に届かない場合、代案に切り替える。代案の候補（プロジェクト
側が選ぶ）:
- (a) 既製UIテンプレートを丸ごと採用する
- (b) 人間・外部デザインを入力として受け取り、designerは実装向けの整形のみを行う
- (c) 視覚の野心を下げる（デザインシステムの既定値により忠実に従う等）

**メタ層が定めるのは「escape hatchを必ず持つこと」という原則のみ**。Nの具体的な値・代案の選択は
プロジェクト側（例: projects/reservation-frontend/adr/0004）が定める。無限に洗練を繰り返さない
（P-02の精神: 完璧な設計を先に追い求めない）。

### 承認
既存の「設計骨格」承認点（permissions.md）に相乗りする。新しい5つ目の承認カテゴリは作らない（各プロ
ジェクトのモック承認プロセスADRが、この相乗りを具体化する）。

## 検討した代替案

- 案A: architectがモック作成も引き続き担う（現状維持） / 不採用: 専門性の分離が必要と人間が判断
- 案B: モック作成をdeveloperに委譲する / 不採用: 実装バイアスのリスク
- 案C: 独立した新しい人間承認カテゴリ（5つ目）を新設する / 不採用: 既存の「設計骨格」承認点で足りる
- **案D（本改訂で不採用に変わった旧決定）: designerをarchitectの下流に置く（本ADR初版のモデル）** /
  不採用の理由: 契約が凍結された後にdesignerが着手するため、UI/UXの要求が契約に反映されない。
  reservation-frontendの「room-list」摩擦が、この構造的欠陥の実例として観測された。同階層・並行モデル
  （reconciliationあり）に置き換える
- 案E: designerに視覚デザインをゼロから自由に作らせる（デザインシステムに載せない） / 不採用: 一貫性の
  無い場当たり的な視覚判断（「ダサい」問題）が生じるリスクが高い。採用済みのデザインシステムに載せる
  ことで、designerはレイアウト・構成という本来の専門性に集中できる
- 案F: refinementループ・escape hatchを定めず、designerの出力をそのまま承認プロセスに乗せる / 不採用:
  一発の出力が実用水準に届かない前提を無視すると、承認が繰り返し差し戻される・無限に洗練を続ける、
  いずれかに陥るリスクがある。名前のある工程と上限（escape hatch）を先に定義する方が健全

## 帰結

- meta/agents/designer.md（役割規程の原本）・.claude/agents/designer.md（デプロイ側subagent定義）の
  「起動時に読むもの」「コンテキスト遮断」「責務」（デザインシステムの上に構成する旨・reconciliation
  ・refinementループへの対応）を更新する
- meta/agents.md 2節（designerの役割説明を並行モデルに更新）・4節（標準フローを並行モデル＋
  reconciliationステップに置き換え）を更新する。3節（designerの実装コード非参照の理由）は変更なし
- 影響を受けるプロジェクトのADR（例: projects/reservation-frontend/adr/0004）は、作成タイミングの
  記述（「シナリオ承認後」→「ユースケース整理後、architectと並行」）と、デザインシステム選定・
  refinementループ・escape hatchの具体化が必要（プロジェクト側ADRの改訂として別途行う。本ADRはそれを
  代替しない）
- reservation-frontendでは、デザインシステム選定がまだ未決（activeContext.mdに記録）。既存のRFE-A
  モック（design/mocks/rfe-a-availability-view/、代表例の配色を独自に定義したもの）は、デザイン
  システム選定後にdesignerが作り直す前提になる可能性がある（人間判断）
- reviewer相当（designerの成果物への独立監査）は新設しない。人間が設計骨格承認点で直接判断するため
  （tester→reviewerの分離とは異なる構成）。ただしrefinementループの「人間クリティーク」が、この
  非対称を部分的に埋める（人間が直接・反復的にモックを評価する）。この非対称は意図的な決定として記録
  するが、モックの数・複雑性が将来増えた場合、同種の理由（自己申告の防止）で独立監査の要否を再検討する
  余地がある
- developer.md（各プロジェクト共通のA層役割規程）は、UIを持つプロジェクトで「承認済みモックに忠実に
  実装する」という拘束を明示していない。本ADRでは変更しない。並行モデルにおいても、developerは「人間が
  承認した契約とモック」を実装する立場は変わらない。実務上の齟齬が生じたらfriction-logを経て改めて
  提案する（P-05）
