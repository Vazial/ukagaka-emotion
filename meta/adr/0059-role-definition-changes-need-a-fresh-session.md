# ADR-0059: 役割定義の変更は、セッションを開き直すまで実際には効かない

> **承認者向けサマリ**
>
> このリポジトリは、AIの役割（designer・developer・tester など）を `.claude/agents/` の下の
> Markdownファイル1枚ずつで定義している。そのファイルには、役割の説明文と、その役に渡す道具の
> 一覧（`tools:` の行）が書いてある。`meta/adr/0036` は、このファイル群を役割定義の唯一の正と
> 定めた。
>
> 2026-08-23、designer の役割定義を書き換える変更（`meta/adr/0050`。外部AIへの発注をやめ、
> designer 自身が画面を作る役へ変える）をマージした直後に、その designer を起動した。**起動した
> designer に渡されたのは、書き換える前の定義と、書き換える前の道具一覧だった。** 新しい定義は
> 「`/design` という道具で画面を作る」と定めているのに、その道具が渡されていないため、定義どおりに
> 動くことが構造的に不可能だった。
>
> 原因は1つである。役割定義のファイルはセッションを開いた時点で読み込まれ、そのセッションが
> 走っている間は更新されない。マージで実ファイルが変わっても、走っているセッションが配る定義は
> 変わらない。**「正」と「実際に走るもの」が、セッションをまたぐまで一致しない。** そして何も
> 警告しない。
>
> 実害が出かけた。症状が「定義が古い」と「道具が足りない」の2つに見えたため、起動された designer は
> 「役割定義に、発行できないときの代わりの手順を書き足すべきだ」と提案した。原因が1つだと分かって
> いれば出ない提案である。採っていれば、セッションを開き直せば消える一過性の問題への回避策を、
> 役割契約に恒久的に焼き付けていた。
>
> 決定は6点。
>
> 1. 役割定義を変えるPRがマージされたら、その役を起動する前にセッションを開き直す
> 2. 役割agentは、起動したら自分に渡された道具を定義と突き合わせ、食い違ったら作業を始めずに報告する
> 3. 一過性のズレに対する回避策を、役割契約に恒久的に書かない
> 4. 機械検査は置かない。代わりに後退条件を先に書く
> 5. designer が出す寸法は常に未実測である、と定義に書く
> 6. designer が実装コードの代わりに何を読めば足りるかを、定義が名指しする
>
> 払うもの: 役割定義を変えるたびにセッションを1回開き直す手間がかかる。決定2の自己検証は、
> 役割agentの起動ごとに数行分の出力を増やす。

## 文脈

### 1. 何が起きたか

2026-08-23、`meta/adr/0050` をマージした。この決定は designer の役割を作り替えるものである——それまで
designer は「自分では画面を発案せず、外部のAI（Gemini）に発注して、返ってきたものをそのまま置く」役
だった。`/design`（画面のキャンバスを組み立てて共有できる形で発行する道具）が使えるようになったため、
designer 自身が画面を作る役へ変えた。

マージの直後、人間から「designer がうまく効きそうか実測したい」という要請があり、実際に designer を
起動した。題材は、この製品で唯一残っていた未決の画面判断（スマホの画面で、地図を畳むか、地図に
重ねるか）である。

designer は成果物を作ったが、依頼した形では出せなかった。報告された事実は2つ。

- 起動時に渡された役割定義が、`meta/adr/0050` を適用する**前**の版だった
- 渡された道具が `Read`・`Grep`・`Glob`・`Write` の4つで、新しい定義が要求する `Skill`（`/design` を
  起動する道具）・`Artifact`（発行する道具）・`Bash` が付いていなかった

### 2. 症状は2つに見えたが、原因は1つだった

改定前の `designer.md` の `tools:` 行を確認すると `Read, Grep, Glob, Write` であり、**渡された道具立てと
完全に一致した**。説明文も改定前のものと一致した。つまり道具が足りなかったのは、新しい定義が道具の
指定を書き忘れたからではない。**古い定義がそのまま配られていたからである。** 新しい定義の `tools:` 行は
`Read, Grep, Glob, Write, Bash, Skill, Artifact` であり、正しく書かれていた。

Claude Code は役割定義のファイルをセッションを開いた時点で読み込む。走っているセッションの中では、
実ファイルが変わっても配られる定義は変わらない。`meta/adr/0036` が「`.claude/agents/**` が役割定義の
唯一の正である」と定めたのは、runtime ごとに別のコピーを持たせないためだったが、**その「正」が実際に
走るものと一致するのは、次にセッションを開いたときからである**。

### 3. 気づけたのは偶然だった

designer がこの食い違いに気づけたのは、依頼文にたまたま「あなたの役割定義は 2026-08-22 に
`meta/adr/0050` で改定されたばかりなので、`.claude/agents/designer.md` を読むこと」と書いてあった
からである。designer 自身がそう報告している——その一文が無ければ、古い定義（自分では発案せず外部AIに
発注する）に従い、依頼を丸ごと取り違えていた。

つまり、**現状この食い違いを捕まえる仕組みは無く、今回は依頼文の書き方に依存して偶然捕まった**。

### 4. 原因を取り違えた提案が出かけた

症状が2つに見えたため、designer は次を提案した——「新しい定義には、発行する手段が無いときにどうするか
の受け皿が書かれていない。書き足すか、道具を渡すか、どちらかが要る」。

これは原因が1つだと分かっていれば出ない提案である。採っていれば、セッションを開き直せば消える問題に
対する迂回路を、役割契約の恒久的な条文として書き込んでいた。役割契約は AI の行動を縛るものなので、
一度書けば以後ずっと「発行できないときは orchestrator に渡す」という経路が正規のものとして残る。
`meta/adr/0050` が廃止したばかりの「orchestrator が designer の代わりに実行する」という構図が、
別の理由で戻ってくることになる。

### 5. 同じ起動で、designer の定義の不足が2つ見つかった

これはセッションの古さとは別の話で、`meta/adr/0050` が書いた定義そのものの不足である。

**寸法を検証できない。** designer は自分が描いた画面の寸法を測る手段を持たない（実際に描画して測る
道具が無い）。今回 designer は「カードは3件と4件目の頭まで見える」「地図上のピンは3つ見える」と
いった具体的な数字を出したが、これらは全部作図上の値である。designer 自身がそう報告している。この
製品の運用規則は「測っていない見た目の主張には未実測と書く」と定めているが、**役割定義の側には同じ
要求が無い**。下流がこれを実測値と誤読すると、案の選択が根拠のない数字に乗る。

**実装コードを読まない代わりに何を読むかが書かれていない。** `meta/adr/0050` は「実装コードを読まない」
という遮断を維持した（実装の都合にデザインが引きずられるのを防ぐため）。今回は、契約のうち画面の
DOM構造を定めたファイルと、プロジェクトの現在状態を書いたファイルが非常に詳しかったため、タップ
できる最小の大きさ・要素の識別子・カードに必ず載る項目といった制約を契約側だけで拾えた。designer は
「契約が薄いプロジェクトでは同じことができない」と報告している。**読まない代わりに何を読めば足りるかを
定義が名指ししていないと、契約が薄いプロジェクトで designer は制約を知らないまま描く。**

## 決定

1. **役割定義（`.claude/agents/**`）を変えるPRがマージされたら、その役を起動する前にセッションを
   開き直す。** 手順を `meta/guardrails.md` に置く。マージした本人が同じセッションで続けて起動しない、
   というのが実際に守るべき形である。

2. **役割agentは、起動したら自分に渡された道具を定義と突き合わせる。** 自分の役割定義ファイルの
   `tools:` の行を読み、そこに書かれた道具が実際に渡されているかを確かめる。食い違っていたら、作業を
   始めずにその事実を報告して止まる。今回この食い違いを捕まえた唯一の経路が、まさにこれ（designer が
   自分の道具立てと定義を見比べた）である。全役割agentの定義に共通で入れる。

3. **一過性のズレに対する回避策を、役割契約に恒久的に書かない。** 具体的には、`meta/adr/0050` に
   「発行できないときは orchestrator に渡す」という受け皿を足さない。セッションを開き直せば道具は
   揃う。今回 orchestrator が発行を引き取ったのは、その場をしのぐための一度きりの処置であって、
   正規の経路ではない。

4. **機械検査は置かない。** 走っているセッションが何を配っているかは、git からは見えない。検査を
   書く先が無い。代わりに後退条件を先に書く——**決定2の自己検証が入ったあとで、なお古い定義のまま
   走った事例が2回記録されたら**、役割定義の変更を検知して警告する仕組み（マージ後に警告を出す、
   起動時にファイルの更新時刻を見る等）を別のADRで検討する。

5. **designer の定義に、寸法の扱いを書く。** designer が成果物に書く寸法・件数・可視範囲は常に
   作図上の値であり、実測値ではない。designer はそれらに未実測と明示する。下流（人間の判断・
   developer の実装）がこの数字に依存する場合は、orchestrator が実測する。

6. **designer の定義に、実装コードの代わりに読むものを名指しする。** 画面のDOM構造を定めた契約
   （このリポジトリでは `contracts/*-browser-interface.yaml`）と、プロジェクトの現在状態を書いた
   `activeContext.md` を、実装コードの代わりに読むものとして定義に挙げる。そこに書かれていない制約
   （タップできる最小の大きさ、要素の識別子、必ず載る項目など）を必要とした場合は、推測せずに
   報告する。

## 検討した代替案

- **役割定義の変更を検知して警告する仕組みを、いま作る**: 不採用。走っているセッションの中身は git から
  見えないため、検知をどこに置くかが自明でない。加えて、決定2の自己検証で足りるかどうかがまだ分かって
  いない（今回の1件では実際に機能した）。P-05（要るようになってから作る）に従い、後退条件（決定4）を
  書いて待つ。
- **designer に道具が無い場合の受け皿を `meta/adr/0050` に書き足す**: 不採用。決定3のとおり、原因を
  取り違えた対処になる。これは designer 自身の提案だが、原因が1つだと判明した時点で前提が崩れている。
- **役割定義を変えるPRを、その役を使わないセッションからしか出せないようにする**: 不採用。守れたか
  どうかを機械で見られないうえ、ADRの起草と実測を別セッションに強制すると、今回のように「改定して
  すぐ実測する」という有用な流れが取れなくなる。開き直すコストのほうが小さい。

## 帰結

- 役割定義を変えるたびにセッションを1回開き直す。開き直すまでの間、その役を起動しても旧定義で走る。
- 決定2の自己検証は、役割agentの起動ごとに数行の確認を増やす。食い違いが無ければ何も報告しない。
- `meta/adr/0050` の初回実運用で分かったことを、この1本にまとめた。0050 自体は書き換えない
  （`meta/adr/0053` 決定4: 承認済みのADRは書き直さない）。決定5・6は designer の定義ファイルへ
  直接反映する。
- 今回 orchestrator が designer の成果物を発行したことは、決定3のとおり正規の経路ではない。次に
  designer を起動するときは、開き直したセッションから起動し、designer 自身が発行する。
