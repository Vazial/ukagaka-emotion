# ADR-0044: Codexは検証を弱めず、重複実行・Browser反復・過大出力を避ける

> **承認者向けサマリ**: 認証スライスでCodexは、必要なL1〜L4の検証に加え、同じ成功済み検証の再実行、
> Browserの接続・画面確認の反復、全量ログ・diffの取得を重ね、会話のコンテキストを過度に消費した。
> **L1〜L3の事前検証と既存のL4フローは維持する**。改善するのは検証の強さではなく、同じ成果物に対する
> 重複実行と不要な出力量である。Codexは各適用ゲートを変更後に一度通し、変更がない限りその成功証跡を
> 再利用する。GitHub Actionsは独立した最終証跡として引き続き全ゲートを実行する。Browserは画面提示・
> 意味理解を要するUX確認・視覚的不具合調査に限り、同一画面の反復確認は行わない。既知CLIの探索と
> コマンド結果の出力も最小化する。これはCodexだけの運用投影であり、Claude共通role定義、CI、
> `meta/agent-runtime-mapping.md` は変更しない。

## 文脈

Dining Radarの認証実装で、L1〜L3、L4、GitHub Actions、実ブラウザ確認を行った。正しさを
機械検証で担保するため、L1〜L3をPR前に実行し、L4も既存のtesterフローに従うこと自体は必要である。
人間も2026-08-01にL1〜L3の維持を明示した。

一方で、トークンを多く使った主因は検証そのものではなかった。同じ成功済みの検証を変更なしに繰り返す、
成功ログ・ファイル一覧・diffを全量で読む、Browserの接続仕様・DOM・スクリーンショットを反復して取得する、
既知のCLI経路を再探索するといった、成果物の正しさを増やさない操作が混ざっていた。

既存のADR-0039は、role成果物を次段へ渡す前にorchestratorが適用ゲートを実行することを定める。
この一度の実行を省略することは今回の対象外である。またADR-0041は全PR種別で機械検証を必須とし、
GitHub Actionsは統合結果に対する独立した証跡である。したがって「CIだけにする」ではなく、
**各段で必要な一回を守り、同じ段の無変更な再実行をしない**ことが今回の判断である。

Browser操作は内部でPlaywright系の操作面を用いるが、通常の自動テストでは検出しにくい表示や
利用者の操作理解を確認できる。全面禁止はADR-0024の走破・画面提示の用途を失わせるため採らない。

## 決定

### 1. 適用ゲートは維持し、無変更な成功証跡を重複実行しない

- L1〜L3は、実装成果物をPRへ出す前に従来どおり実行する。L4は既存のtester/reviewerフローに従う。
  ADR-0039の「role成果物を受け取ったorchestratorが適用ゲートを実行する」責任も変えない。
- 適用ゲートが成功した後、当該ゲートの対象となる実装・設定・テスト・依存定義が変わっていなければ、
  CodexはPR作成直前や報告直前に同じコマンドを再実行しない。結果、対象、実行時点を簡潔に引き継ぎ、
  PRにはその証跡を記載する。
- GitHub Actionsはローカル成功を置き換えない。PRの統合候補に対する独立した全ゲートの証跡として維持し、
  CI成功後も、変更がなければローカルで同じゲートを再実行しない。
- 失敗、対象差分、依存・実行環境の変更、または証跡の不足がある場合は、再実行してよい。失敗を隠すために
  省略してはならない。

### 2. Browserは目的を持つ最小限の確認に限定する

CodexのBrowser操作は、次のいずれかに限る。

1. 人間へ画面を提示する合意済みの確認点
2. ADR-0024が対象にする、意味理解を要するUX・control surface・ユースケース走破
3. 自動検証だけでは切り分けられない視覚的な不具合の調査

利用前に、確認する画面・目的・成功/失敗の判断を短く定める。同一画面について、関連UIの変更も新しい
不具合仮説もないのに、DOM取得・スクリーンショット・再ログインを繰り返さない。既存のブラウザ接続と
ローカルサーバーを再利用できる場合は再接続・再起動を避ける。

BrowserはL1〜L4またはCIの代替ではない。反復可能で意味理解を要しない確認は、将来必要になった時点で
プロジェクトの自動テストへ移すかを検討する。本ADRはその自動テストやCIを新設しない。

### 3. Codexの探索・出力は、判断に必要な最小量にする

- ADR-0037のhost CLI discoveryに従い、一度確認できた実行経路は同じセッションで再利用する。
  ただし、ホスト固有の絶対パス、認証情報、環境変数をリポジトリへ記録しない。
- 成功時はquietなコマンドと件数・終了コード・要約を優先する。失敗時だけ、原因を判断できる範囲で
  詳細ログを読む。
- `git status`、diff、文書は、まず変更ファイル一覧・統計・関連箇所を確認する。全量のdiffや長文ログを
  既定で取得しない。規程など「全文を読む」ことが明示された入口文書はこの限りでない。
- 既存の共有role定義・runtime model mappingをCodex効率化のために書き換えない。モデル選択の変更が必要に
  なった場合は、別の人間判断として扱う。

### 4. 適用範囲

この決定はCodexの入口規約 `AGENTS.md` にだけ投影する。Claudeのrole定義、共有CI、検証ゲート、
`meta/agent-runtime-mapping.md`、既存PRには変更を加えない。

## 検討した代替案

- **案A: L1〜L3をGitHub Actionsだけに任せる** / 不採用: 失敗をPR作成後まで遅らせ、手戻りを減らさない。
  人間もL1〜L3の事前検証を維持する判断をした。ADR-0039・0041にも反する。
- **案B: Browserを禁止し、すべてを自動テストへ移す** / 不採用: 画面提示、未知の視覚的不具合、
  意味理解を要するUX確認を失う。繰り返せる機械的確認だけを後から自動化すればよい。
- **案C: 共有role定義やCIをCodex向けに最適化する** / 不採用: Claudeと共用する契約を、Codex固有の
  実行環境の摩擦だけで変えることになる。今回の問題は入口運用と出力量で解ける。
- **案D: 検証を維持しつつ、無変更な再実行・Browser反復・全量出力だけを避ける** / 採用:
  正しさの根拠を弱めず、観測された摩擦にだけ最小限に対処できる。

## 帰結

- CodexはL1〜L4とCIの責務を維持したまま、同じ成功結果の再実行と冗長なツール出力を減らす。
- Browser確認は残るが、利用目的と回数がレビュー可能になる。画面の最終判断は従来どおり人間にある。
- `AGENTS.md` はCodexだけにこの運用を読み込ませる。共有規程やClaudeの実行契約のSSoTを増やさない。
- この運用でも同種の摩擦が継続する場合は、実測をfriction logに記録してから、より機械的な改善を別途検討する。
