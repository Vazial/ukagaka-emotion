# ADR-0041: PRの種別ごとに「人間が何を判断するか」を明示する

> **承認者向けサマリ**: PRの種別によって人間が判断すべきことは全く違うのに、**すべて同じ重さで出していた**。
> 昇格PR（`project/<p>` → `main`）は中身がすべて承認済みコミットの積み上げで**新しい決定を含まない**のに、
> DoD表・承認方式・長い論拠を書いて**読む必要のないものを読ませていた**（#55）。逆に、形式上は機械的な
> 同期PRでも**衝突解決で編集判断をしている**場合があり、そこが本文に埋もれていた（#60）。決定は2点——
> **PRを4種別に分類し、テンプレ冒頭で明示する**／**機械検証はどの種別でも必須、人間の判断は「そのPRに
> 人間がまだしていない決定が含まれるとき」だけ**とする。判定基準を「PRの形（base/head）」ではなく
> **「未承認の決定を含むか」**に置くのが要点である——同じ同期PRでも、衝突解決を含めば判断が要る。

## 文脈

人間の指摘（2026-07-30）:

> PRの出し方は考えてほしい。昇格ならユーザが合意してるからレビューいらないよね？とかの区別ができて
> いない

実例が両方向に出ていた。

**過剰**: #55（昇格PR、`project/reservation-frontend` → `main`）に、DoD充足の表・承認方式の選択・
各スライスの論拠を書いた。しかし中身は #35・#39・#45・#46・#49・#53 として**既に人間が承認・マージ
した13コミットの積み上げ**であり、**新しい決定はゼロ**だった。読む必要のないものを読ませていた。

**過少**: #60（同期PR、`main` → `project/reservation-frontend`）は形式上「main取り込みのみ」だが、
実際には activeContext の衝突を解決する過程で「**解決済み項目を『（解決済み）』と書いて残さず削除する**」
という編集判断をしていた（ADR-0034 の accretion 禁止に照らした判断）。これは人間が確認する価値のある
判断だが、本文の中ほどに埋もれていた。

つまり **PRの形（base/head）と、人間が判断すべきかどうかは一致しない**。

## 決定

### 1. PRを4種別に分類し、テンプレ冒頭で明示する

| 種別 | base ← head | 中身 | 人間の判断 |
|---|---|---|---|
| **スライス** | `project/<p>` ← `<type>/<p>-<slice>` | 新しい作業 | **要**（4承認点のうち該当するもの: 契約／設計骨格／step実装／規程変更） |
| **meta** | `main` ← `meta/<slug>` | 共有ガバナンス | **要**（規程変更） |
| **昇格** | `main` ← `project/<p>` | 承認済みコミットのみ | **不要** |
| **同期** | `project/<p>` ← `main` | mainの取り込み | **衝突解決を含むときのみ要** |

### 2. 機械検証は全種別で必須。人間の判断は「未承認の決定を含むとき」だけ

**判定基準は「そのPRに、人間がまだしていない決定が含まれるか」**である。PRの形ではない。

- **機械検証（L0〜L4）はどの種別でも省略しない**。昇格・同期でも、統合して初めて壊れる可能性がある
  （例: ADR-0038 でシナリオIDの名前空間をリポジトリ全体にしたため、昇格時に別プロジェクトの採番と
  衝突しうる）。orchestrator は統合結果に対して検証を実行してから提出する（ADR-0039 決定1）。
- **人間の判断が不要な種別（昇格・衝突なしの同期）では、本文冒頭に「承認事項: なし」と明記する**。
  中身が承認済みコミットのみであること、マージが branch protection の形式要件であることを1行で述べる。
  DoD表・承認方式・論拠は**書かない**（既に承認済みPRに書かれている）。載るものの一覧と検証結果だけを示す。
- **判断を含む場合は、それを冒頭に置く**。同期PRで衝突を解決したなら「**判断した箇所**」を最初に書く。
  形式上の種別が「同期」であることを理由に埋もれさせない。

### 3. 適用範囲

以後のPRに適用する。既存PRには遡及しない。

## 検討した代替案

- **案A: 現状維持（全種別に同じテンプレを適用）** / 不採用: 人間の指摘そのものが実害の報告である。
  読む必要のないものを読ませ、読むべきものを埋もれさせていた。
- **案B: 昇格PRを廃し、`project/<p>` を直接 `main` にfast-forwardする** / 不採用: `main` は branch
  protection でPR経由のみ（`meta/guardrails.md` §1）。構造上PRは必要であり、変えるべきは**PRの中身の
  書き方**であって経路ではない。
- **案C: 種別を base/head から機械判定し、テンプレを自動で出し分ける** / 不採用（当面）: 決定2の通り
  **形と判断の要否は一致しない**（衝突解決を含む同期がその反例）。機械判定は誤った安心を与える。
  P-05 に従い、手で選ぶ運用で摩擦が出てから考える。
- **案D（採用）: 4種別＋「未承認の決定を含むか」を判定基準にする** / 採用: 形と判断を分けて扱えるため、
  #55（過剰）と #60（過少）の両方を同時に直せる。

## 帰結

- 昇格・同期PRが短くなり、読み手が「何も判断しなくてよい」ことを1行で判別できる。
- 同期PRの衝突解決が、判断として可視になる。
- **`.github/pull_request_template.md` に種別の選択を追加する**（同一PRで実施）。ADR-0035 が承認方式の
  二択をテンプレに載せたのと同じ形——**全PRが通る関所に載せることで飛ばされにくくする**（P-04）。
- **`meta/guardrails.md` §2 に条文として追加する**（同一PRで実施）。ADR-0039・0040 で「規程反映を宿題に
  回すとドリフトする」と学んだ通り、同じPRで閉じる。
- 検証の省略は認めない。「承認事項なし」は**人間の判断が不要**という意味であって、**機械検証が不要**と
  いう意味ではない。この2つの混同は、本ADRが最も避けたい誤読である。
