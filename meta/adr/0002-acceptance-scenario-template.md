# ADR-0002: 受け入れシナリオの書き方規約を雛形として追加する

## 文脈

初適用スライスRSV-Cで、契約（受け入れシナリオ）の可読性への人間の指摘が2回発生した（FR-002: フラットな11本並びと要約なしAPI仕様、FR-003: 読者に伝わらないヘッダ項目）。friction-logの運用ルール「同原因2回で構造的欠陥」に該当。原因は「人間が短時間で承認できる契約の書き方」の規約がA層に無いこと。

## 決定

meta/templates/acceptance-scenario.feature を追加し、以下を雛形として固定する:
1. ヘッダは読者（承認者）向けの最小情報のみ（正体・ステータス・ID凡例）。書き手向け規約は規程から繰り返さない（P-04）
2. キーワードは英語Gherkin（Given/When/Then）+ 日本語文（行頭が揃い構造が追える）
3. シナリオは業務ルール（Rule:）でグルーピングし、同型の拒否ケースはScenario Outline + 例表に畳む
4. 出典（不変条件・ADR）は各Ruleの直下にコメントで置く
5. シナリオIDは登場順・欠番は再利用しない

## 検討した代替案

- 案A: verification.mdに文章の規約として追記 / 不採用の理由: 雛形をコピーして書き始める方が従いやすく、文章ルールより機械的（P-03の精神）
- 案B: 日本語キーワード（前提/もし/ならば） / 不採用の理由: 初適用で人間が英語キーワードの方が読みやすいと判断した実績

## 帰結

- FR-002/FR-003の押し込み先が確定する
- 今後の契約起草時、architectはこの雛形から始める
- 雛形末尾の記入コツに「シナリオをAPIスキーマの具体値に落として表現可能性を確認する」を含める（FR-005の教訓）
