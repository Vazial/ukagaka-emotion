# ADR-0077: 人間が立てた大きなチケットをClaudeが分解した子チケットは、親の作業場所で指揮役が進める

> **承認者向けサマリ**
>
> 伺か向けの試作（KEN-38）を進めたとき、人間が立てたチケットは「やりたいこと」の大きさで、実際の作業は
> 契約の起草・実装・受け入れテスト・監査と、途中の追加作業に分かれた。ところが現行の手順は、
> 「Todoへ移すのは人間だけ」「チケットごとに作業場所を作る」としか書いておらず、分解した小さな作業を
> どう扱うかが無い。人間からは「人間が作るチケットは大きい機能なので、Claudeがタスク分解して子チケットに
> したものは、親チケットのClaudeの作業場所での管理でよい」との指示があった。
>
> 決定は4点。
>
> 1. 子チケットは、親（人間がTodoへ移したチケット）の範囲に収まる分だけ、指揮役がLinearの子として作る
> 2. 子はTodoへ移す人間の操作を要さず、指揮役が状態を動かしてよい。範囲の合意は親のTodo移動が兼ねる
> 3. 作業場所は子ごとに作らず、親のものを使う。PRは原則として親1つに1本（ADR-0071）
> 4. 止まる条件は変えない。親の範囲を超える判断が要る子は、作らずに親へコメントして止まる
>
> 払うもの: 親の説明欄が薄いと、子の範囲が指揮役の解釈で膨らむ。膨らみは「親の範囲を超えたら止まる」
> （決定4）と、人間が見る親チケットの説明欄で抑える。

## 文脈

`meta/orchestration.md` §2 は「AIは Todo へ移さない。範囲の合意は人間が Todo へ移す操作で成立する」
（ADR-0068 決定5）と定め、§3 は1チケットごとに作業場所を作る前提で書かれている。これは人間が立てた
チケットが1つの作業単位である間はそのまま成り立つ。

しかし KEN-38 では、1つの相談から「契約の承認」「公開仕様の補足」「実装のやり直し」「監査対応」と
作業が分かれ、Linear の外で順に回した。どれも親の範囲に収まる作業だったが、現行の手順に従うなら
それぞれに人間のTodo移動が要ることになり、実態とも指示とも合わない。

モデルケースは KEN-18（dining-radar。症状・場所・根拠が説明欄に揃った小さな Bug で、Project とラベルが付く）。
子チケットは、これと同じ形で書く。

## 決定

### 決定1. 子チケットは、親の範囲に収まる分だけ指揮役が作る

親は、人間が作り、Todoへ移したチケットとする。指揮役は着手前のタスク分解（`meta/orchestration.md` §7、
ADR-0071）で、親の説明欄だけを根拠に子を作る。子は Linear の子（`--parent-id`）で、親と同じ Project を付け、
ラベルは Feature / Bug / Improvement から付ける。説明欄には、KEN-18 と同じく症状または目的・場所・根拠を書く。

### 決定2. 子はTodoへ移す人間の操作を要さない

親のTodo移動が範囲の合意であり、その範囲に収まる子へ及ぶ（ADR-0068 決定5の及ぶ範囲の明確化）。指揮役は
子を In Progress / In Review へ動かしてよい。親にも子にも書いていない判断が要るときは、従来どおり止まる。

### 決定3. 作業場所は親のものを使い、PRは原則として親1つに1本

子ごとに作業場所を作らない。子の作業は親の作業場所と枝で行い、PRは親チケットに紐づく1本にまとめる
（ADR-0071の「同じ判断のまとまりは1本」）。承認の性質が違う子（例: 規程変更と、それを反映するだけの同期）は
分けてよい。人間への報告は親チケットを示す（ADR-0076）。子は、親のPRがマージされたあとに指揮役が閉じる。

### 決定4. 止まる条件は変えない

契約・設計骨格・step実装・規程の変更に人間の合意が要ること、チケットに書いていない判断が要ること、
機械検証が赤のまま直らないことは、子でも同じである。分解の途中で親の範囲を超える作業が見つかったら、
子を作らず、親に判断を仰ぐ型（決めること・選択肢・トレードオフ・推奨）でコメントして止まる。

## 検討した代替案

- 案A: 子ごとに人間がTodoへ移す / 不採用: 人間のTodo移動が作業の数だけ増え、親の範囲に収まる分解でも
  止まることになる
- 案B: 子ごとに作業場所とPRを作る / 不採用: ADR-0071が戒めた「3本に割りすぎた」状態を招く

## 帰結

- 良い影響: 人間の判断は親チケットの説明欄とTodo移動と承認点に集まり、分解した作業のたびに呼ばれない
- 払うもの: 親の説明欄の質が、子の範囲の質を決める
- 波及する作業: `meta/orchestration.md` §2・§3・§7 に反映する。派生リポジトリには template-sync で届く
