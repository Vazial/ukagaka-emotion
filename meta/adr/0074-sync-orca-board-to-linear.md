# ADR-0074: Orcaのワークスペースボードは、作業場所を作るときと節目ごとにLinearへ紐付ける

> **承認者向けサマリ**
>
> 2026-09-27、Orcaのワークスペースボードが「良さそうだが連動していない」と指摘された。
> 調べると、ボードの列（Todo/In progress/In review/Done）は`workspaceStatus`、チケットとの
> 紐付けは`linkedLinearIssue`という、作業場所ごとのフィールドで決まっていた。どちらも設定されて
> いなかったため、全部が既定値の`in-progress`のまま積み上がっていた。
>
> `meta/orchestration.md` §1は元々「作業場所の一覧＝Orcaのボード（窓。状態は持たない）」とし、
> 状態のSSOTはLinearだと定めている。この決定は、その原則を変えない。**ボードはLinearの写しの
> ままにし、作業場所を作るとき・節目ごとに、この2つのフィールドを実際に埋める**ようにするだけである。
>
> 決定は2点。
>
> 1. チケットの作業場所を作るときは`--linear-issue`を必ず付ける（§3手順2は既に書いていたが、
>    実際には守られていなかった）
> 2. §3手順7「節目ごとに書く」で、チケットのコメントを書くのと同時に`orca worktree set
>    --workspace-status`も更新する

## 文脈

2026-09-27、実際のボードを見ると6枚の作業場所カードが全部「In progress」に積まれていた。
内訳を`orca worktree list --json`で調べると、`main`ブランチの素の端末が4枚（指揮役の居場所。
§1・§3手順2が元々「チケットの作業場所とは分ける」としていたもの）、指揮役自身の作業場所が1枚
（このセッション。複数チケットにまたがり、単一チケットには紐付かない）、そして本物のチケット
作業が1枚（dining-radarの`docs/dining-radar-after-split`）だった。

最後の1枚は、対応するPR #1が既にマージ済みに見えたため、当初「片付け忘れの放棄物」と誤認して
削除しかけた。中身を見ると、KEN-24（人間裁定待ち4件）を人間が確認するための、未コミットの
ローカル専用デモ機能だった。`--linear-issue`が設定されていれば、この誤認は起きなかった。

## 決定

### 1. チケットの作業場所は`--linear-issue`を必ず付けて作る

`meta/orchestration.md` §3手順2は元々この手順を書いていたが、実際には守られておらず、
今回の6枚のうち紐付いていたものは0枚だった。実効性を持たせるため、手順2の文言をそのまま
運用する（変更なし）。今回見つかった1枚（dining-radarの作業場所）は、この決定にあわせて
KEN-24へ手で紐付け直した。

### 2. 節目ごとに`workspace-status`も更新する

§3手順7「節目ごとに書く」（着手・役割の完了・止まった理由・PR作成をチケットのコメントに残す）を
行うのと同時に、`orca worktree set --workspace-status`をLinearのチケット状態に合わせて更新する。

| チケットの状態（Linear） | `workspace-status` |
|---|---|
| In Progress | `in-progress` |
| In Review（Draft PR作成後） | `in-review` |
| Done（マージ後） | `completed` |

Linearが状態のSSOTである原則（§1）は変えない。ボードは表示の写しを合わせるだけで、
新しい状態の持ち場を作らない。

### 3. 指揮役の居場所はPin留めする（人間の操作）

`main`ブランチの素の端末、および複数チケットにまたがる指揮役自身の作業場所は、
チケットに紐付けない（§1・§3手順2のまま）。ボード上でPin留めし、Todo/In progress等の
列から外す。Pin留めはCLIから操作できないため、これは人間がボードUI上で行う。

### 4. マージ済みの作業場所は削除する

チケットのPRがマージされたら、対応する作業場所は`orca worktree rm`で削除する。
削除する前に、未コミットの変更が残っていないかを確認する（今回のように、マージ済みの
ブランチの上に別の未コミット作業が乗っている場合があるため）。

## 検討した代替案

- ボード側に状態のSSOTを移す（Linearを見ない） / 不採用の理由: §1の原則（状態のSSOTはLinear）を
  変える大きな決定になる。今回困っていたのは「窓が汚れている」ことで、「窓の外に別の家を建てる」
  必要はない
- 何もしない（気づいたときに手で直す） / 不採用の理由: 今回、本物の作業を「放棄物」と誤認して
  削除しかけた。紐付けが無いことが実害（誤削除の危険）に直結した

## 帰結

- 次にチケットの作業場所を作るときは`--linear-issue`を付ける。節目ごとのコメント更新に
  `workspace-status`の更新が1つ増える
- 指揮役の居場所（main端末・複数チケットにまたがる作業場所）はPin留めし、ボードのTodo/In
  progress等の列から外す（人間の操作）
- マージ済みの作業場所は、未コミットの変更が無いことを確認してから削除する
