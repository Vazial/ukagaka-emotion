# ADR-0046: 検証ツール（govlint・build.gradle）を「ゲート」として扱い、AIから施錠する。開錠は人間、施錠の確認は機械

> **承認者向けサマリ**: `meta/agents.md` §6 は「検証インフラのうちロジックを持つもの（build.gradle・
> govlint等）はdeveloperの領分」と**明文で**定めているが、orchestrator がこれを破って自分で書いた事例が
> **通算4回**（FR-006/008/009/022。cause_key `orchestrator-as-substantive-source`）。**明文の禁止が4回
> 破られた以上、規程への書き足しでは直らない**（P-04: 口頭ルールにせず構造で強制する）。決定は4点。
> **(1)** `.claude/settings.json` の deny に `meta/tools/**` と `build.gradle*` の Edit/Write を加える。
> **(2)** これは orchestrator だけでなく developer も止める——**実測により、deny はサブエージェントにも
> 継承されることが確定した**（本ADR「実測」節）。したがって `meta/permissions.md` の当該行を、隣接する
> 「CIワークフロー」行と同じ扱い（**ゲート変更は人間承認**）に揃える。段差があったのはそもそも規程の側
> である。**(3)** 開錠は人間が deny を外すコミットで行い、**施錠されたままであることを govlint が ERROR
> で検証する**——開錠したまま**マージできない**。開錠の可否は人間の判断だが、閉め忘れは機械が確定できる
> （P-04）。**(4)** `.claude/settings.json` 自体は deny に含めない（理由は決定4）。
> **本ADRは鉄壁ではない**——Bash 経由の抜け道は残る。止められるのは「うっかり」だけであり、FR-022 が
> うっかりの4連発である以上それで足りる、という費用対効果の判断である（決定5）。

## 文脈

### 1. 何が起きたか

`meta/agents.md` §6「orchestratorの制約」は次を明文で禁じている。

> **実質的成果物を自ら作らない（meta/adr/0014）**: (…) 検証インフラのうち、ロジックを持つもの
> （build.gradle・govlint等）は**developerの領分**（テスト付き）、薄い宣言的なCIワークフロー
> （`.github/workflows/`）のみorchestratorが直接編集してよい。(…) 検証インフラの問題は発見即修正
> （自己採点）せず、修正をdeveloper/testerに委譲してフローに載せる。

にもかかわらず、orchestrator は ADR-0038（シナリオID検査の3欠陥）と ADR-0043（契約の承認記録）で
`meta/tools/govlint.py` を自分で書いた。`projects/reservation-system/build.gradle` も同様に直接編集した。

cause_key `orchestrator-as-substantive-source` の出現は**通算4回**である（FR-006・FR-008・FR-009・
FR-022。うち FR-008 は「技法の指定」という別の現れ方だが、根は同じ「orchestrator が実質的判断の源に
なる」）。govlint の cause_key 再出現REPORTは friction-log ファイル単位でしか数えないため、機械には
3回に見えている（この計数の穴は別途 activeContext に記録済み）。

### 2. なぜ「規程に書き足す」では直らないか

**すでに書いてある。** §6 は禁止の理由（(a)非バージョン管理になる (b)orchestratorが劣化の点になる
(c)agentの独立導出を短絡させる）まで説明している。それでも4回破られた。

破られ方に共通するのは、**悪意でも規程の不知でもなく「その瞬間、禁止されていることを想起しなかった」**
という点である。FR-022 の実例では、orchestrator が違反に気づいたのは**別件のブリーフを書くために §6 を
読み返したときの偶然**であった。「気づけば止まる」型の対策（PRテンプレのチェック項目・レビュー時の
目視）は、**気づかないことが失敗の中身である以上、同じ穴に落ちる**。

P-04（構造で強制する）が要求しているのはここである。**禁止を、想起に依存しない位置に置く。**

### 3. `meta/permissions.md` に段差がある

権限表の隣り合う2行が、実は同じ性質のものを別扱いしている。

| 行 | 対象 | 人間の関与 |
|---|---|---|
| 16 | ビルド設定・検証ツール（build.gradle・govlint等） | **原則関与しない**（developerがテスト付きで実装） |
| 17 | CIワークフロー（`.github/workflows/`） | **ゲート（必須チェック）の変更時のみ承認** |

しかし `govlint.py` と `build.gradle` は「**正しさを判定する機械そのもの**」であり、ワークフローファイルは
それを起動する薄い宣言にすぎない。**判定ロジックの方がゲートとしての本体である。** 16行目が
これを「実装の一部」として扱っていたのは、L0〜L4 という検証の階層（`meta/verification.md`）を権限表に
射影しそこねた結果である。

FR-022 で orchestrator が4回踏み抜いたのは、この段差だと考えられる。**「実装には関与しない」と書いて
ある行の対象物が、実はゲートだった。**

## 実測（証跡）

ADR-0040 が確立した先例（**権限機構の性質は推測せず実測して証跡を残す**）に従い、設計前に測定した。

測定方法: `.claude/settings.json` の deny に `Edit(./meta/tools/**)` と `Write(./meta/tools/**)` を
一時的に追加し、orchestrator と developer サブエージェントの双方から書き込みを試みた（2026-08-03）。

| 実行主体 | ツール | 結果 |
|---|---|---|
| orchestrator | `Write` | **拒否** — `File is in a directory that is denied by your permission settings.` |
| developer（サブエージェント） | `Write` | **拒否** — 同一の文言 |
| developer | `Edit` | **拒否** — 同一の文言 |
| developer | `Read` | **通過**（deny はツール単位。ADR-0040 の実測結果と整合する） |
| developer | `Bash`（`>>` によるリダイレクト） | 拒否。ただし `.claude/settings.json` に該当ルールは無く、**別機構による判定**である |

**最も重要な結果: deny はサブエージェントに継承される。** パスベースの deny では、orchestrator と
developer を区別できない。したがって activeContext に記録されていた当初案——「orchestrator のツール権限
からのみ deny する」——は**この形では成立しない**。

`Bash` の結果は本ADRの根拠に用いない。1回の観測では、内容を解釈するガードが働いたのか、単に許可の
問い合わせが否で確定したのかを判別できず、**ADR-0040 が記録した「Bash の deny は前方一致で回避できる」
という穴が塞がったとは言えない**（この穴は activeContext に未解決として残す）。

フックによる呼び出し元の識別可否は**測定できなかった**。フック設定の書き込みが権限機構側で拒否された
ためである（フックは任意コマンドを実行するので妥当な制限である）。回避は試みていない。

## 決定

### 1. `meta/tools/**` と `build.gradle*` の Edit/Write を deny する

`.claude/settings.json` の `permissions.deny` に次の4項目を加える。

```json
"Edit(./meta/tools/**)",
"Write(./meta/tools/**)",
"Edit(./**/build.gradle*)",
"Write(./**/build.gradle*)"
```

`Read` は deny しない。**読めなければ委譲先への事実の供給も、レビューもできない**（実測でも Read は
deny の対象外であることを確認済み）。

**適用範囲は現時点で摩擦が出た2つに限る**（P-05: 要るようになってから足す）。他スタックの同等物
（フロントエンドの `vitest.config.ts`・`package.json` の scripts 等）は**まだ含めない**——orchestrator が
そこを踏み抜いた実績が無いためである。踏み抜いたら足す。

### 2. `meta/permissions.md` の当該行を「ゲート変更は人間承認」に揃える

決定1により developer も止まる。これは副作用ではなく**規程の段差（文脈3）を正す本筋**である。
`meta/permissions.md` 16行目の「人間の関与」を、17行目（CIワークフロー）と同じ **「ゲート変更時は
人間承認」** に改める。

これは `meta/permissions.md` が定める**4つの人間承認ポイントを増やすものではない**。「信条・規程の
変更」という既存の承認ポイントの**対象範囲に、検証ツール本体が含まれることを明示する**変更である
（ゲートの変更＝何を正しいと判定するかの変更＝規程の変更）。

developer の役割は変わらない。**開錠後は従来どおり developer がテスト付きで実装する**——決定1は
「誰が書くか」を変えるものではなく、「**書き始める前に人間が一度ゲートを開ける**」段を1つ挟むだけで
ある。

### 3. 開錠は人間のコミット、施錠の確認は govlint（ERROR）

**開錠**: 検証ツールを変更する必要が生じたら、人間が `.claude/settings.json` から決定1の deny 項目を
外すコミットを打つ。開錠そのものが git 履歴に残り、PR の差分に現れる。

**施錠の確認**: `meta/tools/govlint.py` に検査を1つ加える。`.claude/settings.json` の
`permissions.deny` に決定1の4項目がすべて存在しなければ **ERROR**（終了コード1）とする。

これにより次が成り立つ。

- 開錠したままでは **L0 が赤になり、マージできない**（L0 は全PRで必ず起動する hard-required な共有
  ゲートである。`meta/guardrails.md` §2、ADR-0026 決定1.3 案i）
- 作業の流れは「人間が開錠 → developer が実装（この間 L0 は赤でよい。**未マージのコミットだから**）
  → 人間が施錠 → L0 が緑 → マージ」となる。**マージゲートが見るのは最終状態だけである**

**なぜ ERROR にしてよいか**（ADR-0035 決定2 が「意味判定を ERROR 化するな」と述べたのと対照的である
理由）: 「このADRは承認されるべきか」は意味判定だが、「**deny 項目が settings.json に存在するか**」は
文字列の有無であり、機械が確定できる（P-04: 機械が確定できるものだけ機械に確定させる）。開錠すべきか
どうかという判断は人間に残ったままであり、機械が引き受けたのは**閉め忘れの検出**だけである。

**この検査は developer が実装する**（テスト付き）。orchestrator は書かない——**本ADRが定める規律の
最初の適用対象が、本ADR自身の実装である**。

### 4. `.claude/settings.json` 自体は deny に含めない

含めれば orchestrator は自分でロックを外せなくなるが、**採らない**。理由は3つ。

- ADR-0040 のようなガードレール設計そのものが実行不能になる。権限設定は「AIが触ってはならない機密」
  ではなく、**AIが設計に参加すべき対象**である（ADR-0040 は実測込みでそれを行った）
- 鉄壁にはならない。`Bash` 経由で JSON を書き換える経路は残る（実測節のとおり Bash の穴は未解決）。
  **塞いだつもりになることの害の方が大きい**
- 決定3の govlint 検査が、実効的な歯止めになる。ロックを外すこと自体は可能でも、**外したままマージ
  することはできない**。「外せない」より「外したまま閉じられない」の方が、この文脈では強い

deny 項目を外す行為は git 差分に現れ、PR レビューで人間の目に触れる。**うっかりで起きる種類の行為
ではない**——FR-022 の失敗が「気づかずに手が出た」である以上、ここは守備範囲が違う。

### 5. 本ADRの限界を明示する（鉄壁ではない）

決定1〜4は、**手段を選ぶ相手を止められない**。`Bash` から `python -c` でファイルを書き換える経路は
残っており、`Bash` の deny は前方一致で回避できることが ADR-0040 で実測済みである。

止められるのは**「うっかり」だけ**である。そしてそれで足りる、というのが本ADRの費用対効果の判断で
ある——FR-022 の4回はいずれも、禁止を想起しないまま手が出たものであり、**拒否がその瞬間に返ること
自体が、必要な合図として機能する**。

**もう1つの限界: 決定1の deny が効くのは Claude Code だけである。** `.claude/settings.json` は
Claude Code の権限機構であり、Codex（`meta/agent-runtime-mapping.md`）はこれに拘束されない。
したがって2つの効果は**runtime によって届き方が違う**。

| | Claude | Codex |
|---|---|---|
| 決定1（手が出た瞬間に拒否が返る） | **効く** | **効かない** |
| 決定3（施錠が外れたままマージできない） | 効く | **効く**（L0 は共有の必須ゲートであり、runtime を問わない） |

FR-022 は Claude 側で起きた摩擦なので、当面はこれで対処できる。Codex 側で同種の摩擦が観測されたら、
Codex の権限機構に相当物を置くことを検討する（P-05: 要るようになってから）。**現時点で Codex 側に
同じ摩擦の実績は無い。**

この限界を明示するのは、`meta/PRINCIPLES.md` P-03（実行可能 > 機械検証可能 > 人間可読）の下段に
何が残っているかを読み手に見せておくためである。**塞いだ穴と塞いでいない穴を取り違えることが、
ガードレールの最大の失敗**である（ADR-0040 が `Write` の deny 漏れで実際に踏んだ）。

## 検討した代替案

- **案A: 当初案どおり orchestrator のツール権限からのみ deny する** / **不採用（機構が存在しない）**:
  実測により deny はサブエージェントに継承されることが確定した。パスベースの deny に呼び出し元を
  区別する能力は無い。
- **案B: PreToolUse フックで呼び出し元を識別して orchestrator だけを止める** / **不採用（測定不能・
  かつ筋が悪い）**: フックの入力に呼び出し元を識別できる情報が含まれるかを測定できなかった。仮に
  可能でも、**フックのスクリプトはロジックを持つ検証インフラであり、それ自体が developer の領分**に
  なる——本ADRが解こうとしている問題を1段深いところで再生産する。
- **案C: 止めずに、govlint の REPORT で毎回可視化する** / 不採用: 「見えれば止まる」という前提が、
  FR-022 の失敗の中身（気づかなかった）と噛み合わない。今回 orchestrator が違反に気づいたのは偶然の
  再読によるものであり、REPORT を出していても同じ結果になった可能性が高い。ただし**コストは最小**で
  あり、決定1が過剰と判明した場合の後退先として記録しておく。
- **案D: PRテンプレのチェック項目に「検証インフラを自分で書いていないか」を足す** / 不採用: 自己申告
  であり、`meta/guardrails.md` が checklist を正しい強制レベルとするのは**意味判定**の場合に限る
  （ADR-0034・0035）。「誰が書いたか」は意味判定ではなく事実であり、checklist は強制レベルとして弱い。
  4回破られた明文の禁止を、もう1箇所に書き写すだけになる。
- **案E（採用）: deny で施錠し、開錠は人間のコミット、施錠は govlint が ERROR で確認する** / 採用:
  想起に依存しない位置に禁止を置き（P-04）、正当な変更経路も閉ざさず（決定2）、閉め忘れという
  機械が確定できる部分だけを機械に渡す（決定3）。

## 帰結

- orchestrator が `meta/tools/**`・`build.gradle*` に手を出した瞬間、拒否が返る。cause_key
  `orchestrator-as-substantive-source` の5回目は、少なくともこの経路では起きない
- 検証ツールの変更に**人間の操作が1つ増える**。実績ベースで直近2週間に3回（ADR-0038・0043・0045）で
  あり、頻度としては軽くない。**過剰と分かれば案Cへ後退する**（本ADRを supersede する）
- `meta/permissions.md` の権限表から、L0〜L4 の階層と噛み合っていなかった段差が1つ消える
- **未解決のまま残るもの**: `Bash` の deny が前方一致で回避できる穴（ADR-0040 から継続）、govlint の
  cause_key 再出現検出が friction-log ファイル単位である穴。いずれも activeContext に記録を維持する
- FR-022 のステータスを「対応済み」に更新する。ただし**本ADRは再発の可能性を消してはいない**（決定5）

## 確認事項（人間に確認されたい）

**meta層のADRを orchestrator が起草してよいのか。** `.claude/agents/architect.md` は architect の職務を
「契約（受け入れシナリオ・API仕様・**ADR**）のドラフト作成」と定めており、文言上はメタADRの起草も
architect の領分と読める。しかし実運用では、メタADRは orchestrator（および Codex）が起草してきた
（0035・0038〜0043 等）。**本ADR自身も orchestrator が起草している。**

これが §6 の禁止（実質的成果物を自ら作らない）に触れるかは、本ADRでは決めない（P-02: 全体を先に
設計しない）。触れるとすれば FR-022 と同じ cause_key であり、**本ADRの deny は問題の一部しか塞いで
いない**ことになる。判断材料として記録するに留める。
