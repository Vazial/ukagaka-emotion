# ADR-0049: セッションログからfriction候補を収穫し、mainへのマージを収穫のトリガにする

> **承認者向けサマリ**
>
> 開発中に起きた引っかかりを friction と呼び、1件ずつ台帳（各プロジェクトの
> `friction-log.md`）に記録する運用になっている。書くのはその場で、が原則である。だが実際
> には書き損ねる。
>
> 手元に溜まっていた Claude Code のセッションログ（28セッション・149MB）を機械的に走査した
> ところ、すでに台帳に載っている摩擦のいくつかを、記録を見ずに見つけ直せた。既知を拾えると
> いうことは、書き損ねた分も同じ精度で拾えるということである。これが本ADRの根拠である。
>
> 決定は8点。
>
> 1. セッションログを、台帳に書き損ねた分の回収先として正式に位置づける
> 2. 走査は機械的なシグナルだけで行い、中身の意味は判定しない
> 3. 出力は候補であって台帳の1件（FR）ではない。台帳に書くのは人間のGOのあと
> 4. トリガはPRのマージ。閾値に届かなければ何も出さない（軽い修正はここで黙って落ちる）
> 8. 走査の前に**正規化の層を1枚挟む**。生のログは3つの癖を持っていて、そのまま数えると
>    必ず間違える——フォークで2割が重複し、役割agentの記録は別ファイルに分かれ、
>    `role: user` は人間の発話とは限らない。畳むのは1箇所でよい
> 5. 置き場は `meta/loop/`。この道具は合否を判定しないので、検証ツールの施錠（ADR-0046）の
>    対象ではない
> 6. どこまで走査したかの記録は各自の環境の事情なので、gitに入れない
> 7. 効果の測定は悪化の検知に限る。人間が打ち直す割合は現状3.8%だが、この流量では改善は
>    測れない
>
> 払うもの: 誤検出を人間が読み飛ばすコスト。
> 効かない範囲: 見るのは Claude Code のログだけなので、Codex のセッションには届かない。

## 文脈

### 0. このADRを起草したのは誰か

指揮役（orchestrator）が起草した。テンプレート自身の運用を決めるADR（メタADR）は、素材が
「摩擦の観測」であればorchestratorが書く、という目安をADR-0047が置いている。本ADRの素材は
溜まったセッションログそのもので、走査も評価もorchestratorが手を動かした。設計役
（architect）は関与していない。

### 1. 「その場で書く」は正しい。だが記録は落ちる

摩擦はその場で書く、というのが今の運用である。あとでまとめて棚卸しすると記憶が薄れて精度が
落ちるからで、この前提自体は正しい。ただしそこから「その場で書かなかった分は永久に失われて
よい」までは意図していない。

記録が落ちた例はすでにいくつも残っている。指揮役が実装役の領分に手を出す失敗（同じ原因を
束ねるキーで `orchestrator-as-substantive-source` と呼んでいるもの）は実質4回起きているが、
機械はファイル単位でしか数えられていない。予約システムのスライスRSV-Lで監査が抜けたまま
進んだ件は、監査役（reviewer）が独立に同じ問題を見つけ直すまで誰も気づかなかった。記録は
落ちる、というのは推測ではなく実績である。

### 2. 落ちた記録は、実は手元に残っている

Claude Code はセッションを1本ずつ生ログとして残している（`~/.claude/projects/<slug>/*.jsonl`。
1行1レコードのJSON）。このリポジトリの分だけで28セッション・149MB（2026-07-13〜08-22）が
溜まっていた。人間の発話、AIの応答、ツールの呼び出しと結果、ブランチ名、時刻がすべて入って
いる。

一次データは捨てられていない。回収していないだけである。

### 3. 走査して分かったこと

実際に走査を実装し、28セッションに当てた。

拾えたシグナルは次の5つで、いずれも中身を読まずに判定できるものだけである。

| シグナル | なぜ摩擦の印になるか |
|---|---|
| 人間が打ち直した否定・訂正 | 人間が手で止めた＝AIが外れた証拠。最も強い |
| AI自身の自己訂正 | 直前に何かを誤っている |
| ツール実行の拒否・割り込み | 同上。より明示的 |
| 同一エラーの連発（4回以上） | 詰まっていた |
| 同一ファイルへの書き込みの往復（8回以上） | 迷っていた |

**精度を壊すもの**は、人間が打っていない発話の混入だった。ログ上 `role: user` として記録
されるレコードには、サブエージェントの完了通知のように人間がタイプしていないものが大量に
混ざる。実測でその手の通知が231件、人間の発話が522件である。これを外さずに走らせた最初の
実装では、候補の中身がほぼ全部その通知になった。`promptSource` というフィールドは通知にも
付くので判別に使えない（実測）。先頭の形（`<`・`[Image:`・`Caveat:`・引き継ぎサマリ）と長さで
落とす必要がある。

**スコアの分布には段差が出た**。これが「軽い修正を落とす」判断の根拠である。

```
29, 25, 22, 19, 15, 15, 13, 8   ← 摩擦のあったスライス（8本。閾値8以上）
--------------------------------  ← 段差
 5, 5, 5, 4, 3, 3, 2, 2, 2, 0×11  ← 軽量・雑務のセッション（20本）
```

スコアはセッションの長さでは決まっていない。345ターンあってスコア0のセッションがある。
シグナルが何回立ったかで決まる。

**すでに台帳に載っている摩擦を、記録を見ずに拾い直せた**。外部AIへのデザインブリーフが
狭すぎて弱い成果物が返った件（FR-002）の議論、機密ガードレールの穴だった `.env.example` の
扱いを決めた議論（のちのADR-0040）、検証ツールの施錠（ADR-0046）で権限が拒否され `denied`
が連発した箇所。いずれも走査だけで浮かんだ。

## 決定

### 決定1. セッションログを、台帳に書き損ねた分の回収先として位置づける

その場で書く、は引き続き第一の手段であり、本ADRはそれを緩めない。収穫はあくまで、書き
損ねた分を拾い直すための第二の手段である。

### 決定2. 走査は機械的なシグナルだけで行い、中身の意味は判定しない

スコアが表すのは「人間が読む価値がありそうか」であって、摩擦の重さではない。判別の要は
人間がタイプした発話とそれ以外を切り分けるところにあり、ここを外すと候補は無意味になる
（文脈3の実測）。この切り分けロジックには単体テストを付ける
（`meta/loop/test_harvest_friction.py`）。

### 決定3. 出力は候補であって、台帳の1件ではない

収穫がするのは「読み返すべき瞬間」を並べることまでで、台帳への追記は人間のGOのあとに行う。

権限規程（`meta/permissions.md`）は台帳をAIが自律更新してよい対象にしている。しかし機械が
拾った候補を機械がそのまま起票すると、誤検出が台帳に居座る。同じ原因を束ねるキーを使い
回してよいかの判断（ADR-0012が定めた仕組み）にも人間の目が要る。自律更新の対象は「AIが
自分で気づいて書く」場合に留める。

### 決定4. トリガはPRのマージ（PostToolUse hook）とする

スライスがmainへ入る瞬間が、振り返りの自然な区切りである。走査するのは前回の収穫以降の
分だけとし、スコアが閾値（既定8）に届かなければ何も出さない。軽い修正はここで黙って落ち、
収穫は摩擦のあったスライスにだけ反応する。

ただし hook 側の起動条件（マージコマンドへの前方一致）だけに頼ってはいけない。実測で、
バッククォートで囲まれた文字列がコマンド置換として解析され、起動条件に一致することが
分かった。クォート付きの heredoc の中でも同じで、本ADRのコミットメッセージにマージコマンドを
書いただけで hook が発火した。誤発火そのものは無害だが、収穫位置だけが黙って進み、未収穫の
蓄積を食ってしまう。したがって呼ばれた側でコマンド文字列を検査し直し、一致しなければ収穫
位置も進めない。

### 決定5. 置き場は `meta/loop/` とする

ADR-0046が施錠したのは「何を正しいと判定するか」を決めている道具、つまりゲートである。
収穫ツールは何も失敗させず、何も判定しない。したがってゲートではなく、施錠の対象でもない。
この区別を本ADRで明文化する。

`meta/tools/` に置くと、権限設定にある `Write(./meta/tools/**)` の拒否によって、閾値を
少し動かすたびに人間の開錠が要る。拒否は許可で上書きできず、除外の書き方も無い（ADR-0040と
ADR-0046で実測済み）。何も判定しない道具にその手続を課す理由がない。

### 決定6. 収穫位置の記録（`.claude/harvest-state.json`）はgitに入れない

どこまで走査したかは各自の環境に属する事実で、共有しても意味を持たない。「今」を持つのは
1箇所だけ、という信条（P-11）と同じ形である。

### 決定7. 効果の測定は悪化の検知に限り、「ループが効いた」の証明には使わない

人間が打ち直した訂正の割合（訂正プロンプト ÷ 人間のプロンプト総数）を
`meta/loop/friction_trend.py` で測る。実測のベースラインは3.8%（訂正17件／450件、
2026-07-13〜08-22）で、およそ26回に1回は人間が打ち直している計算になる。

**この指標で改善は証明できない。** 理由は2つあり、どちらも運用では消えない。

1. 交絡が畳めない。モデルが変わる、タスクの性質が変わる（初期は規程が無いので摩擦が多くて
   当然である）、人間の指示も上手くなる。摩擦率が下がってもループの寄与を切り出せない
2. 流量が足りない。週あたり約75プロンプトしかない。両側5%・検出力80%で、半減の検出には
   片側1,207件（約7.5か月）、3割減なら片側3,789件（約23か月）を要する。一方で2倍の悪化は
   片側585件（約3.6か月）、3倍なら片側190件（約1.2か月）で捉えられる

つまり改善は現実的な期間では測れず、大きな悪化だけが測れる。週次の折れ線は読んではいけない
（週あたりの訂正は1〜5件で、上下はただのノイズである）。ツールは判定に足る件数が貯まるまで
「まだ判定できない」と言い、あと何件要るかを示す。測れないことを測れると言わない、という
のがこの決定の本体である。

測定にあたっては、レコードの `uuid` による重複排除が必須である。セッションはフォークや再開で
分岐し、同じレコードが複数ファイルに入る（実測で全レコードの21.7%）。潰さずに率を出すと、
分岐の多かった週だけ分母が膨らみ、実在しないトレンドが出る。

### 決定8. 走査の前に正規化の層を1枚挟む

生のログは3つの癖を持っている。どれも実測で確かめたもので、畳まずに数えると必ず間違える。

**フォークで重複する。** セッションを分岐すると、親の全レコードをコピーした新しいファイルが
作られる。全レコードの21.7%が重複していた。各レコードの `sessionId` が本来の出自を保持して
いるので、そちらを正とすれば畳める。

**役割agentの記録は別ファイルにある。** メインのトランスクリプトに `isSidechain` は1件も
入っていない。実体は `<session>/subagents/agent-*.jsonl` で、`.meta.json` の `toolUseId` が
親セッションの `Agent` 呼び出しと対応する（108件すべてが一致した）。**分量はメインとほぼ
同じ**——実測でメイン82.2MB に対し役割agent側が77.8MB、108実行（architect 46 / developer 34 /
tester 18 / reviewer 9 / designer 1）ある。委譲を中心に回すこのリポジトリで、ここを見ないのは
半分を捨てるのに等しい。

**`role: user` は人間の発話とは限らない。** メインでは task-notification や slash の展開が
同居する。役割agentのログではさらに違って、そこでの `role: user` は orchestrator が渡した
ブリーフと途中連絡であり、人間は登場しない。ここを取り違えると、**agentへの指示が「人間の
訂正」として数えられる**——実際に一度そうなった。

この3つを `meta/loop/index_sessions.py` が一度だけ畳み、SQLite に落とす。分析側は畳み終わった
ものだけを読む。正規化の層は**判定をしない**——摩擦かどうかも良し悪しも決めず、形を揃える
だけである。決定2（機械的なシグナルだけで判定しない）はその上に載る。

出力先は作業ツリーの**外**（`~/.claude/session-index/`）に置く。DBはログ本文をそのまま含み、
閲覧したページ由来のメールアドレス（実測461件）やローカル開発用の資格情報が写り込む。
リポジトリ内に置くと `.gitignore` がブランチごとの版に依存するため、別ブランチを
チェックアウトしている作業ツリーでは untracked として現れてしまう（実際にそうなった）。


## 帰結

- **得るもの**: 書き損ねた摩擦が失われなくなる。テンプレート改善の一次データの回収率が
  上がる。同じ原因が2回目に出たことを機械が知らせる仕組み（ADR-0012）が、実データで
  裏打ちされる。正規化の層が入ったことで、**役割agentの層が初めて分析の対象になる**——
  見られるイベントが17,728件から35,479件へ倍増した
- **役割agentの層から、これまで見えなかった摩擦が出た**: 収穫を正規化インデックスの上へ
  載せ替えたところ、architect が「作業ディレクトリが違う」というエラーで23回続けて詰まって
  いた実行や、orchestrator が tester に「**前回の私の指示が間違っていました**」と差し戻して
  いた実行が候補に上がった。どちらもメインのトランスクリプトだけを見ていたときは拾えて
  いない。後者は orchestrator 自身の誤りの記録であり、台帳が繰り返し指している
  `orchestrator-as-substantive-source` と同じ場所を指している
- **途中連絡は狭く取る**: orchestrator が実行中のagentへ送る連絡は43件あるが、その多くは
  正常な調整である（人間の判断の伝達、前セッションからの再開、reviewerの差し戻しという
  設計どおりの流れ）。全部を摩擦として数えると候補が意味を失うので、ゲートやテストが落ちた
  ことを告げているものだけを拾う
- **払うもの**: 誤検出を人間が読み飛ばすコスト。閾値は実測の段差から8としたが、運用で
  調整する。調整は施錠の外なのでAIが実施できる（決定5）
- **効かない範囲**: hook は Claude Code の機構なので、Codex には届かない。Codexのセッションは
  別の形でログを残すため、本ADRの収穫はClaudeのセッションに限る。runtime をまたいで効かせたい
  規律は権限設定や hook ではなく govlint（統治文書の機械チェッカ）に置く、という既存の原則は
  変わらない
- **やらないこと**: 生ログの削除・圧縮・ローテーション。溜まっていること自体は問題ではなく、
  回収していないことが問題だった（摩擦が起きてから足す、というP-05の順序である）
