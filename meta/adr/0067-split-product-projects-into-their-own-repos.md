# ADR-0067: 製品として運用に入ったプロジェクトは、自分のリポジトリへ切り出す

> **承認者向けサマリ**
>
> dining-radar は公開運用中の製品になり、テンプレのリポジトリの中で一番大きく、一番よく動く
> プロジェクトになった。テンプレの履歴とPRが製品の作業で埋まっている。人間が「分けてもいいかも」
> と提案し、チャットで方向を合意した。
>
> 決定は5点。
>
> 1. 製品として運用に入ったプロジェクトは、独立したリポジトリへ切り出してよい。最初は dining-radar
> 2. 切り出した先も、テンプレと同じ配置（`meta/`・`.claude/`・`projects/<p>/`）を保つ
> 3. 共有ファイルは写しを置き、どのテンプレのコミットから写したかを `TEMPLATE_SYNC` に記録する
> 4. テンプレからの取り込みは差分を当てるPRで行い、テンプレへ戻すときはテンプレ側のPRで行う
> 5. 履歴ごと切り出し、テンプレ側には行き先へのポインタだけを残す
>
> 払うもの: 規程の更新が即時には届かなくなり、取り込みの手間が1回ずつ要る。

## 文脈

### 1. 何が起きたか

dining-radar は 2026-07-29 に始まり、2026-08-14 から公開運用している。`main` へのマージが
CI 通過後に Render へ自動デプロイされる。2026-09-26 時点で `projects/` の中の容量は
dining-radar が 6.6MB、残り3つが合計約 2.6MB である。dining-radar のパスに触れたコミットは
331件ある。

テンプレ（このリポジトリ）の本来の仕事は、A層（`meta/`。言語に依らない規程と道具）を育てる
ことである。いまは製品の作業がそれを上回り、テンプレとしての変化が履歴とPR一覧の中で見えにくい。

2026-09-26、人間が「テンプレのリポジトリに入れちゃってるのでわけてもいいかも」と提案した。
続けて、写しを置きつつ「適宜テンプレに反映したりテンプレから取り込んだりできるといい」と
方向を示した。

### 2. いまの結びつき

切り出すとき手当てが要るのは次の箇所である。

- **デプロイ**: Render はこのリポジトリの `main` を見ており、`rootDir: projects/dining-radar` を持つ
- **CI**: `ci-dining-radar.yml` はパス `projects/dining-radar/**` で起動する。L0 の `govlint.yml` は
  `projects/*/adr` や `projects/*/contracts` を走査する
- **役割と規程**: `.claude/agents/`・`meta/`・`HANDOFF.md`・`CLAUDE.md`・`AGENTS.md` を共有している
- **状態**: ルートの `activeContext.md`（テンプレ全体とプロジェクト跨りの現在）が dining-radar の
  行を持つ（2階層の activeContext を定めた ADR-0033）

## 決定

### 決定1. 製品として運用に入ったプロジェクトは、独立したリポジトリへ切り出してよい

切り出すかどうかは人間が決める。目安は、公開運用に入ったこと、またはテンプレの履歴を主に
占めるようになったことである。最初の対象は dining-radar で、行き先は公開リポジトリ
`Vazial/dining-radar` とする。公開のままにするのは人間の裁定である（2026-09-26 チャット）。

### 決定2. 切り出した先も、テンプレと同じ配置を保つ

切り出した先のリポジトリは、テンプレから他のプロジェクトを除いた形にする。

```
meta/                  … テンプレの写し
.claude/agents/ など    … テンプレの写し
HANDOFF.md ほか         … テンプレの写し
activeContext.md       … 切り出した先のルート（そのリポジトリ全体の現在）
projects/dining-radar/ … 本体。パスは変えない
```

パスを変えなければ、ADR・契約・activeContext の中のパス参照はそのまま生きる。govlint・CI・
Render の `rootDir` も書き換えずに済む。これはテンプレから新しいプロジェクトを始めるときの形と
同じであり、その形が実際に回るかの検証にもなる。

### 決定3. 共有ファイルは写しを置き、写した元を `TEMPLATE_SYNC` に記録する

切り出した先のルートに `TEMPLATE_SYNC` を置く。持つのは次の3つである。

- 写した元のテンプレのコミット SHA
- 同期の対象になるパスの一覧（`meta/`・`.claude/agents/`・`.claude/skills/`・`.githooks/`・
  `guardrails/`・`.github/workflows/govlint.yml`・`.github/workflows/adr-number.yml`・
  `.github/pull_request_template.md`・`HANDOFF.md`・`CLAUDE.md`・`AGENTS.md`）
- 対象ファイルそれぞれの内容ハッシュ

ハッシュを持つのは、写しを直接いじったことをネットワーク無しで検出するためである。govlint は
ワーキングツリーの実ファイルしか見ない（ADR採番の衝突検査を govlint の外に置いた ADR-0052 の
前提）。手元のファイルと記録したハッシュを比べるだけなら、この性格を崩さずに済む。

### 決定4. 取り込みは差分を当てるPR、戻すのはテンプレ側のPRで行う

**テンプレから取り込む**: 切り出した先にテンプレを `template` という名前の git remote として
登録する。`TEMPLATE_SYNC` の SHA からテンプレの `main` までの、対象パスの差分を取り、
`git apply -3` で当てる。これをPRにし、同じPRで `TEMPLATE_SYNC` を更新する。手順は
スクリプト（`scripts/template-pull.sh`）にして、切り出した先に置く。

**テンプレへ戻す**: dining-radar で規程を直したくなったら、テンプレに `meta/**` の PR を出す
（`meta/**` の変更を1本ずつ通す直列化を定めた ADR-0026 決定4 のとおり）。マージされたら、
上の取り込みで切り出した先へ戻ってくる。

**写しは原則として直接いじらない。** 急ぎで直接直した場合は、ハッシュの不一致を govlint が
警告する。その警告は、テンプレへ戻す PR が取り込まれるまで残る。プロジェクト固有の決定は、
これまでどおり `projects/<p>/adr/` に置く。

### 決定5. 履歴ごと切り出し、テンプレ側には行き先へのポインタだけを残す

`git filter-repo` で、`projects/dining-radar/` と `ci-dining-radar.yml` の履歴を残したまま
切り出す。その上に、共有ファイルの写しと `TEMPLATE_SYNC` を1コミットで載せる。

テンプレ側では、`projects/dining-radar/` と `ci-dining-radar.yml` を消す。ルートの
`activeContext.md` のプロジェクト一覧には、行き先のリポジトリへのポインタを1行だけ残す。
シナリオIDの接頭辞の台帳（`meta/scenario-id-prefixes.md`）の `TDR` の行は消さず、切り出したことを
書き足す。過去のメタADRや friction-log の中の dining-radar への言及は、P-06（記録を書き換えない）に
従ってそのまま残す。

## 検討した代替案

- 案A: テンプレの中に置いたままにする / 不採用の理由: テンプレの履歴とPRが製品の作業に
  埋もれ続ける。テンプレから始める流れも、いつまでも試されない
- 案B: submodule でテンプレを参照する / 不採用の理由: 取り込みは速いが、CI の checkout・パス・
  `.claude/agents` の置き場がすべて複雑になる。プロジェクト側で先に試す、という余地も無くなる
- 案C: GitHub のテンプレ機能で新しいリポジトリを作り、そこへ移す / 不採用の理由: 製品の履歴が
  切れる。テンプレとの同期の手段も別に要り、結局は決定3・4と同じものを作ることになる
- 案D: 切り出した先で配置を平らにする（`projects/dining-radar/` をルートへ上げる） /
  不採用の理由: パス参照・govlint・CI・Render をすべて書き換えることになる。得るものは見た目だけ

## 帰結

- **良い影響**: テンプレの履歴とPRがA層の仕事に戻る。テンプレから始める流れを、実際の製品で
  初めて通す
- **払うもの**: 規程の更新が即時には届かない。取り込みの PR が1回ずつ要る。写しと元がずれる
  期間ができる（ハッシュ検査で見える状態に保つ）
- **コミット SHA が変わる**: 切り出した先では過去コミットの SHA が変わる。dining-radar の
  activeContext や ADR にある SHA（例: 圧縮前の全文を指す `094f323`）は、テンプレのリポジトリの
  SHA として読む。この読み方は、切り出した先の activeContext に1行書いておく
- **人間の作業**: Render のサービスを新しいリポジトリへつなぎ替える（ダッシュボード）。
  切り出した先のブランチ保護を確認する
- **波及する作業**（この ADR の承認後、順に行う）:
  1. 切り出した先のリポジトリを作り、履歴ごと切り出す
  2. 共有ファイルの写し・`TEMPLATE_SYNC`・`scripts/template-pull.sh` を載せる
  3. govlint にハッシュの検査を足す（テンプレ側では `TEMPLATE_SYNC` が無ければ何もしない）
  4. CI を緑にし、Render をつなぎ替え、本番の `/healthz` を確かめる
  5. テンプレ側から dining-radar を消し、ポインタを残す
