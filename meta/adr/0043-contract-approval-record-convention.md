# ADR-0043: 契約の承認記録もPR1本で閉じ、承認待ちの契約を機械が棚卸しする

> **承認者向けサマリ**: ADR-0035 が**ADRについて**直した「承認記録のドリフト」が、**契約（`.feature`）
> では直っていなかった**。契約のステータスは行コメントで持つため**機械検証の対象外**であり、
> `my-reservations.feature`（RFE-C）は **PR #49 で人間が承認したのにファイルは「承認待ち」のまま**
> だった。機構はFR-015と同一——起草時は「承認待ち」と書くしかなく、承認行為はPRのマージで、記録には
> 2本目のPRが要るため飛ばされる。さらに調査で**より重い事実**が出た: **RFE-A・RFE-B は契約が一度も
> 承認されていないのに実装が本番コードとして載っている**。RFE-B は契約と実装が同一コミット
> （`f1dac2a`、ラベルは断面②）で、ADR-0022 が定めた「断面①（契約承認）→断面②（実装）」の順序を
> 通っていない。**フロントで契約承認点が実際に機能したのは RFE-C が初めて**である。決定は3点——
>
> **（2026-08-01・訂正。meta/adr/0045）** 上記の「RFE-B が順序を通っていない」という記述は**帰責が
> 不正確だった**。契約だけを先に load することは**当時、機械的に不可能**であり（シナリオIDが L0 の
> 参照整合と L4 の実装網羅を結合していた。FR-014）、RFE-B は FR-014 が処方した運用回避
> 「受け入れシナリオは実装スライスと必ず同じ粒度で land させる」に**従った結果**である。規律の問題では
> なく構造の問題だった。ADR-0045 がこの構造を直したため、以後は断面①が実際に実行できる。
> **契約もADRと同じ承認方式の二択を起草時に選ぶ**／**govlint が契約のステータス行を機械検証し、
> 承認待ちを棚卸しREPORTに出す**（形式不正はERROR、承認すべきかの判断はREPORT）／**RFE-C の記録漏れを
> 是正する**（RFE-A・RFE-B は実際に未承認なので「承認待ち」のまま残し、REPORTで可視化し続ける）。

## 文脈

### 1. 発覚の経緯

RSV-T（会議室の登録）の契約ドラフトを検証する過程で、リポジトリ全体の契約のステータス行を確認した。

| 契約 | ステータス行 | 実態 |
|---|---|---|
| reservation-system 5本（RSV-C/K/A/R/L） | `承認済み(日付)` | 一致 |
| `my-reservations.feature`（RFE-C） | **`承認待ち`** | **PR #49 で承認済み**（ドリフト） |
| `reservation-booking.feature`（RFE-B） | `承認待ち` | 実装・マージ済み |
| `availability-view.feature`（RFE-A） | `承認待ち` | 実装・マージ済み |

### 2. 機構はFR-015と同一

契約は**承認される前に**起草されるので、起草時に書けるのは「承認待ち」だけである。一方、承認行為の
実体は**人間がPRをマージすること**であり、承認の事実をファイルに書き込むには**マージ後に2本目のPR**が
要る。その差分は行コメント1行だけで単独の価値が見えないため、飛ばされる。

**ADR-0035 はこの機構をADRについて直したが、契約には適用していなかった。** 加えて、ADRのステータスは
frontmatter にあり govlint が機械検証するのに対し、**契約のステータスは行コメントで機械検証の対象外**
だったため、ドリフトしても誰も気づけなかった。

reservation-system の5本に日付が入っているのは、当時2本目のコミットを打っていたからである（規律で
維持していたものが、続かなくなった）。これは「規律の呼びかけでは直らない」というFR-015の結論の再確認
でもある。

### 3. より重い事実——未承認の契約の上に実装が載っている

RFE-A・RFE-B の履歴を追ったところ、**どちらも契約承認点を通っていない**ことが分かった。

- **RFE-A**（`availability-view.feature`）: `0314645 docs(reservation-frontend): 設計判断・契約・
  designerフローの設計記録` で導入。**契約の承認PRではなく設計記録のdocsコミット**
- **RFE-B**（`reservation-booking.feature`）: `f1dac2a feat(reservation-frontend): RFE-B 予約するスライス
  を実装（シナリオ＋実装・断面②）` で導入。**契約と実装が同一コミット**であり、ラベル自体が断面②である

`meta/adr/0022` は断面①（契約の形に人間が合意）→断面②（動く実装に人間が合意）の順序を定めているが、
RFE-B はこれを通らず、契約と実装が一度に入った。`projects/reservation-frontend/activeContext.md` の
「未解決の論点」には**「RFE-A契約の人間承認」がずっと残ったまま**だった——記録はされていたが、
実装が進むことを止めなかった。

すなわち **`meta/permissions.md` の4承認点のうち「契約」が、フロントでは RFE-C まで実質的に機能して
いなかった**。

## 決定

### 1. 契約も承認方式を起草時に二択で選ぶ（ADR-0035と同じ形）

契約（`.feature`）のステータス行は次のいずれかとする。

**(i) マージ＝承認（既定）**

```
# ステータス: 承認済み(YYYY-MM-DD) — <このPRのマージをもって承認された旨>
```

起草時からこう書き、人間は**マージしないことで拒否する**。1本のPRで閉じるため記録が遅れる余地が無い。

**(ii) 記録のみ・承認は後日**

```
# ステータス: 承認待ち — <保留する理由>
```

「判断材料は残すが決定はまだしない」と**意図して選ぶ場合に限る**。

### 2. govlint が契約のステータス行を機械検証する

- **ERROR**: ステータス行が無い／形式が不正（`承認済み(YYYY-MM-DD)` でも `承認待ち` でもない。
  「承認済み」だけで日付が無いものを含む）。**「この契約が拘束力を持つのか」を読み手が判別できない
  状態**であり、機械が確定できるためERRORが正しい強制レベル（P-04）
- **REPORT**: 承認待ちの契約の一覧。**「承認すべきか」は意味判定なのでERROR化しない**——ADR-0035 が
  提案中ADRの棚卸しをREPORTに留めたのと同じ設計判断である

REPORTの文面には「**この契約の上に実装が載っていないかも確認すること**」を含める。RFE-A・RFE-B で
実際に起きた失敗を、次に見る人が見落とさないようにするためである。

### 3. RFE-C の記録漏れを是正し、RFE-A・RFE-B は「承認待ち」のまま残す

- **RFE-C**（`my-reservations.feature`）: PR #49 で人間が承認した事実を記録する（`承認済み(2026-07-30)`）
- **RFE-A・RFE-B**: **実際に未承認なので「承認待ち」のまま残す**。決定2のREPORTに出続けるため、
  可視化された状態で人間が判断できる。**本ADRで遡って承認したことにはしない**——読まずに承認するのと
  同じであり、ADR-0035 決定3（既存の提案中ADRを一括承認しない）と同じ理由である

### 4. 適用範囲

以後に起草する契約に適用する。既存の是正は決定3の範囲に限る。

## 検討した代替案

- **案A: 契約のステータスもfrontmatter化してADRと同じ機構に載せる** / 不採用（当面）: `.feature` は
  Gherkin であり、frontmatter を足すと構文の外側に別の様式を持ち込むことになる。既存9本すべての
  書き換えも要る。**行コメントのまま機械検証すれば同じ効果が得られる**（決定2）ため、移行コストを
  払う理由がない。
- **案B: 承認待ちの契約をERRORにする** / 不採用: 正当な保留（起草直後、人間の承認待ち）が常にCIを
  赤にする。ADR-0035 決定2 が提案中ADRについて述べたのと同じ誤り——回避のために内容を伴わない承認を
  誘発する。
- **案C: RFE-A・RFE-B を本ADRで遡って承認済みにする** / 不採用: 実装が既に載っているという既成事実を
  根拠に契約を承認するのは、承認点の意味を失わせる。**未承認のまま実装が載っている状態を可視化し続ける
  方が正直**であり、人間が個別に判断すべき。
- **案D（採用）: 二択の明示＋機械検証＋RFE-Cのみ是正** / 採用: ADR-0035 で確立した形をそのまま契約に
  適用でき、既存の書式を壊さず、未承認の実態を隠さない。

## 帰結

- 以後の契約は原則1本のPRで承認まで閉じる。ステータス行の記録漏れは構造的に起きなくなる。
- **`RFE-A`・`RFE-B` が承認待ちのまま実装が載っている事実が、毎回のCIに見える**。人間がいつ判断しても
  よいが、忘れることはなくなる。
- 契約の形式不正がERRORで止まる。**新規契約は必ずステータス行を持つ**ことが機械で保証される。
- 併せて friction-log に FR-021 を起票する。cause_key は **FR-015 と同じ `record-update-needs-second-pr`
  を再利用する**——ADRと契約で対象は違うが、機構は完全に同一（起草時に書けない→承認はマージ→記録に
  2本目のPRが要る→飛ばされる）であり、**同一キーの2回目としてgovlintが構造的欠陥のシグナルを出すこと
  自体に意味がある**。
- **未対応として残す**: `meta/adr/0022` が定めた断面①→断面②の順序を、**何が強制しているのか**。
  RFE-B は契約と実装を同一コミットで入れたが、それを止める機械的な仕組みは無い（PRテンプレの
  チェック項目はあるが、自己申告である）。本ADRは「承認されたかどうかを可視化する」ところまでで、
  「未承認の契約に対する実装を止める」ところまでは踏み込んでいない。同じ形が再発したら、そこを
  構造で直す判断に進む。
