# ADR-0047: メタADR（`meta/adr/`）の起草はorchestratorの領分とする。architectが起草するのはプロジェクトscopeのADRである

> **承認者向けサマリ**: ADR-0046 の確認事項——「`.claude/agents/architect.md` が『契約（受け入れ
> シナリオ・API仕様・**ADR**）のドラフト作成』を architect の職務としているのに、メタADRは実際には
> orchestrator と Codex が起草してきた。これは §6 が禁じる『実質的成果物を自ら作らない』に触れるのか」
> ——に対し、人間が **「ADRはorchestratorでいい」** と裁定した（2026-08-03）。本ADRはこの裁定を記録し、
> **なぜそれが FR-022（orchestratorがgovlintを自分で書いた違反）と矛盾しないか**を明示する。決定は3点。
> **(1)** `meta/adr/` のADRはorchestrator（およびCodex）が起草してよい。architect の職務記述にある
> 「ADR」は**プロジェクトscopeのADR（`projects/<p>/adr/`）を指す**と読む。`.claude/agents/architect.md`
> の文言をその意味に明確化する。**(2)** ただし orchestrator が起草してよいのは、**方法論・運用・
> ガバナンスについてのメタADR**に限る。プロジェクトの契約・設計骨格の中身を決めるADRは、`scope` が
> `meta` であっても architect の領分である。**(3)** FR-022 との違いは「**自己採点かどうか**」である
> ——検証ツール（govlint）を自分で書くことは自分の仕事を判定する機械を自分で作ることだが、ADRの起草は
> **人間の承認点で必ず止まる**。orchestratorは判断材料を提出するだけで、決定はしていない。

## 文脈

### 1. 何が問われたか

ADR-0046（検証ツールの施錠）を起草する過程で、orchestrator 自身が次の疑いを立て、確認事項として
記録した。

- `.claude/agents/architect.md` の `description` は「契約（受け入れシナリオ・API仕様・**ADR**）の
  ドラフト作成」を architect の職務としている
- 一方 `meta/agents.md` §6 は orchestrator に「**実質的成果物を自ら作らない**」を課している
- 実際には、メタADRは orchestrator と Codex が起草してきた（0035・0038〜0043・0045・0046、
  Codexは0036・0037・0044）。**ADR-0046 自身も orchestrator が起草している**
- 文言どおりに読むなら、これは FR-022 と同じ cause_key（`orchestrator-as-substantive-source`）の
  5例目以降ということになり、ADR-0046 の deny は**問題の一部しか塞いでいない**ことになる

人間の裁定は「**ADRはorchestratorでいい**」であった。本ADRはこの裁定を記録するとともに、**裁定が
恣意的ではないこと**——FR-022 で禁じた行為とは性質が違うこと——を明文化する。裁定の記録だけを残すと、
将来の読み手には「4回破られた禁止を、5回目で規程の側が折れた」ようにしか見えないためである。

### 2. なぜ性質が違うのか（自己採点かどうか）

FR-022 が問題にしたのは「orchestrator が **govlint と build.gradle を自分で書いた**」ことである。
これらは**正しさを判定する機械**であり、orchestrator の成果物もその判定を受ける。自分で書けば
**自己採点**になる。誰の承認も経ずに機械が変わり、その機械が自分を通す。

ADRの起草はこれと構造が違う。**ADRは `meta/permissions.md` の4つの人間承認ポイントの1つ（信条・
規程の変更）に載っており、承認されなければ効力を持たない**。orchestrator が書くのは**判断材料**で
あって決定ではない。ADR-0035 が方式(i)（マージ＝承認）を定めて以降、この性質はいっそう明確になって
いる——**人間はマージしないことで拒否できる**。

| | 検証ツール（govlint・build.gradle） | メタADR |
|---|---|---|
| 効力の発生 | **コミットした瞬間**（次のCIから判定が変わる） | **人間がマージした瞬間** |
| 人間の承認点 | 無かった（ADR-0046 で追加した） | 最初からある（4承認点の1つ） |
| orchestratorが書くと | **自己採点**になる | 判断材料の提出にとどまる |

### 3. さらに、メタADRをarchitectに書かせる方が §6 に反する

これが本ADRの実質的な根拠である。

メタADRの素材は**摩擦の観測**である——「どの規程が破られたか」「どの検証が抜けていたか」「どの
役割が何を知り得なかったか」。これらを観測できる位置にいるのは orchestrator だけである。architect は
プロジェクトの契約しか読まず、役割のディスパッチもCIの結果も見ない。

したがってメタADRを architect に起草させると、orchestrator は**観測した事実・原因の仮説・設計の
選択肢をディスパッチ・プロンプトに書いて渡す**ことになる。これは `meta/agents.md` §6 が名指しで
禁じている行為そのものである。

> **書いてはならない**: ドメインルール・設計制約・解釈・答えといった実質的内容。これらをプロンプトに
> 注入すると、(a)非ルーチン・非バージョン管理になり（P-04）、(b)orchestratorが劣化・バイアスの点に
> なり（FR-006と同型）、(c)agentの独立導出を短絡させる。

**メタADRをarchitectに委譲することは、委譲の見た目をとりながら、実際には FR-008 とまったく同じ機構
（orchestratorが実質的内容の源になりつつ、成果物には別のagentの名前がつく）を作る。** これは委譲では
なく、責任の所在をぼかすだけである。§6 自身が「注入したくなったら、それは成文ソースの不足のサイン」
と述べているが、メタADRの場合は**不足しているのではなく、そもそも観測点が orchestrator にしかない**。

### 4. architectの独立性が何のためにあるか

architect が実装コードを読まず、人間の意図の聞き取りから契約を起草するのは、**契約が受け入れテストの
導出元だから**である（tester が `src/**` を読まないのと同じ理由。実装を知った上で書いた契約は、実装を
追認するだけの契約になる）。

この独立性は**プロジェクトの契約**について意味を持つ。テンプレート自身の方法論を決めるメタADRには、
「追認してしまう実装」に相当するものが存在しない。architect の独立性を持ち込む先ではない。

## 決定

### 1. メタADR（`meta/adr/`）の起草はorchestratorの領分とする

`meta/adr/` 配下のADRは orchestrator が起草してよい。Codex も同様である（`meta/agent-runtime-mapping.md`。
0036・0037・0044 が既にそうなっている）。

`.claude/agents/architect.md` の職務記述にある「ADR」は、**プロジェクトscopeのADR（`projects/<p>/adr/`）
を指す**と読む。同ファイルの文言を、その意味に明確化する（`.claude/agents/**` は役割契約のSSoTである。
ADR-0036）。

これは職務の移管ではなく**読み方の確定**である。architect.md の本文（責務節）は元から「**スライスの**
契約（…・ADR）」「プロジェクト開始時、…選定理由を**ADR第1号**のドラフトにする」と書いており、
プロジェクトscopeを前提にしている。曖昧だったのは `description` の1行だけである。

### 2. 範囲は「方法論・運用・ガバナンス」に限る

orchestrator が起草してよいのは、**テンプレート自身の方法論・運用・ガバナンスについてのメタADR**で
ある。次は `scope: meta` であっても architect の領分とする。

- プロジェクトの契約の中身を決めるADR（シナリオの解釈・API形状・ドメインルール）
- プロジェクトの設計骨格を決めるADR（モジュール境界・データモデル）

判定に迷う場合の目安: **そのADRの素材が「摩擦の観測」なら orchestrator、「人間の意図と業務の言葉」
なら architect**。前者は orchestrator にしか見えず、後者は orchestrator が持つべきでないものである。

### 3. 本ADRは FR-022 を弱めない

ADR-0046 の決定1〜4（検証ツールの施錠）は**そのまま維持する**。本ADRが認めたのは「人間の承認点で
必ず止まる成果物の起草」であって、「自己採点になる成果物の作成」ではない。

したがって cause_key `orchestrator-as-substantive-source` の計数に、メタADRの起草を**遡って加えない**
（FR-006・FR-008・FR-009・FR-022 の4件は、いずれも人間の承認点を経ずに効力が発生する成果物であった）。

**friction-log には起票しない。** `meta/permissions.md`「人間判断の記録ルール」は「人間判断の発生
そのものはfrictionではない（エスカレーションは正常動作）。**AIの迷い・誤り・見逃しが関与した場合のみ**
friction-logにも記録する」と定める。本件は、orchestrator が規程の曖昧さを自ら検知して人間に上げ、
人間が裁定した——**設計どおりの動作**である。AIの誤りも見逃しも関与していない。

## 検討した代替案

- **案A: 文言どおりメタADRもarchitectに起草させる** / 不採用: 文脈3のとおり、orchestrator が観測事実と
  選択肢をプロンプトで注入することになり、**§6 が禁じる実質的内容の注入を、委譲の見た目で行う**結果に
  なる。FR-008 と同じ機構である。
- **案B: メタADR起草用の新しい役割（例: methodologist）を立てる** / 不採用: 観測点が orchestrator に
  しかないという構造は変わらないため、案Aと同じ問題を抱えたまま役割定義が1つ増える。P-05（摩擦が
  発生してから足す）にも反する——現時点で orchestrator の起草によって生じた実害は観測されていない。
- **案C: 裁定だけをactiveContextに1行書いて済ませる** / 不採用: `meta/permissions.md`「人間判断の
  記録ルール」（ADR-0003）が、人間判断はADRを起票してから作業を再開せよと定めている。またこの裁定は
  FR-022 との関係を説明しないと「禁止が5回目で折れた」と読まれる。**説明こそが本ADRの中身**である。
- **案D（採用）: 裁定を記録し、FR-022 との境界を「自己採点かどうか」で引く** / 採用: 裁定を残しつつ、
  ADR-0046 が塞いだものを弱めない境界線を明示できる。

## 帰結

- メタADRの起草者が確定し、ADR-0046 の確認事項が閉じる
- `.claude/agents/architect.md` の `description` の曖昧さが解消される。**役割契約のSSoT（ADR-0036）の
  変更なので、Codex側の読み取りにも同時に効く**
- **orchestrator が自ら「自分は規程違反ではないか」と問い、人間が裁定し、その境界が成文化された**という
  経路自体が1つの実績になる。§6 の禁止は残り、その適用範囲が明確になった
- 判定に迷うADRが出た場合の目安（決定2）は、実際に迷う事例が出るまで検証されない。**目安が機能しな
  かったら、その時点で摩擦として記録する**（P-05）
