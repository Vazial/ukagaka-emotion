# ADR-0057: PR本文は、このリポジトリを知らない人が読めるように書く

> **承認者向けサマリ**
>
> 人間から「PRの内容をもう少し人間がコンテキストを持たずに読めるようにしたい」という指摘が
> 出た。直近20本のPR本文を測ると、説明のない記号（`ADR-0046`・`FR-022`・`P-04`・`L0` など）が
> 平均して160字に1個の割合で出てくる。20本のうち、そうした記号を1つも使っていないPRは無い。
> 原因は書き手だけでなく雛形の側にもある。雛形の最初の節は内部統治の分類（PR種別のチェック
> ボックス4つ）で、「この変更は何か」を書く欄はどこにも無い。実際、直近4本は雛形を丸ごと
> 捨てて自前の節で書かれており、その巻き添えでactiveContextの更新確認や採番確認も一緒に
> 落ちている。**読みやすく書くことと手続きを踏むことが、いま二者択一になっている。**
>
> 決定は4点。
>
> 1. PR本文を上下2段に分ける。上は読む人のため（何が変わるか／判断してほしいこと／なぜ／
>    代償）、下は記録（検証・統合先・手続き）
> 2. 上段の書き方を3つ決める（記号には中身を添える／他のPRの中身を前提にしない／「なぜ」は
>    起きた事から始める）
> 3. 雛形の実体を `.github/pull_request_template.md` 一本にする。`meta/templates/pull-request.md`
>    は中身を持たずポインタにする
> 4. 機械検査は足さない。ただし後退条件を先に書いておく
>
> 払うもの: PR本文は少し長くなる。そして守られる保証は無い（決定4の通り、機械で見ないため）。

## 文脈

### 1. 何が起きたか

2026-08-23、人間から指摘が出た。「PRの内容をもう少し人間がコンテキストを持たずに読めるように
したい」。PRを承認するのはこのリポジトリの外にいる時間のほうが長い読み手であり、いまの本文は
「さっきまでこの中で作業していた人」にしか読めない、という意味である。

### 2. 測ってみて分かったこと

直近20本のPR本文を機械的に数えた。数えたのは**説明を伴わずに置かれた記号**である——`ADR-0046`・
`FR-022`・`P-04`・`L0`〜`L4`・`§2`・`cause_key`・`決定3` のような、指し先を開かないと中身が
分からない表記を指す。コードブロックとインラインコードは数える前に落としている。

| | 値 |
|---|---|
| 記号の密度（中央値） | 本文1000字あたり6.2個 ＝ **約160字に1個** |
| 最も密なPR | #130（53字に1個）・#128（89字に1個）・#122（99字に1個） |
| 記号を1つも使っていないPR | **20本中0本** |

密度そのものより、**1本も例外が無い**ことのほうが重い。書き手の癖ではなく、この形式が常態に
なっている。

### 3. 原因の半分は雛形の側にある

GitHubがPR作成時に自動で開く雛形（`.github/pull_request_template.md`）の第1節は「PR種別と
承認事項」で、中身はチェックボックス4つである。読み手が最初に目にするのは内部統治の分類に
なっている。そして**「この変更は何か」を平文で書く欄が、雛形のどこにも無い**。

これが効いていることは、雛形からの離れ方に表れている。20本の見出しを雛形の6節と突き合わせた。

| PR | 雛形の節をいくつ持つか | 冒頭の節 |
|---|---|---|
| #130・#129・#128・#124（直近） | **0/6** | 「何を決めるか」「承認事項」「何を決めたか」 |
| #127〜#111 | 5〜6/6 | 「PR種別と承認事項」 |

**直近4本は雛形を丸ごと捨てている。** 捨てた先で書かれているのは「何を決めるか」「なぜ」
「承認者に判断してほしいこと」——つまり読み手向けの節であり、書き手は毎回それを自前で
作り直している。

ただし捨てたことで失われたものがある。#128・#129 のどちらにも、activeContextを更新したか
（全PRが通す関所として ADR-0034 が置いた確認欄）と、ADR番号を未マージのブランチまで見て
取ったかの確認欄（ADR-0026・0052）が無い。**読みやすく書くことと手続きを踏むことが、
いまの雛形では二者択一になっている。**

### 4. 雛形が2つあり、既に食い違っている

同じPR雛形が2箇所にある。`meta/templates/pull-request.md`（33行）と
`.github/pull_request_template.md`（57行）で、後者は前者の上位互換である。後者にしか無い節が
3つある——PR種別（ADR-0041）・摩擦の収穫確認（ADR-0055）・ADRの承認方式（ADR-0035）。
同じものを2箇所に置けば必ず食い違う、というのはこのリポジトリの信条（P-04）が言っていることで、
実際に食い違っている。

### 5. これは ADR-0016 が「実例が出たら対応する」と留保した箇所である

人間が承認する成果物は冒頭に承認者向けサマリを置く、という一般則を ADR-0016 が定めている。
そのADRは代替案の1つとして「PR雛形にもサマリ節を機械的に足す」を検討したうえで見送っており、
理由は「PRはタイトルが同じ役目を果たしている」「この雛形固有の読みにくさの実例が無い」で
あった。実例が記録されたら個別に対応する、とも書かれている。今回の指摘がその実例にあたる。

### 6. 同じ指摘がADRについては先に出ている（本ADRはそれに依存しない）

2026-08-22 に「ADRが読みにくい。1枚だけ読んでも何のことか分からない」という指摘があり、
ADRの文体と自己完結性を定める ADR-0053 が書かれている。ただし**そのADRはまだ承認されて
おらず**（PR #133 として提出中）、本ADRはその承認を前提にしない。対象（PR本文）も、
効かせる手段（GitHubが自動で開く雛形）も別であり、ADR-0053 が否決されても本ADRの決定は
変わらない。両者が同じ方向を向いているのは、指摘が2回とも同じ場所を突いているからである。

## 決定

### 決定1. PR本文を上下2段に分ける

上段は読む人のためのもので、4節を持つ。

| 節 | 何を書くか |
|---|---|
| 何が変わるか | 前提知識ゼロで読める3〜5行。変更後にどうなるかを、ふつうの言葉で |
| 判断してほしいこと | 承認者が決めること。無いなら「なし」とその理由を1行 |
| なぜ | 起きた事から始める |
| 代償・残る弱点 | 何を諦めるか、何が壊れうるか。無いなら「なし」 |

区切り線を挟んで下段が記録である——変更したファイル・検証結果・統合先と対象契約・手続きの
確認欄。**区切り線は「ここから下は判断に要らない」という合図**であり、承認者が読むのを
どこでやめてよいかを示す。

「判断してほしいこと」の1行目に、PRの種別と判断の要否を書く。PRを4種別（スライス／meta／
昇格／同期）に分けて冒頭で明示するという決定（ADR-0041）は**そのまま維持する**。変えるのは
表現だけで、チェックボックス4つを1行に畳む。判定基準（そのPRに人間がまだしていない決定が
含まれるか）も、「判断なし」の意味（人間の判断が不要という意味であって、機械検証が不要と
いう意味ではない）も変えない。

### 決定2. 上段の書き方を3つ決める

1. **記号には中身を一言添える。** 説明を先に書き、IDは後ろの括弧に置く。「ADR-0046により」では
   なく「検証ツールへの書き込みをAIから塞いだ決定（ADR-0046）」と書く。上段はそもそもIDを
   使わずに書けるなら使わない
2. **他のPRやissueの中身を前提にしない。** 「#121の起こし直しです」だけでは、何が起きたのかは
   #121 を開かないと分からない。中身をこのPRの本文に書く
3. **「なぜ」は起きた事から始める。** 規程の引用・ファイル名・IDから始めない

タイトルも同じ扱いにする。末尾の「（ADR-00xx）」に中身を代弁させず、タイトル本体で変更内容を
一文にする。

### 決定3. 雛形の実体を1つにする

`.github/pull_request_template.md` を実体とする。GitHubがPR作成時に自動で開くファイルであり、
**全PRが必ず通る関所**だからである。`meta/templates/pull-request.md` は中身を持たず、実体を指す
ポインタにする。役割定義について、実行時に読まれるファイル（`.claude/agents/**`）を実体にして
meta側を説明に徹させた形（ADR-0036）と同じ扱いである。

### 決定4. 機械検査は足さない。後退条件を先に書いておく

PR本文はリポジトリの中に無いので、統治文書のチェッカ（`meta/tools/govlint.py`。ネットワークを
使わずリポジトリ配下だけを見る、という性格を持つ）からは見えない。PR作成の直前に走るhook
（摩擦の収穫のために `gh pr create` に既に付いている。ADR-0055）なら本文を読めるが、今回は
入れない——選択肢3つ（雛形の改訂だけ／hookで測って報告／hookでブロック）とトレードオフを
提示したうえでの人間の判断（2026-08-23）である。まず規約で試す、というのは摩擦が出てから
足すという信条（P-05）に沿う。

**後退条件**を先に書いておく。本決定より後に出した meta scope のPRを5本ためて、そのうち
**3本以上が上段4節を持たない**か、**上段に説明のない記号が3個以上ある**なら、hookで測って
報告する案（ブロックはしない）を別ADRとして出す。検証ツールの施錠を決めたADR（ADR-0046）が
「過剰と分かれば後退する」と条件を書いておいたおかげで、19日後に実測して畳めた（ADR-0054）。
同じ形を採る。

## 検討した代替案

- 案A: 雛形は触らず、書き方の心得を `meta/guardrails.md` に足すだけ / 不採用の理由: 直近4本が
  既に雛形を捨てて自前の節で書いている。守られていないのは心得ではなく雛形の側であり、心得を
  足しても、PR作成時に自動で開くのは雛形のほうである
- 案B: 上段だけの短い雛形にし、記録の節を全部落とす / 不採用の理由: 検証結果・activeContextの
  更新・ADRの承認方式・採番確認は、それぞれ別のADR（0034・0035・0041・0052・0055）が「全PRが
  通る関所に載せる」と決めた結果そこにある。落とせば飛ばされる。直近4本で現に飛んでいる
- 案C: PR作成直前のhookで本文を測って報告する / 不採用の理由: 人間の判断（決定4）。ただし
  後退条件を満たしたら、この案を別ADRで出す
- 案D: 人間向けの要約をPR本文とは別のコメントに出す / 不採用の理由: 同じ内容が2箇所に分かれれば
  必ず食い違う（P-04）。1枚の中で層を分ける手段（区切り線）で足りる

## 帰結

- **本PRで実施する**: `.github/pull_request_template.md` の全面改訂／`meta/templates/pull-request.md`
  のポインタ化／それを参照している `AGENTS.md`・`meta/README.md` の追随／`meta/guardrails.md` §2
  への条文追加
- ADR-0034 は「PRテンプレ2種の**両方**にactiveContextのDoDを載せる」と書いている。雛形が1つに
  なるので載る場所も1つになるが、0034 の決定（全PRが通る関所に載せる）は満たされたままである。
  承認済みADRは書き直さない（P-06）
- **効かない範囲**: 上段が本当に前提知識なしで読めるかは機械では確かめられない。決定2が守られて
  いるかは人間が読んで判断するしかなく、本ADRはその判断基準を文章にしたに留まる
- 過去のPRは書き直さない
