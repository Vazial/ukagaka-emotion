# ADR-0071: 着手前に全体をタスク分解し、それからPR単位を決める

> **承認者向けサマリ**
>
> 2026-09-27、テンプレ取り込みの登録漏れ対策で、思いつくたびにPRを切ってしまい、3本（手順書追記・表とスクリプトとADR・表への1行追加）に割れた。
> 特に最後の1本は、前の1本に含めるべき小ささだった。人間から「PR単位が小さすぎる」「タスク分解するフローが必要だった」と指摘された。
>
> 決定は1点。役割を起動する前、あるいはPRを書き始める前に、まず全体のタスクを分解し、どこでPRを区切るかを先に決めてから手を動かす。
> 目安は `meta/orchestration.md` §7 に置く。
>
> 払うもの: 最初に分解の時間を取る分、着手が一手遅れる。

## 文脈

同じ会話の中で、関連する変更（手順書・表・スクリプト・ADR・表への追記）が段階的に見えてきた。
その都度「見えた分だけ」PRにしてしまい、承認の性質が同じもの同士まで分かれた。
`.github/pull_request_template.md` は PR の種別（スライス/meta/昇格/同期）ごとに判断の要否を定めるが、
同じ種別・同じ判断のまとまりを何本に割るかは、何も定めていなかった。

## 決定

複数の変更が見えてきたら、着手前に全体をタスク分解し、どこでPRを区切るかを先に決めてから手を動かす。
区切りの目安は次のとおり。

1. **同じ判断のまとまりは1本にする**。同じ会話・同じ合意から出た変更で、`.github/pull_request_template.md` の
   「判断してほしいこと」欄に書く種別・判断の要否が同じなら、分けない
2. **分けるのは、承認の性質が違うときだけ**。規程変更（判断: 要）と、それを反映するだけの昇格・同期（判断: なし）が
   混ざるときは分ける
3. **迷ったら大きい側に倒す**。着手後に「これは別々に切ったほうがよかった」と気づいたら、その時点でまとめ直す提案をする

`meta/orchestration.md` §3「1チケットの流れ」の役割起動（4）とDraft PR化（6）の間で、この分解を行う。
Linear のチケットに紐づかない、チャット主導の meta 作業でも同じ目安を使う。

## 検討した代替案

- PRの行数・ファイル数に数値の上限を決める / 不採用の理由: 数値は文脈で意味が変わる（表への1行追加と、規程1本の新設は同じ「小ささ」でも性質が違う）。判断の性質で区切るほうが実効性がある
- 個人の記憶（Claude Codeのmemory）にとどめる / 不採用の理由: このリポジトリはClaudeとCodex双方が並行して動く（CLAUDE.md）。個人の記憶はセッションをまたぐと薄れ、Codex側には届かない。リポジトリ自身の手順書に置けば、どちらのセッションが読んでも効く

## 帰結

- 次にPRを切るときは、複数の変更が見えた時点で先に分解を書き出し、区切りを決めてから着手する
- 分解の記録そのものをどこかに残す義務は課さない。区切りの結果（PRの本数と境界）に表れれば足りる
