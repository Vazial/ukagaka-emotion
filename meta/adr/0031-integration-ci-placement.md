# ADR-0031: クロスプロジェクト結合CIの置き場と起動規約を定める（ADR-0026の穴埋め）

> **承認者向けサマリ**: フロントの2本目の実バックエンド接続（`GET /rooms/{roomId}/availability`）に着手
> するにあたり、ADR-0009決定6(b)が「結合の回帰ゲートを設計せよ」と要求している。ところが ADR-0026 の
> CI分割（共有govlint＝L0／プロジェクト別`ci-<project>.yml`）は、**2つのプロジェクトにまたがる結合
> テストの置き場を定義していない**。本ADRはこの穴を埋める。決定は3点。**(1)** 第3のワークフロー種別
> として「結合CI」`.github/workflows/ci-integration.yml` を新設の置き場と定め、起動は**関与する両
> プロジェクトのpathsの和集合**（＋自ファイル）とする。これは ADR-0026 §1.2 の「新プロジェクト＝
> 1ファイル追加・共有ファイル不編集」不変条件の、**明示的に認めた例外カテゴリ**である（結合は本質的に
> 横断的でどちらか一方のプロジェクトに分類できない）。**(2)** 必須チェック方針は ADR-0026 §1.3 に従い
> **案i（緩い運用）から始める**——結合CIは当面 required にせず、レビュー時に緑を目視確認する。理由は
> 「形（レスポンス構造）の互換性はSSoT yamlを介して既に推移的に機械ゲートされており、結合CIが固有に
> 検証するのは配線（proxy・URLパス・fetch・env・識別子空間の整合）であってopt-inで低リスク」だから。
> 摩擦が観測されたら案iii（常時起動＋内部paths判定でrequired化）へ強化する。**(3)** 結合ジョブの中身
> （実スタック＝PostgreSQL＋Spring＋フロントを起動するスモークか、より軽い配線チェックか）は本ADRでは
> 決めない（P-02）。実装スライス（availability実接続）で設計する。本ADRは置き場・起動・必須方針という
> **構造の穴だけ**を埋める。**本ADRはCIワークフローの実ファイルを作らない**（ADR-0026 と同じく、ADRは
> 決定、実装はスライス）。

## 文脈

`GET /rooms`（RSV-L）は実バックエンドに接続済み（ADR-0009、main）。次スライスは
`GET /rooms/{roomId}/availability` の実接続であり、これは ADR-0009 決定6 が「条件(b) 2本目のAPIを
実接続する時」として明示的に「結合の回帰ゲートを設計する」と定めた地点にあたる。ADR-0009 §6 は同時に、
**「meta/adr/0026は結合テストの置き場を定義していないという穴があり、(a)(b)に至った時点でその穴を埋める
設計（meta層の追補）も同時に必要になる」**と、本ADRが対処すべき欠落を名指ししている。

ADR-0026 の CI 構造は2種類しか持たない:

- **共有 govlint（L0、`govlint.yml`）**: 全プロジェクト横断の統治文書検証。常時実行・pathsフィルタなし。
- **プロジェクト別 `ci-<project>.yml`**: 自プロジェクト配下（`projects/<project>/**` ＋自ファイル）の
  変更時のみ起動。ADR-0026 §1.2 の不変条件「新プロジェクトの参入は新規ワークフローを1本足すだけ・
  既存の共有ファイルと他プロジェクトのCIは編集しない」を守る。

結合テストは**このどちらにも属さない**。フロントとバックの配線（Vite proxy・URLパス・fetch実装・環境
変数・CORSの有無・実DBのroomId名前空間）は、片方のプロジェクトのpathsだけを見ていては壊れを捕まえ
られない——バック側の変更でフロントの実接続が壊れることも、その逆もある。したがって結合CIは**両
プロジェクトのpathsで起動する必要があり**、ADR-0026 の2分類には収まらない。

この穴は、FR-007（走破＝L5で発見: `GET /rooms`だけ実接続すると実DBのUUIDとモックのroomIdが食い違い
画面が機能しない）が実証した「配線・識別子空間は、モックのみで完結するL1/L4では原理的に検出できない」
という性質と対になっている。**P-10（上段で見つかった失敗は下段の検証を強化する材料にする）**に照らせば、
走破で見つかったこの失敗種は、下段（CI）の検証を強化する置き場を必要とする。本ADRはその置き場を用意する。

## 決定

### 1. 第3のワークフロー種別「結合CI」を新設し、両プロジェクトのpathsで起動する

クロスプロジェクトの結合検証は `.github/workflows/ci-integration.yml` に置く。起動トリガーは、関与する
プロジェクト群のpathsの**和集合**（＋自ファイル）とする。availability実接続の結合（reservation-frontend
⇄ reservation-system）の場合は次の形:

```
on:
  pull_request:
    branches: [main, "project/**"]
    paths:
      - "projects/reservation-frontend/**"
      - "projects/reservation-system/**"
      - ".github/workflows/ci-integration.yml"
  push:
    branches: [main, "project/**"]
    paths:
      - "projects/reservation-frontend/**"
      - "projects/reservation-system/**"
      - ".github/workflows/ci-integration.yml"
```

これは ADR-0026 §1.2 の不変条件（新プロジェクト＝1ファイル追加・共有ファイル不編集）の、**明示的に
認めた例外カテゴリ**である。ADR-0026 の不変条件は「**プロジェクト別**CI」を対象とした規律であり、結合は
本質的に横断的でどちらか一方のプロジェクトに分類できない以上、そこに含めるのは無理がある。整理すると:

- **プロジェクト別CI**（`ci-<project>.yml`）: ADR-0026 §1.2 の不変条件が引き続き全面的に適用される。
  新プロジェクトの参入でこのファイル群を相互編集しない。
- **結合CI**（`ci-integration.yml`）: 横断カテゴリ。関与するプロジェクトのpathsを列挙する。新プロジェクト
  の追加は、そのプロジェクトが結合に**参加する場合に限り**このファイルのpaths（と中身）を触る。参加
  しないなら触らない。結合の組が将来複数になる場合は `ci-integration-<pair>.yml` のように組ごとに
  分割してよい（本ADRは現時点で1組のみを想定し、単一ファイルで足りるとする。P-02）。

### 2. 必須チェック方針は ADR-0026 §1.3 の案i（緩い運用）から始める

結合CIは**当面 required status check にしない**。PR上に表示される結合CIの結果を、レビュー時に人間が
目視で緑を確認してマージする運用とする。

理由:

- **形の互換性は既に推移的に機械ゲートされている**。バックはL4で `OpenApiInteractionValidator` が
  yaml原本に対して応答を照合し、フロントは型をyaml（SSoT）から生成する（ADR-0008）ため、使い方が
  ずれれば `npm run build` が落ちる。すなわち結合CIが**固有に**検証するのは配線（proxy・URLパス・
  fetch・env・実DBのroomId名前空間）だけであり、これは実API経路が**opt-in＝まだ誰の既定経路でもない**
  うちは低リスク（壊れても有効化した本人に影響が限られ即座に気づく。ADR-0009 §6）。
- 重量級の横断ジョブ（実スタック起動を伴いうる）をいきなり hard-required にすると、ADR-0026 §1.3 が
  指摘する「pathsでスキップされた required check が Waiting のまま詰まる」既知の落とし穴と、全PRに
  かかるCIコストの両方を招く。

摩擦（無関係PRの待ち問題、または required 外による緑担保の緩みへの不満）が実際に観測されたら、
ADR-0026 §1.3 の**案iii（トリガーからpathsを外して常時起動させ、ジョブ内部で変更検出して無関係なら
成功スキップ→required化）**へ強化する。**required checks 一覧の変更は人間承認**（meta/permissions.md
「ゲート変更」）を要する点は ADR-0026 §1.3 と同じ。

### 3. 結合ジョブの中身は本ADRで決めない（実装スライスで設計する）

結合CIが実際に何を実行するか——実スタック（PostgreSQL＋Spring＋フロント）を起動して proxy 越しに
`GET /rooms`→`GET /rooms/{roomId}/availability` の識別子連続性（FR-007の失敗種そのもの）を叩くスモーク
なのか、より軽い配線チェック（fetchパスとproxy設定・yamlのpathsの静的照合）なのか——は、本ADRでは
確定しない（P-02: 全体を先に設計しない）。これは実装スライス（availability実接続）の検証設計として、
ADR-0009 の走破優先の姿勢（ADR-0024）とコスト方針を踏まえて決める。

本ADRは**置き場（ci-integration.yml）・起動（両プロジェクトpaths和集合）・必須方針（案iから）**という
構造の穴だけを埋める。走破（ADR-0024、人間が最終判断）は引き続き結合検証の主軸であり、自動化された
結合ジョブは（追加される時は）それを**補完**するものであって置き換えない——FR-007は自動テストではなく
走破が発見した未知の帰結であり、走破の役割（既知でない帰結の発見）は自動ゲートでは代替できない。

## 検討した代替案

- 案A: 結合テストを既存の `ci-<project>.yml`（例: フロント）に相乗りさせる / 不採用: バック側だけの
  変更で壊れる配線を捕まえられない（フロントのpathsで起動しないため）。かつ「フロントCIがバックの
  スタックを要求する」ことになり、プロジェクト別pathsの意味論（自プロジェクト配下のみ）を壊す。
- 案B: 共有 `govlint.yml`（常時実行ゲート）に結合ジョブを足す / 不採用: govlintは統治文書検証専用で
  プロジェクトのランタイムを持たない。常時実行の共有ゲートに重量級の実スタックジョブを乗せると全PRが
  遅くなる。
- 案C: 結合CIを一切設けず、走破のみを恒久ゲートにし続ける / 不採用: ADR-0009 §6 が条件(b)で「ゲートを
  設計せよ」と明示しており、置き場を定義しないままだと次に同じ地点へ来た者が同じ穴を再発見する。ただし
  **重量級ジョブの中身は本ADRでは先送りする**（決定3、P-02）——穴（置き場）は今埋め、実ジョブはopt-in
  で後から足す、という段階導入は妨げない。
- 案D（採用）: `ci-integration.yml` を横断カテゴリとして命名・定義し、必須方針は緩い運用から、中身は
  スライスへ委譲する / 採用: ADR-0026 の2分類の穴をちょうど埋め、P-02（先に全体を設計しない）と
  P-05（摩擦が出たら足す）を守る最小の構造追補になる。

## 帰結

- availability実接続スライスは、結合テストを足す場合の**定まった置き場**（`ci-integration.yml`）と、
  必須方針（案iから）を持つ状態で着手できる。中身の設計はスライスの検証設計として行う。
- ADR-0026 §1.2 の不変条件は「プロジェクト別CI」を対象とする規律であることが明確化された。結合CIは
  別カテゴリ。`meta/guardrails.md` §2「CI構成」の記述への反映は、**結合CIの実ファイルを作る実装スライス
  とセットで行う**（ADR-0026 が guardrails/agents への反映を「実装とセット」に回したのと同じ扱い。本ADR
  では宿題として記すに留める）。
- 本ADRはCIワークフローの実ファイル（`.github/workflows/*.yml`）を変更しない。
- 併せて、`meta/guardrails.md` §2 の ruleset 状態行の**事実誤り**を訂正する（本PRに同梱。ADR-0028 の初
  適用で `project/reservation-frontend` ブランチ＋ruleset を 2026-07-29 に作成済みであり、「未作成」の
  記述が古くなっていた）。これはCI構成の記述変更とは別の、純粋な事実訂正である。
