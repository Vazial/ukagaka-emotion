# ADR-0019: designerの外部AI実行をCLI経由で自動化できるようにする（案A）

## 文脈

ADR-0018でdesignerを「design integrator」へ再定義し、(b)外部AIによる画面設計の実行は「当面は人間が
実行を担う」とした（design系のMCP/CLIコネクタが現存しないため）。今セッションで、この前提を検証する
実験を行った結果、2つの事実が実証された。

1. **自動化(案A)は動く**: Gemini CLI（`@google/gemini-cli`）をヘッドレスモード（`gemini -p ...
   -o text --skip-trust`）で呼び出すことで、ブリーフを渡し設計をファイルとして得る一連の流れが動作
   することを確認した。認証は`~/.gemini/.env`のGEMINI_API_KEYを実行時にsourceする形で、プロセス
   継承の問題を回避した。スパイクのラッパスクリプトは`scratchpad/commission-design.sh`に残っている
2. **質を決めるのはモデルでなく"ブリーフ"**: 同一モデル（gemini-3.5-flash）に対し、体験全体・現状の
   不満点を要件として明示し「既存APIに縛られず理想を描いてよい」と指示したリッチなブリーフでは実用
   水準の設計（タイムライン・ダッシュボード）が得られたが、「パネル1枚を簡潔に」という狭いブリーフ
   では凡庸な結果しか得られなかった。これはADR-0018の主張（designerの(a)ブリーフ作成が下流品質を
   決める）の直接の実証である

あわせて、運用上の現実も判明した（正直に規約化する）:
- 無料枠は入力（ブリーフ）・出力（設計）を学習に利用しうる上、人間レビューが入る可能性がある。**ブリーフ
  に個人情報・機密情報を書いてはならない**という規律は、既存のno-personal-info規律と同一線上にある
- 実案件では**有料枠・Vertex AI（学習に利用しない設定）へ切替える**（低頻度な利用なら実質数円程度）
- **Pro系モデル（2.5-pro/3.x-pro等）は無料枠ではlimit:0＝有料専用**。無料で使えるのはFlash系のみ
- 無料枠の**日次上限は低い**（3.5-flashで概ね20回/日程度を観測）。低頻度の実運用では足りるが、反復
  検証には向かない

## 決定

designerの(b)外部AIによる画面設計の実行を、**CLI経由で自動実行できる（案A）**ものとして選択肢を追加
する。ADR-0018が定めた「当面は人間がこの実行を担う」という前提は**置き換えない**（本ADRはADR-0018を
supersedeしない）。人間-in-the-loopは**引き続き有効な代替経路**として残す（例: CLI実行環境が使えない
場合、コスト・利用枠の都合、人間が結果を吟味しながら反復したい場合等）。

### 運用規約（明記）
- **無料枠の扱い**: 学習利用・人間レビューの可能性があるため、ブリーフに個人情報・機密情報を書かない
  （既存のno-personal-info規律をそのまま適用する）
- **実案件の切替**: 低頻度の実運用では有料枠・Vertex AI（学習不使用の設定）へ切替える
- **モデルの制約**: Pro系モデルは無料枠では使えない（limit:0）。無料で使えるのはFlash系のみ。無料枠を
  使う場合、Flash系モデルの性能で「リッチなブリーフ」が効くという実証（上記2）を前提にする
- **日次上限**: 無料枠の日次上限は低い（Flash系で概ね20回/日程度）。反復検証を要する場面（refinement
  ループの複数反復等）では、上限に達する可能性を見込んでおく

### ツール実体（指定のみ・実装しない）
CLI自動実行の実体は`meta/tools/commission-design.sh`に置く、と**指定する**。ただし**ロジックを持つ
実装＋smokeテストはdeveloperの領分**（meta/adr/0014: 検証インフラのうちロジックを持つものはテスト付き
でdeveloperが実装する）。本ADRは指定のみを行い、実装しない（architectの禁止事項: 実装コードを書かない）。
developerへの宿題として以下を切り出す:
- `meta/tools/commission-design.sh`（またはproject固有の対応物）の実装: ブリーフファイルを受け取り、
  Gemini CLIをヘッドレス実行し、設計成果物をファイルに保存する
- 認証情報（GEMINI_API_KEY）の扱い: `~/.gemini/.env`からのsourceを含め、シークレットとしてAI読み取り
  禁止設定（guardrails.md 3節）と矛盾しない形にする
- 上記「運用規約」（無料/有料切替・Pro系不可・日次上限）を、スクリプトのドキュメント・エラーメッセージ
  等に反映するかはdeveloperの実装判断
- smokeテスト（実際にAPIを叩かない、または最小限のモック呼び出しで動作確認する形を想定。実際のAPI
  呼び出しを伴うテストの要否・コストはdeveloperが判断する）

### designer役定義の改訂
meta/agents.md §4の(b)の記述を「CLI経由の自動実行が可能（案A）。人間-in-the-loopは代替として残る」に
更新する。designer.md（原本・デプロイ側双方）の(a)ブリーフ作成に、「リッチなブリーフ」の基準を明記する
（下記「帰結」参照）。

## 検討した代替案
- 案L: 人間-in-the-loopのみを維持し、自動化しない / 不採用: CLI経由の自動実行が動作することを実証済み。
  自動化の選択肢を用意しないのは、実証した事実を活かさないことになる。ただし人間-in-the-loopを廃止する
  わけではない（コスト・利用枠・反復検証の都合で使い分ける）
- 案M: 有料枠・Vertex AIのみを前提にする（無料枠は使わない） / 不採用: 低頻度の実運用・検証目的では
  無料枠で十分な場面がある。無料枠の制約（学習利用・Pro不可・日次上限）を正直に規約化した上で選択肢
  として残す方が実用的
- 案N: ADR-0018をsupersedeする（前提が変わったため） / 不採用: ADR-0018の核（designerを発案者から
  design integratorへ再定義する、人間-in-the-loopを当面の前提とする）自体は変わらない。今回追加された
  のは「自動実行という選択肢」であり、既存の決定を置き換えるのではなく拡張する。ADR-0016がADR-0002・
  0010を置き換えずに一般化した先例（「両者が個別に辿り着いた形の一般化・正当化であり、置き換えでは
  ない」）に倣い、relates_toで関連付けるにとどめる
- 案O: ツール実装（commission-design.shの本実装）をこのADRに含める / 不採用: architectの禁止事項
  （実装コードを書かない）に反する。ロジックを持つ検証インフラの実装はdeveloperの領分（meta/adr/0014）。
  本ADRは指定のみに留め、実装はdeveloper宿題として明示的に切り出す

  要素（目的、対象ユースケース、ドメインルール、現状の不満を要件として明示、「既存APIに縛られず理想を」
  という指示、採用済みデザインシステムの指定、成果物の指定）を明記し、meta/templates/design-brief.md
  （新設）へのポインタを置く
- meta/agents.md §4の(b)の記述を更新する
- meta/templates/design-brief.mdを新設する。今回効いたリッチなブリーフの構造を実例として、必須要素を
  テンプレート化する。個人情報・機密情報禁止の注記を含める
- **developer宿題**（上記「ツール実体」参照）: `meta/tools/commission-design.sh`の実装＋smokeテスト。
  次のスライス作業としてorchestratorが割り当てる
- reservation-frontendでは、自動化の到達点と「ブリーフが要」という学びをactiveContext.mdに反映する
- friction-log: 「狭いブリーフ→凡庸な設計」という学びは、architectの判断でFR-002として記録した
