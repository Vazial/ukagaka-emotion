# ADR-0035: ADRの承認記録をPR1本で閉じる。滞留はgovlintが棚卸しする

> **承認者向けサマリ**: ADR-0031〜0034 は人間が承認しマージ済みでありながら、frontmatter が
> `status: 提案中` / `approved_by: null` のまま残っていた（2026-07-29発覚・訂正済み）。原因は手順の
> 構造にある——ADRは承認前に起草するので `提案中` で書くしかなく、**承認行為はそのPRのマージ**である
> ため、承認の事実をファイルに書き込むには**マージ後に2本目のPR**が要る。その2本目は差分が
> frontmatter 2行だけで単独の価値が見えないため、飛ばされる。実測すると、**提案中のまま滞留している
> ADRは10本**（最古11日）あり、そのうち複数は**すでに施行されている**（`meta/guardrails.md` の
> ブランチ運用・CI構成は `meta/adr/0026`（提案中）を根拠に記述されている）。規程が「まだ決めていない
> 決定」の上に立っている状態である。決定は3点。**(1)** ADRを含むPRは承認方式を**二択で明示する**——
> **(i) マージ＝承認**（起草時に `status: 承認済み` ＋ `approved_by: "本PRのマージをもって承認…"` と
> 書き、人間はマージしないことで拒否する。1PRで閉じる。**既定**）か、**(ii) 記録のみ・承認は後日**
> （`status: 提案中` のまま。判断材料は残すが決定はしない、と意図して選ぶ場合）。PRテンプレのチェック
> 項目にする。**(2)** govlint に `[REPORT] 提案中のまま滞留しているADRの棚卸し`（経過日数つき）を
> 追加する。承認すべきかは意味判定なので**ERROR化しない**（P-04：機械が確定できるものだけ機械に
> 確定させる）。**(3)** 既存の提案中10本を本ADRで一括承認しない——棚卸しREPORTを出した上で人間が
> 個別に判断する。**本ADR自身が(i)の初適用**であり、`status: 承認済み` で起草されている。

## 文脈

### 1. 何が起きたか

ルート `activeContext.md` は ADR-0031〜0034 を「承認済み」と記述していた。ところが4本とも frontmatter は
`status: 提案中` / `approved_by: null` のままだった。人間に確認したところ「承認済みが正・frontmatter の
記録漏れ」との裁定が出た（2026-07-29）。frontmatter は ADR-0028 と同じ様式に訂正した（PR #42）。

### 2. 原因は個別のうっかりではなく手順の構造

ADRは**承認される前に**起草される。したがって起草時に書ける status は `提案中` だけである。一方、
`meta/permissions.md` の承認ポイント「信条・規程の変更」における**承認行為の実体は、人間がPRをmainへ
マージすること**である（`meta/guardrails.md` §1「人間のみができること: main・`project/<project>` への
マージ」）。

```
起草（status: 提案中）→ PR → 人間がマージ ＝ 承認が成立
                                    ↓
                          この時点でファイルは「提案中」のまま
                                    ↓
                    承認を記録するには 2本目のPR が要る ← 飛ばされる
```

2本目のPRは差分が frontmatter 2行だけで、レビューする内容も無く、単独では価値が見えない。したがって
**飛ばされることが常態**になる。ADR-0031〜0034 で起きたのはこれである。

### 3. ADR-0028 だけが正しく記録されていた理由

ADR-0028 の frontmatter は次の形をしている:

```yaml
status: 承認済み
approved_by: "本PRのマージをもって承認（人間裁定 2026-07-28: …）"
```

**起草時から `承認済み` と書き、`approved_by` で「このPRのマージが承認行為である」と宣言している。**
人間は承認しないなら**マージしなければよい**ので、拒否の手段は失われない。この方式は1本のPRで閉じる
ため、記録が遅れる余地がそもそも無い。ADR-0028 は意図してこう書いたわけではなく結果的にそうなったが、
**構造として正しいのはこちら**である。

### 4. 実害はすでに出ている

提案中のまま滞留しているADRは **10本**（2026-07-29時点、最古は2026-07-18起草の
`reservation-frontend/adr/0004` で11日経過）。問題は本数ではなく、**そのうち複数がすでに施行されて
いる**ことである:

- `meta/guardrails.md` §1 のブランチ運用は `meta/adr/0026 決定2` を根拠に記述されている。**0026 は提案中**
- `meta/guardrails.md` §2 のCI構成・必須チェック方針は `meta/adr/0026 決定1・1.3` を根拠にしている。同上
- `meta/adr/0032`（承認済み）は `meta/adr/0024`（**提案中**）の走破を前提に、その適用範囲を精緻化している

つまり**承認済みの規程が、未承認の決定の上に立っている**。これは「どれが本当に決まったことか」を
読み手が判別できない状態であり、P-11（現在だけを映す）の趣旨にも反する。同時に、`提案中` という状態が
「まだ決めていない」を意味しなくなることで、**意図的に判断を保留したADR（`reservation-frontend/adr/0004`
・`0005` は本当に承認待ち）と、単なる記録漏れが混ざり、区別できなくなっている**——これが最も悪い帰結である。

## 決定

### 1. ADRを含むPRは承認方式を二択で明示する（既定は(i)）

**(i) マージ＝承認（既定）**

起草時に次を書く。人間は**マージしないことで拒否する**。

```yaml
status: 承認済み
approved_by: "本PRのマージをもって承認（人間裁定 YYYY-MM-DD: 裁定の要旨）"
```

PRの本文には、承認者向けサマリへのポインタと「**このPRのマージが承認行為である**」旨を明記する。
1本のPRで閉じるため、記録が遅れる余地が構造的に無い。

**(ii) 記録のみ・承認は後日**

`status: 提案中` / `approved_by: null` のまま出す。**「判断材料は残すが決定はまだしない」と意図して
選ぶ場合に限る**（例: 論点を文書として固定したいが、前提となる別の決定を待っている）。この場合、
後日の承認は別PRで frontmatter を更新して記録する。

**PRテンプレの「人間の承認が必要な差分」節に、この二択のチェックを追加する**（決定2のREPORTと対に
なる関所。currencyの担保と同じく、ここは意味判定なのでchecklistが正しい強制レベル。P-04・ADR-0034）。

### 2. govlint に「提案中のまま滞留しているADR」の棚卸しREPORTを追加する

`meta/tools/govlint.py` に、`status: 提案中` のADRを **`date` からの経過日数つきで一覧する
`[REPORT]`** を追加する。既存の2つのREPORT（`cause_key` の再出現／未対応FRの棚卸し）と同じ扱いで、
**終了コードを1にしない**。

**ERROR化しない理由**（P-04）: 「このADRは承認されるべきか」「保留は妥当か」は意味判定であり、機械が
確定できない。日数の閾値を決めてERRORにすると、正当な保留（`reservation-frontend/adr/0004`・`0005`）が
CIを赤にし、回避のために内容を伴わない承認が押されるという最悪の誘因を生む。**機械は「見えていない
ものを見せる」ところまでを担い、判断は人間に残す**——これは govlint が `cause_key` 再出現をREPORTに
留めているのと同じ設計判断である。

閾値は設けず**全件を経過日数の降順で出す**。滞留が解消されればREPORTは自然に短くなる。

### 3. 既存の提案中10本を本ADRで一括承認しない

本ADRは方式を定めるだけであり、**既存の提案中ADRの status には触れない**。決定2のREPORTが一覧を
可視化した上で、人間が個別に判断する。理由: 一括承認は「読まずに承認する」ことと同義で、本ADRが
防ごうとしているもの（記録と実態の乖離）を別の形で再生産する。

### 4. 適用範囲

以後に起草するADRに適用する。既存には遡及しない（決定3）。本ADR自身が方式(i)の初適用である。

## 検討した代替案

- **案A: 2本目のPR（承認記録PR）を出す運用を徹底する** / 不採用: 飛ばされる理由が「規律の不足」では
  なく「単独の価値が見えない差分だから」である以上、徹底の呼びかけでは直らない。ADR-0031〜0034で実際に
  飛ばされた。P-04（口頭ルールにせず構造で強制する）に反する。
- **案B: 滞留日数のERROR化（例: 14日を超えた提案中ADRでCIを赤にする）** / 不採用: 決定2の理由の通り、
  正当な保留を罰し、内容を伴わない承認を誘発する。意味判定をERRORに載せる誤り。
- **案C: `status` フィールドを廃止し、mainにマージされていること＝承認とみなす** / 不採用: 「記録は
  するが決定はまだ」という正当な状態（`reservation-frontend/adr/0004`・`0005`）を表現できなくなる。
  また `superseded` の表現も status に依存している。
- **案D: 承認をGitHubのPR approve機能（レビュー承認）で表現し、frontmatterから承認情報を外す** /
  不採用: 承認の事実がリポジトリ外（GitHub API）にしか無くなり、`gh` を持たない読み手・将来の
  マイグレーションで失われる。統治文書は自己完結すべき（govlintが機械検証できる位置に置く）。
- **案E（採用）: 起草時に二択を明示させ（既定＝マージ＝承認）、滞留はREPORTで可視化する** / 採用:
  大半のADRを1PRで閉じて記録漏れの余地を消しつつ、正当な保留を表現する手段（(ii)）も残る。
  機械は可視化まで、判断は人間、という既存のREPORT設計と一貫する。

## 帰結

- 以後のADRは原則1本のPRで承認まで閉じる。frontmatterの記録漏れは構造的に起きなくなる。
- `提案中` が「意図して保留している」の意味を取り戻す。滞留はREPORTで毎回のCIに見える。
- 既存の提案中10本は残る。**特に `meta/adr/0024`（走破。承認済みの `0032` がこれを前提にしている）と
  `meta/adr/0026`（ブランチ運用・CI構成。`guardrails.md` がこれを根拠にしている）は、規程本体が
  すでに依存しているため優先度が高い**。個別の判断は人間に委ねる（決定3）。
- 本ADRはPRテンプレとgovlintを変更するが、**既存のADRファイルの status には一切触れない**。
- 併せて friction-log に FR を1件起票する（AIの見逃しが関与したため。`meta/permissions.md` の記録
  ルール）。cause_key は `record-update-needs-second-pr`。

## 確認事項（人間に確認されたい）

**meta層のfriction-logの置き場が無い。** 本FRはテンプレート自身の手順に関する摩擦だが、
`meta/tools/govlint.py` の `check_friction_logs()` は `projects/*/friction-log.md` しか走査せず、
`meta/friction-log.md` は存在しない。先例（FR-010: HANDOFF.md、FR-012: ルートREADME/activeContext は
いずれもmeta層の摩擦）に倣い `projects/reservation-system/friction-log.md` に置いたが、これは
ADR-0033 が activeContext について解いたのと同じ「meta層の状態がプロジェクト配下に間借りしている」
構図である。`meta/friction-log.md` を新設すべきかは本ADRでは決めない（P-02）。
