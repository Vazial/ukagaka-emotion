# ADR-0011: orchestratorのディスパッチは routing に限り、実質的内容を注入しない

## 文脈

スライスRSV-Aの契約起草をarchitectにディスパッチする際、orchestratorがプロンプトに「読み取りモデルはイベントを生まない・べき等」「空き枠はキャンセル済みを除外する（部分排他制約の読み取り版）」といったドメイン・設計上の実質的内容を書き込んだ。人間から「orchestratorがアドリブで指示を出すのはやめたほうがいい。明文化されずルーチン化されない」との指摘。

この注入は3つの問題を持つ:
1. **非ルーチン・非バージョン管理**: プロンプトはその場限りで消える。同じ指示が次回も出る保証がなく、品質がorchestratorの記憶に依存する（P-04違反: ルール化できるものを成文化していない）
2. **FR-006と同型**: seam仕様のorchestrator言い換えが劣化点だった件と同じ構造。orchestratorが実質的内容の出所になると、そこが劣化・バイアスの点になる
3. **独立導出の短絡**: architectに答え（キャンセル済み除外）を手渡すと、「ワーク素材から自力で導出したか」が検証不能になる。tester/reviewer分離が防ぐ「誤解の自己申告」と同じ失敗を、orchestrator自身が持ち込む

これまでorchestrator自身の制約はどの規程にも明文化されていなかった（4agentには役割定義があるが、束ねる役の枠が無い）。

## 決定

orchestratorのディスパッチ・プロンプトは以下に限る:
1. **タスクの同定**（どのスライス／タスクか）
2. **読むべき成文ソースの指定**（PRINCIPLES.md／役割定義／activeContext.md／契約／ADR／ワーク素材／テストインフラ契約 等、既にある文書への参照）
3. **産出物の指定**（何を出力するか）
4. **既存ルールの発動**（例: 「ADR-0009に従い直前スライスの申し送りを確認せよ」）

ドメインルール・設計制約・解釈・答えといった**実質的内容を注入してはならない**。注入したくなったら、それは成文ソースに欠けているサインである。まず該当ソース（役割定義／ADR／契約／activeContext）に足し、agentにはそれを読ませる。新規のドメイン判断が要るなら人間に回す（勝手に決めてプロンプトに書かない）。

## 検討した代替案

- 案A: 現状維持（必要に応じてプロンプトで補足する） / 不採用: 上記3問題。特に独立導出の短絡は保証設計の根幹を崩す
- 案B: orchestratorにも4agent同様の完全な役割定義ファイルを作る / 部分採用: 本ADRとmeta/agents.mdへの節追加がその第一歩。フルな定義ファイルは必要が生じてから（P-05: 予防的に書き溜めない）

## 帰結

- meta/agents.md に「orchestratorの制約」節を追加する
- 本ルールの初適用として、RSV-Aのarchitect起草をやり直す。orchestratorが実質指示を注入した最初のドラフトは破棄し、routingのみのプロンプトで再起草する。これにより「architectが成文ソースだけからドメインルールを自力導出できるか」も同時に検証される
- FR-009として記録
- 副次的に、この検証は「成文ソース（ワーク素材・既存契約・ADR）が、agentが自力導出するのに十分な情報を持っているか」のテストにもなる。導出に失敗したら、それはソースの不足であり、そちらを強化する（P-10）
