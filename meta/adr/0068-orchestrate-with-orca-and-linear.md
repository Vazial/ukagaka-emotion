# ADR-0068: やることはLinearに置き、Claude Sonnetが指揮してCodex Lunaに実装させる

> **承認者向けサマリ**
>
> 人間は毎日の監査より、作り込みと仕様のブレストに時間を使いたい。そこで Linear（課題管理サービス）と
> Orca（複数のAIを作業場所ごとに走らせる道具）で回す形に移ることを、2026-09-26 に決めていた。
> ところがテンプレの決まりごとは、人間がチャットで毎回つき合う前提のままだった。
> とくに Codex は「着手前に毎回チャットで範囲を合意する」決まりがあり、無人では1歩も進めない。
>
> 決定は6点。
>
> 1. 作る前のもの（アイデア・やること・順番・状態）は Linear に置き、リポジトリには決まったものと作ったものを置く
> 2. Linear の状態とラベルの意味を固定する
> 3. 役割ごとの既定の実行先を決める。指揮・仕様・監査は Claude Sonnet、実装とテストは Codex Luna、画面は Claude Opus
> 4. 指揮は Orca の監督付き起動で行う。1チケット＝1作業場所＝1回の指揮
> 5. 人間がチケットを「やる」へ移したことを、実装の範囲の合意とみなす。AIはDraft PRまで聞かずに進める
> 6. 無人の自動実行は朝と夜の2本。どちらも1チケットずつやり切る
>
> 払うもの: 範囲の合意がチャットからチケットの文面へ移るので、チケットを書く質がそのまま作業の質になる。

## 文脈

2026-09-26、人間はテンプレと派生リポジトリの進め方を作り直すと決め、Linear のチケット KEN-5 に決定を書いた。
要点は次の4つである。

- 契約は Claude・Codex とも月20ドル級。上限は使用量で決まる
- 置き場は2つ。Linear は作る前のもの、リポジトリは決まったものと作ったもの
- Orca のボードは置き場にせず、Linear のチケットを見る窓として使う
- 役割は Codex が実装、Claude が判断・仕様・アイデア出し

2026-09-27、人間は「現状の構成に合わせてテンプレを改善したい。うまく指揮できるなら設定してほしい」と依頼した。
あわせて「Sonnet が指示、Luna が実行」という分担を挙げた。

テンプレ側には、これと噛み合わない決まりが3つ残っていた。

- Codex は新しい作業に入る前に、チャットで範囲を合意して返事を待つ（ADR-0030）。夜の無人実行では誰も返事をしない
- 役割とモデルの対応表（`meta/agent-runtime-mapping.md`）は、Claude で回すときと Codex で回すときを別々に書いていた。1つの作業の中で両方を混ぜる書き方が無かった
- 「次にやること」は各プロジェクトの activeContext（いま何が決まり、どこまで進んだかを書くファイル）が持っていた。Linear に同じ一覧を置くと二重になる

Orca には、指揮役の AI が別の AI を監督付きで起動する仕組みがある。
起動時にモデルを指定でき、完了報告（成功か失敗か）を受け取って次を決められる。
これを使えば、Claude が指揮し Codex が手を動かす形をそのまま組める。

## 決定

### 1. 置き場を2つに分ける

- Linear: アイデア・やること・順番・状態。ブレストの結果はチケットの説明欄に書く
- リポジトリ: 仕様・ADR・契約・コード。つまり決まったものと作ったもの
- activeContext は「何が決まったか・いまの作業がどこまで進んだか」だけにする。次にやることの一覧と順番は Linear が持ち、activeContext にはチケット番号だけを書く
- Orca のボードは状態を持たない。カードの表示名はチケット名にし、状態は Linear 側で動かす

### 2. Linear の状態とラベルの意味

既存の状態名を改名せず、意味だけを固定する。

| Linear の状態 | 意味 |
|---|---|
| Backlog | 未整理。アイデアや思いつき |
| Todo | やる。人間が範囲を読んで、着手してよいと決めたもの（決定5） |
| In Progress | 作業中。作業場所がある |
| In Review | Draft PR を出した。人間の確認待ち |
| Done | マージ済み |

ラベルは「アイデア」（ブレストの対象）と、既存の Feature・Bug・Improvement を使う。

### 3. 役割ごとの既定の実行先

| 役割 | 既定の実行先 |
|---|---|
| 指揮役（orchestrator） | Claude Sonnet |
| architect（契約・設計） | Claude Sonnet |
| designer（画面） | Claude Opus |
| developer（実装） | Codex Luna |
| tester（受け入れテスト） | Codex Luna |
| reviewer（テストの監査） | Claude Sonnet |

役割の中身（何をして何をしないか）は変えない。変わるのは、どの AI で起動するかの既定だけである。

tester と reviewer が別の会社の AI になる点を意図している。
reviewer はテストを書いた側の意図を知らされずにコードだけを読んで監査する（`meta/agents.md` §3）。
学習元の違う AI が監査すると、同じ誤解を共有しにくくなる。

Codex だけで回すときの対応（Terra・Sol を含む元の表）は残す。指揮役が Codex のときはそちらを使う。

### 4. 指揮は Orca の監督付き起動で行う

- 1チケット＝1作業場所（git の worktree）＝1回の指揮（Orca の Run）
- 指揮役は `orca orchestration worker-start` で役割を起動し、モデルを決定3の表どおりに指定する
- 起動時の指示に書いてよいのは、これまでどおり routing（どのチケットか・読む文書・作るもの・既存ルールの発動）だけである（ADR-0011）。Orca が推す指示の5項目は、この範囲で埋める
- developer と tester は別々の起動にし、互いの文脈を渡さない
- 指定したモデルが使えないときは、黙って別のモデルに替えない。チケットにコメントを残して止まる

### 5. 「やる」に移したことを範囲の合意とみなす

- 人間がチケットを Todo へ移した時点で、そのチケットの説明欄が実装の範囲の合意になる
- AI はチャットの返事を待たずに Draft PR まで進めてよい。これは Codex のチャット先行の合意（ADR-0030）の代わりになる
- チケットに書いていない判断が出たら、進めずに止まる。問いはチケットのコメントに、判断を仰ぐ型（決めること・選択肢・トレードオフ・推奨）で書く
- 人間の承認点は変わらない。契約・設計骨格・step 実装・規程の変更は、Draft PR にしたうえでチャットで合意を取る
- マージは人間が行う

### 6. 無人の自動実行は朝と夜の2本

- 朝: Claude が「アイデア」ラベルのチケットを読み、論点と選択肢をコメントに書く。リポジトリは触らない
- 夜: Claude が指揮役になり、In Progress があればその続きを、無ければ Todo の先頭を1つ取る。役割を起動して Draft PR まで進める
- 並行しない。1チケットを Draft PR までやり切ってから次へ進む
- チケットは1回の使用量の上限内で終わる大きさに切る

手順と起動の文面は `meta/orchestration.md` に置く。

## 検討した代替案

- 実装だけ Codex、テストも Claude / 不採用の理由: tester と reviewer が同じ Claude になり、決定3の独立性が弱まる。Claude の使用量も判断以外に食われる
- 仕様・監査も Codex の上位モデルに寄せる / 不採用の理由: 指揮役と仕様の担当が別の AI になり、行き来が増える。Claude の使用量は最小になるが、判断を Claude に寄せるという 2026-09-26 の方針に反する
- 無人でもチャットで毎回確認する（現状維持） / 不採用の理由: 夜の自動実行が着手できずに止まる
- 作業場所を作ってコミットまで、PR は人間が見てから / 不採用の理由: 朝の手間が増える。Draft PR はマージされないので、外に出る危険は小さい
- Linear の状態名を日本語に改名する / 不採用の理由: 改名は Linear の設定画面の操作が要り、AI が使う名前と人間が見る名前がずれる期間が生まれる。意味を固定すれば足りる
- 先に派生リポジトリ1本で試してからテンプレに入れる（KEN-5 の当初の順番） / 不採用の理由: 人間がテンプレへ入れることを先に依頼した。効かなければ新しい ADR で覆す（P-06）

## 帰結

- Codex は、チャットが無くても着手できる。範囲はチケットの文面が決める
- activeContext から「次にやること」の一覧が抜け、短く保ちやすくなる。既存プロジェクトの activeContext は、次にそのプロジェクトを触るときに合わせる
- 無人で走る分、止まる理由がチケットのコメントに溜まる。人間は朝にそこを見る
- Claude の自動実行でモデルを Sonnet に固定する手段は、Orca の自動実行の設定には無い。Orca 側で Claude の既定モデルを Sonnet にしておく必要がある（人間の作業）
- 後退条件: 1〜2週間回して、チケットの文面が足りずに止まった回数と、使用量の上限で止まった回数を数える。前者が多ければ決定5を、後者が多ければ決定3かプランを見直す
