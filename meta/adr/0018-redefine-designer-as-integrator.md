# ADR-0018: designer役を「発案者」から「design integrator（外部設計の統合役）」へ再定義する

## 文脈

ADR-0017でagent役割designerを新設し、architectと並行してUI/UXモックを「起こす」役割（発案者）と位置
づけた。reservation-frontendでの実地適用（RFE-A画面設計）で、内部AI（designer, model: opus）による
UI/UX発案が2回にわたり実用水準に届かなかった（人間評価:「デザイン以前の問題」。記録: projects/
reservation-frontend/friction-log.md FR-001）。一方、同じユースケースを人間が外部AI（Gemini）に依頼
したところ、タイムライン・ダッシュボード＋クリック予約＋自分の予約管理という画面設計が実用水準に到達
し、スパイクでの実動作確認にも至った。

この実証から得られた学び: **本テンプレートの「機械化された正しさ」は、正しさが規則で定義できるバック
エンド（契約・シナリオ・API仕様の整合）では機能するが、フロントエンドのプロダクト/UX品質は"発案"を
要し、それはAIエージェント単独では弱い。外部AIによる発案＋パイプラインによる取り込みが有効である**。

人間はこの学びに基づき、designer役を再定義することを決定した。本ADRはこの決定を明文化し、**ADR-0017を
supersedeする**（P-06: 決定は更新せず、新しい決定で置き換える）。ADR-0017が確立した以下の要素は、本ADR
でも維持・引き継ぐ: agent役割designerの存在そのもの、architectとの並行モデル（同じユースケースから
同時に着手する構図）、視覚の土台を採用済みデザインシステムに載せる原則（reservation-frontendでは
shadcn/ui、projects/reservation-frontend/adr/0005）、洗練フェーズ（refinementループ）とescape hatch
を持つという原則。**変わるのはdesignerが何を"する"か——発案者から統合役へ**。

## 決定

designer役を、**「発案者（originator）」から「design integrator（外部設計の統合役）」へ再定義する**。
役割（agent）としてのdesignerは存続する。担う作業の中身が変わる。

### 責務（改訂）

designerはUI/UXデザインを自ら発案しない。代わりに、次の(a)〜(d)を担う:

**(a) デザインブリーフの作成**: ユースケース・契約（ドラフト含む）から、外部AIへの発注書に相当する
デザインブリーフを書く。ブリーフには、対象ユースケース、契約が定める入出力（API仕様・シナリオの
`Then`が要求する状態）、採用済みデザインシステム（shadcn/ui等）の指定、忠実度・除外事項（プロジェクト
のモック承認プロセスADRに従う）を含める。

**(b) 外部AIによる画面設計の実行**: 外部AI（Gemini等）にブリーフを渡し、画面設計を作らせる。**当面は
人間がこの実行を担う**（design系のMCP/CLIコネクタは現存せず、orchestratorがローカルCLI・登録済み
コネクタを確認した結果不在と確認済み）。人間がブリーフを外部AIに渡し、結果を持ち帰ってdesignerに戻す、
という人間-in-the-loopの構成を正直に記録する。将来、外部AIを直接呼び出せるコネクタが登場すれば、
designerが直接実行する形に移行しうる（本ADRの決定はその移行を妨げない）。

**(c) 突き合わせ（reconciliation）**: 外部AIから返ってきた設計を、契約・ドメインと突き合わせる。
必要な新API・契約とのズレ（例: 一覧取得APIの欠如、フィールド名の不一致等）を洗い出し、architectと
共有した上でエスカレーションする（下記「持たないもの」・permissions.mdのプロトコルに従う）。

**(d) 仕上げ**: 突き合わせを経た設計を、承認可能なモック/仕様に仕上げる（レンダリング・静的モック化を
含む）。プロジェクトのモック承認プロセスADR（例: projects/reservation-frontend/adr/0004）が定める
忠実度・形式に従う。仕上げの過程で採用済みデザインシステムへの適合（近似）を行う（projects/
reservation-frontend/adr/0005のようなプロジェクト決定を踏襲する）。

### 持たないもの（保証のための分離。維持＋追加）
1. 出荷実装コードを書かない
2. 契約・シナリオを変更しない（矛盾を検知したらエスカレーション。permissions.mdのプロトコルに従う）
3. **実装コード（src/）を読まない**（実装都合にデザインが引きずられるのを防ぐ）
4. **（新規）UI/UXデザインを自ら発案しない**。外部AIの成果物を統合・仕上げすることに徹する。発案が
   必要な局面（外部AIの結果が無い、ブリーフだけでは足りない等）は、ブリーフの改訂または人間への
   エスカレーションで対応し、designer自身が発案で埋めない

### 読むもの（維持＋追加）
1. meta/PRINCIPLES.md（信条）
2. 自分の役割定義
3. activeContext.md（現在の状態）
4. 対象スライスの契約・受け入れシナリオ、API契約 — ドラフト（承認前）を含む。読み取り専用
5. **（新規）外部AIが作成した画面設計の持ち帰り成果物**（人間経由で受け取る）

### ツール・モデルの再考

tools: Read, Grep, Glob, Write（変更なし。実装コードは書けない）

**model**: これまでの`opus`指定は「発案の質」を根拠にしていた（ADR-0017「他4agentはsonnetのまま、
designerのみopus」）。しかし本ADRにより、designerの中心作業はブリーフ作成・reconciliation（契約との
突き合わせ）・仕上げ（既存の外部設計を承認可能な形に整形）であり、**発案そのものはもう担わない**。
これらの作業は、architect（契約・モデルの整合性チェック）やreviewer（コードだけを読んで対訳表を書く）
と同種の、指示に忠実な変換・照合作業に近い。

**判断: `model: opus`を維持する**。理由:
- ブリーフの質（外部AIへの発注書としての明確さ・完全性）は、外部AI側の出力品質を直接左右する。ここで
  弱いモデルを使うと、"発案の弱さ"を"ブリーフの弱さ"として温存したまま外部AIに転嫁するだけになり、
  今回の学び（発案は外部AI・統合はdesigner）の効果を減殺するリスクがある
- reconciliation（契約とのズレの洗い出し）は、UI要求と契約仕様という異なる語彙を突き合わせる作業で
  あり、誤読のコストが高い（見逃すと室×時間帯のような不変条件に相当するAPI欠落を見落とす）
- コスト最適化は、発案という最も難しい仕事を外部AIに移したことで既に実現されている（内部AIのopus
  呼び出し回数・試行回数そのものは減る見込み）。役割内でさらにsonnetへ下げる根拠は薄いと判断した

この判断はarchitectが行ったものであり、人間が別途モデル選定を確定させたい場合は差し戻しできる
（reservation-frontend/activeContext.mdに確認事項として記録する）。

### escape hatchの読み替え

プロジェクトのモック承認プロセスADR（例: projects/reservation-frontend/adr/0004 §6）が定める
escape hatch（洗練をN回重ねても実用水準に届かない場合の代案）は、旧ADR-0017では「(a)既製UIテンプレート
採用／(b)人間・外部デザインを入力にしてdesignerは整形のみ／(c)視覚の野心を下げる」という3代案を挙げて
いた。**外部AIによる発案が主になった本ADRの下では、旧(b)がデフォルトの運用そのものになる**ため、
escape hatchの意味を次のように読み替える:

- 旧: 内部AI（designer）の発案が実用水準に届かない → 外部（人間・外部デザイン）に切り替える
- 新: **外部AIの発案が実用水準に届かない → (i)デザインブリーフを改訂して外部AIに再依頼する、または
  (ii)別の外部ツール・外部AIに切り替える**

旧代案(a)既製UIテンプレート採用・(c)視覚の野心を下げる、は選択肢として残る（外部AIの発案がなお実用
水準に届かない場合の最終手段として）。具体的な反復回数N・代案の優先順位は、引き続きプロジェクト側
（例: projects/reservation-frontend/adr/0004 §6）が定める。本ADRは読み替えの原則のみを定める。

### 並行モデル・デザインシステム原則の扱い

ADR-0017が定めた並行モデル（architectとdesignerがユースケースから同時に着手する構図）と、視覚の土台を
採用済みデザインシステムに載せる原則は、**維持する**。ただしdesignerの「並行して起こす」作業の中身は、
本ADRの(a)〜(d)に置き換わる。デザインシステム（reservation-frontendではshadcn/ui、projects/
reservation-frontend/adr/0005）は不変: 外部AIはこの土台の上で設計し、designerの仕上げモックもこれに
従う（外部AIへのブリーフに、採用済みデザインシステムの指定を含めることで担保する）。

### 承認（維持）
既存の「設計骨格」承認点（permissions.md）に相乗りする。新しい5つ目の承認カテゴリは作らない。

## 検討した代替案

- 案A: designerの発案能力向上のため、モデル・プロンプトを調整して内製発案を継続する / 不採用: 
  reservation-frontendで内部AI発案が2回にわたり実用水準に届かなかった実証がある（FR-001）。人間評価は
  「デザイン以前の問題」であり、プロンプト・モデル調整で埋まる差ではないと人間が判断した
- 案B: フロントエンドのUX設計そのものをテンプレートの保証対象から外す（L5＝人間の聖域に完全に委ねる） 
  / 不採用: 外部AIによる発案が実用水準に到達した実例（Gemini、タイムライン・ダッシュボード設計）が
  あり、"発案+パイプライン統合"という形でテンプレートに組み込む余地がある。設計プロセスから完全に
  手を引く必要はない
- 案C: 外部AI連携を今すぐ自動化する（コネクタ・API経由） / 不採用: design系のMCP/CLIコネクタは現存
  しない（orchestrator確認済み）。無い物を前提にした設計は現時点でできない。人間-in-the-loopを正直に
  記録し、コネクタが登場した時点で移行する
- 案D: designerのmodelをsonnetに下げる（発案を担わなくなったため） / 不採用: ブリーフの質・
  reconciliationの精度が下流の外部AI成果物の質を左右するため、現時点ではopusを維持する（詳細は
  「ツール・モデルの再考」参照）。人間が別途判断したい場合は差し戻し可能

## 帰結

- .claude/agents/designer.md・meta/agents/designer.mdを、(a)〜(d)の責務・「UI/UXデザインを自ら発案
  しない」禁止事項・外部AI成果物の読み取りを反映する形に改訂する
- meta/agents.md §2（designer行の役割説明を統合役に更新）・§4（標準フローの「設計」ステップを
  「ブリーフ作成→外部AI実行（人間-in-the-loop）→reconciliation→仕上げ」の4段に更新）を改訂する
- プロジェクト側のモック承認プロセスADR（例: projects/reservation-frontend/adr/0004）は、§6
  escape hatchの読み替え（外部AIへのブリーフ改訂／別ツール切替を第一の代案とする）を反映する必要が
  ある（本ADRはそれを代替しない。プロジェクト側で別途改訂する）
- reservation-frontendでは、今回の学びの直接の発端であるGemini設計（タイムライン・ダッシュボード＋
  クリック予約＋自分の予約管理）が、次のフロント設計の出発点になる。この設計が要求する新API・契約
  とのズレ（会議室一覧・占有タイムライン・自分の予約一覧の取得、会議名・氏名等のフィールド）は、
  reconciliationの最初の実例として、プロジェクト側activeContext.mdに記録する（本ADRでは決定しない）
- friction-log: 内部AI発案の限界という学びは、projects/reservation-frontend/friction-log.md FR-001
  として記録した（found_at: 人間、cause_key: agent-ui-ux-origination-weak）。本ADRはFR-001の
  「押し込み先」に該当する
