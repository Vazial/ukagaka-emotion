# ADR-0055: 摩擦の収穫はPRを作る直前に走らせ、繰り返しの検出は横断で別に見る

> **承認者向けサマリ**
>
> `meta/adr/0049` が摩擦の収穫の仕組みを決め、その決定4でトリガを「PRのマージ」とした。
> 運用に入れる前に実データで確かめたところ、**このトリガはほとんど発火しない**。ログ全体で
> `gh pr merge` が打たれたのは12回で、GitHub上でマージされたPRは118本ある。カバー率は約10%
> で、残りは人間がGitHubの画面で押している。**AIが行う操作ではなく人間が行う操作にhookを
> 付けていた**、というのが誤りの中身である。
>
> あわせて、マージ後というタイミング自体にも害があった。マージ後にはPRが閉じているので、
> 摩擦を記録するには新しいPRが要る。それは台帳で最も多く再発している摩擦
> （`record-update-needs-second-pr`、7回）そのものであり、**収穫の仕組みがその摩擦を自ら
> 生み出す**構造になっていた。
>
> 決定は3点。
>
> 1. トリガを「PRを作る直前」に移す。`gh pr create` は30日間で98回打たれており、定着した
>    操作である。PRはまだ開いているので、起票しても2本目のPRは要らない
> 2. 収穫の範囲をそのセッションだけにする。振り返りの単位が「今回のスライス」になり、
>    収穫位置を覚えておくファイルが不要になる
> 3. 繰り返しの検出は別モード（横断）として持ち、自動では走らせない。1セッションの中では
>    見えない層があり、そこにしか現れない欠陥が実際にあった
>
> 払うもの: PRを作らないセッションは自動では拾われない。手動の総ざらい（`--all`）が残る。

## 文脈

### 1. トリガが、実際にマージする人に付いていなかった

`meta/adr/0049` の決定4は、収穫のトリガをPRのマージとした。「スライスが閉じる瞬間」という
直感で選んだもので、**誰がその操作を行うかを確かめていなかった**。

正規化インデックス（同ADR決定8）で数えると、こうなっていた。

| | 回数 | 実施日 |
|---|---:|---|
| `gh pr create` | 98 | 30日 |
| `gh pr merge` | 12 | 1日 |
| GitHub上のPR総数 | 127 | — |

マージの12回はすべて同じ日に集中していて、習慣として定着してもいない。**PRのマージは主に
人間がGitHubの画面で行う操作**であり、そこにClaude Codeのhookは存在しない。

### 2. マージ後というタイミングには、それ自体に害があった

収穫が候補を出したあと、それを台帳に書くには次の道筋を通る。

- **マージ後に走らせた場合**: PRは閉じている。記録のために**新しいPRが要る**
- **PR作成前に走らせた場合**: PRはこれから作られる。記録は同じブランチへのコミットで済む

前者は `record-update-needs-second-pr` という cause_key で台帳に7回記録されている摩擦であり、
`meta/adr/0035`・`0043` が仕組みで塞ごうとしたにもかかわらず、その後も3回再発している最多の
原因である。**収穫の仕組みが、このリポジトリで最も多い摩擦を自ら作り出す設計になっていた。**

### 3. 「今のセッションを振り返る」と範囲を決めると、状態が消える

決定4のもとでは、どこまで収穫したかを覚えておくファイル（`.claude/harvest-state.json`）が
必要だった。これはチェックアウトごとに1つ存在するため、worktreeを複数使うと収穫位置が分裂
する。実際、運用開始時点でどのworktreeにも存在していなかった。

範囲を「PRを作ろうとしている、今のセッション」に限ると、この状態は**まるごと不要**になる。
hookのペイロードに `session_id` が渡るので、範囲は毎回そこから決まる。

### 4. 1セッションの中では見えない層がある

範囲をセッションに限ると、失うものがある。**同じ原因が別々のセッションに1回ずつ現れる場合、
どのセッションから見ても「たまたま起きたこと」にしか見えない。**

実データで確かめると、これは仮定ではなかった。

| 原因 | 跨ったセッション | 回数 | 出た役割 |
|---|---:|---:|---|
| `File does not exist. Note: your current working directory is` | 14 | 124 | architect / designer / developer / tester |
| `Exit code 1` | 18 | 59 | developer / tester |
| `<tool_use_error>File has not been read yet.` | 8 | 18 | developer / reviewer / tester |

1番目は6週間で124回起きているにもかかわらず、**台帳51件のどこにも記録されていなかった**。
役割agentが自分の作業ディレクトリを見失う、という系統的な欠陥である
（`projects/dining-radar/friction-log.md` の `FR-021` として起票した）。

`meta/adr/0012` は「同じ cause_key が2回出たら構造的欠陥」と定めている。その判定に必要なのは
**回数ではなくセッション数**であり、セッション内スコープでは原理的に計算できない。

## 決定

### 決定1. 収穫のトリガを、PRを作る直前に移す

`meta/adr/0049` 決定4（トリガはPRのマージ）を、本決定で置き換える。

`PreToolUse` hook を `Bash(gh pr create*)` に付ける。`PreToolUse` は `additionalContext` を
返せるので、PRの本文を組み立てている最中のAIに候補が届く。

振り返りは終わるときに行うものであり、始めるときではない。そしてPRの作成は、このリポジトリに
おいて「スライスを閉じて何が起きたかをまとめる」唯一の儀式である。`friction-log` の更新が
DoDに載っているのもその瞬間である。**収穫は、その儀式の直前に置く。**

hookの `if` フィルタだけを信用しない。バッククォートで囲まれた文字列はコマンド置換として
解析されて `if` に一致するため（クォート付きheredocの中でも同じ。`meta/adr/0049` の実測）、
呼ばれた側でコマンド文字列を再検査する。

**その再検査も、一度は不十分だった。** 本ADRを書いたコミット自身が旧hookを誤発火させている。
コミットメッセージを heredoc で渡しており、その本文の「`  gh pr merge    12回 / 1日`」という
行が、行を区切り文字として扱う再検査からはコマンドに見えた。heredoc の本文は人間が書いた
文章であってコマンドではないので、判定の前に落とす。

### 決定2. 収穫の範囲は、そのセッションだけにする

hookのペイロードの `session_id` で範囲を決める。範囲が決められないときは**黙る**——全期間を
出すと、締めに入っている作業の邪魔になるだけである。

収穫位置を覚えておくファイルは廃止する。同じセッションで複数のPRを作ると同じ候補が再び出るが、
未対応の摩擦が出続けること自体は正しい挙動なので、実際に困るまで対処しない（P-05）。

### 決定3. 繰り返しの検出は横断モードとして持ち、自動では走らせない

`--recurring` で、同じエラーが何セッションに跨ったかを数える。**セッション数の多い順**に並べる
——`meta/adr/0012` が構造的欠陥の指標としているのは回数ではなく再発だからである。

hookにはしない。毎回見るものではないし、締めの邪魔になる。**回すのは人間が振り返りたいとき、
または週次のルーティンから**である。ルーティンの登録先は各自の環境（`~/.claude/scheduled-tasks/`）
であり、リポジトリには置かない——`meta/adr/0049` 決定8がインデックスの置き場について下した
判断と同じ理由で、個人環境に属する設定だからである。

## 帰結

- **得るもの**: トリガのカバー率が約10%から、Claudeが作るPRのほぼ全部になる。起票が同じPRで
  閉じるようになり、収穫の仕組みが `record-update-needs-second-pr` を生まなくなる。収穫位置の
  状態ファイルが消え、worktreeごとの分裂も消える。そして横断モードが、1セッションでは
  原理的に見えなかった層を可視化する（実際に124回の未記録欠陥が出た）
- **払うもの**: PRを作らないセッション（探索・雑務）は自動では拾われない。`--all` の手動実行が
  受け皿として残る
- **効かない範囲**: `.claude/settings.json` はClaude Codeの機構であり、Codexには届かない
  （`activeContext` の既知の穴）。Codexが作るPRは対象外である
- **弱点として残るもの**: 候補が届くのは、AIが作業を畳もうとしている瞬間である。形式的に流される
  可能性は仕組みでは消せない。`PreToolUse` はPR作成をブロックすることもできるが、硬いゲートは
  採らない——**縛りを増やすと、言われたことしかしなくなる**という人間の明示的な判断による。
  代わりにPRテンプレートに確認欄を1つ置くに留める
