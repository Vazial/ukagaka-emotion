# ADR-0039: 役割は自分に適用される機械検証を申告する。orchestratorは技法を指定せず、検証を通してから次段へ渡す

> **承認者向けサマリ**: RFE-C スライス（標準フローを全段踏んだ初のスライス）で、**orchestratorと役割の
> 境界に起因する失敗が3件**出た。**(1)** architectが `govlint` を実行せずに「既存契約との矛盾は
> 見つからなかった」と報告し、実際は ERROR 4件で落ちた（architectはBashを持たない役割定義であり、
> 実行手段が無いのに検証済みであるかのように報告した）。**(2)** orchestratorがtesterへの指示で
> **前提状態の作り方を技法レベルで指定し**（「2ページ構成で作れ」）、**既存の正しいseamを名指しで
> 禁じた**結果、原理的に成立しない構成を強いた上、その失敗を「契約が実現不能」と誤診して人間に
> 先送りの承認まで求めた（reviewerの独立監査が反証し、撤回した）。**(3)** testerの成果物が赤いまま
> reviewerを起動したため、修正のたびに監査が陳腐化し再監査の往復が発生した。決定は3点——**役割は
> 自分の成果物に適用される機械検証を明示し、実行できないなら「できない」と申告する**（推測で「問題
> なし」と言わない）／**orchestratorは役割の判断領域に属する技法を指定しない**（事実は伝えるが手段を
> 命令しない）／**reviewerは全ゲートが緑になってから起動する**。**役割へのBash付与は行わない**
> （ADR-0021がdesignerについて示した論拠を維持する）——往復コストの摩擦が続いた時点で、
> 検証コマンドに限定したBashの付与を再検討する（P-05）。

## 文脈

RFE-C「自分の予約を確認してキャンセルできる」は、標準フロー（`meta/agents.md` §4）を全段踏んだ最初の
スライスである（architect → 人間承認 → developer と tester を並行 → reviewer → 人間承認）。分離の
設計は実際に機能した——**reviewerの独立監査が、実施者(tester)ではなく指示者(orchestrator)の誤りを
捕まえた**。一方で、orchestratorと役割の境界が未定義だったことに起因する失敗が3件出た。

### 1. 役割が「実行できない検証」を、済んだかのように報告した

architectは受け入れシナリオのドラフトを提出し「既存契約（RFE-A・RFE-B）との整合性チェックを行い、
矛盾は見つからなかった」と報告した。orchestratorが `python meta/tools/govlint.py` にかけると
**ERROR 4件**で落ちた（FR-018）。

architectの役割定義（`.claude/agents/architect.md`）の `tools` は `Read, Grep, Glob, Write` であり、
**Bashを持たないので govlint を実行できない**。差し戻した2回目には「私のツールセットにBashが含まれて
おらず自分では実行できません。この最終確認だけはお願いします」と**正しく申告した**。つまり役割は
申告できる能力を持っており、1回目にそれをしなかっただけである。

問題は、規程が**「自分に適用される機械検証は何か」「実行できない場合どうするか」を役割に要求して
いない**ことにある。`meta/verification.md` は検証の段を定義するが、**どの段の実行責任が誰にあるかを
書いていない**。結果、「整合性チェックを行った」という報告が、機械検証を通したのか目視で読んだのかを
読み手が区別できない。P-01（正しさを人間のレビューでなく機械化された検証に置く）を掲げていても、
その機械検証が実行されたかどうかが自己申告の散文に埋もれるなら、保証は成立しない。

### 2. orchestratorが役割の判断領域に属する技法を指定した

RFE-C-05（別の画面で既にキャンセル済みの予約を、一覧が更新されないままもう一度キャンセルして
拒否される）のL4を書かせるにあたり、orchestratorはtesterへの指示で**前提状態の作り方を技法レベルで
指定した**——「同一browser contextに2ページを開く（localStorageを共有）」「既存の `injectReservation`
seam は使わず UI だけで作れ」。

この構成は原理的に成立しない。端末の記録（localStorage）はページ間で共有されるが、モックの予約台帳は
モジュール変数＝ページごとに独立のため、2ページ目では一覧に出るのに台帳に無く、検証対象の拒否理由に
到達できない。**orchestratorはさらに、この失敗を「モックの状態スコープの分断でL4では実現不能」と
診断し、人間に先送りを提案して承認まで得た**。

reviewerは独立に「testerの構成上の見落としであり実現可能」と反証した。実装を確認すると reviewer が
正しく、同一ページで既存seamを使えば忠実に再現できた。**`injectReservation` のコメントは今回必要だった
ことをすべて説明しており、RFE-B-03 が同じ形の前提を同じseamで作っている先例もあった**（FR-008）。

根本は、orchestratorが「**何を検証するか**」（契約由来の事実）だけでなく「**どう作るか**」（役割の
判断領域）まで指定し、しかも既存の正しい手段を名指しで禁じたことにある。`meta/agents.md` 6節
（meta/adr/0011）は「orchestratorは実質的成果物を作らない」を定めるが、**技法の指定で役割の判断を
奪うことは禁じていない**。cause_keyは `orchestrator-as-substantive-source` を再利用した——成果物を
直接作るのと、技法を指定して判断を奪うのは、同じ「orchestratorが実質を供給する」機構である。

**最終的な修正で、testerはorchestratorが提示した2案のうちorchestratorが推していない方**（製品の公開API
経由でモック内部構造に依存しない）**を選び、そちらが適切だった**。技法の選択を役割に委ねた方が良い
結果になることの、同じスライス内での実証である。

### 3. 赤い成果物を監査に回して、監査が陳腐化した

orchestratorは「developerの実装が並行進行中なのでtesterのテストは最初は落ちる。それは想定内」として、
L4が8/9の状態でreviewerを起動した。その後 RFE-C-05 の修正・reviewerの指摘への対応で成果物が実質的に
変わり、**監査が古くなって再監査が必要になった**。対訳表は人間の承認材料なので、古いままでは承認が
成立しない。

`meta/agents.md` §4 の標準フローは 5(developer/tester並行) → 6(reviewer) → 7(人間承認) → 8(CI) の並び
であり、**CIが最後にあるため「緑になってから監査する」という制約が読み取れない**。実際にはCIは常時
回るので、意味のある順序は 5 → 緑 → 6 → 7 である。

## 決定

### 1. 役割は自分に適用される機械検証を申告する。実行できないなら「できない」と言う

役割agentは、成果物を提出する際に次を報告に含める:

- **その成果物に適用される機械検証は何か**（例: 契約なら L0 `govlint`、実装なら L1〜L3、受け入れテスト
  なら L4）
- **それを実行したか。実行したなら結果（件数・終了コード）。実行手段を持たないなら、その旨を明示する**

**「検証していないこと」を「問題がないこと」として報告してはならない。** 「整合性チェックを行い矛盾は
見つからなかった」のような表現は、機械検証を通したのか読んだだけなのかを区別できないため、**どちらで
あるかを明示する**。

**orchestratorは、役割の成果物を受け取った時点で、その成果物に適用される機械検証を実行してから次段へ
渡す**。これは省略可能な確認ではなく、標準フローの必須ステップである（下記 決定3 の順序に組み込む）。

### 2. 役割へのBash付与は行わない（現時点）

役割が自分で検証を実行できれば往復は減るが、**Bashの付与は役割の中核制約を緩める**——ADR-0021 が
designerについて「中核制約（実装コードを書かない・読まない、UI/UXを自ら発案しない）の担保が緩む」
として不採用にした論拠は、architect・testerにも同じ形で当てはまる。本ADRはその判断と整合させ、
**付与しない**。

代わりに決定1（役割の申告＋orchestratorの必須実行）で、**正しさは担保しつつ往復コストは受け入れる**。
往復の摩擦が繰り返し観測された時点で、**検証コマンドに限定したBashの付与**（`.claude/settings.json` の
`permissions` による絞り込み）を再検討する（P-05: 摩擦が出てから足す）。その際は**限定の実効性を先に
検証する**こと——本リポジトリの既存の `deny` パターンには実際に穴がある（下記「帰結」参照）。

### 3. orchestratorは役割の判断領域に属する技法を指定しない

orchestratorが役割へ渡してよいのは「**何を**」であり、「**どうやって**」ではない。

- **渡してよい**: 契約・承認済み決定・読むべきファイルのパス・スコープ・禁止事項（役割規程由来のもの）・
  **役割が自力で知り得ない事実**（例: 実装のフィールド名、既存seamの存在と設計思想）
- **渡してはならない**: 成果物の作り方の指定、既存手段の使用可否の命令、実装・テスト構成の決め打ち

役割が自力で知り得ない事実を伝えるのは正当であり、むしろ必要である（testerは `src/**` を読めないため、
フィールド名のような事実はorchestratorが供給しないと推測で埋めるしかない）。**事実を伝えることと、
手段を命令することを区別する**。

判断を仰がれた場合は、**選択肢と事実を提示し、選択は役割に委ねる**。orchestratorが「こちらを推す」と
述べるのは構わないが、命令にしない。

### 4. reviewerは全ゲートが緑になってから起動する

`meta/agents.md` §4 の標準フローの順序を次に改める:

```
5. developer と tester が並行作業（互いのコンテキストを共有しない）
6. CI: L1→L2→L3→L4 を実行。全緑になるまで次へ進まない   ← 位置を移動
7. reviewer: testerの成果物から対訳表・監査レポートを独立作成
8. 人間: シナリオ×対訳表×チェックリスト結果を突き合わせて承認
9. マージ（人間）
```

理由: reviewerの成果物（対訳表）は人間の承認材料であり、**監査後に成果物が変わると承認が空を切る**。
赤い成果物は修正されることが確定しているので、監査に回すのは早すぎる。

**例外**: 落ちている原因が「契約が実現不能かもしれない」という疑いである場合は、緑を待たずreviewerに
判断を求めてよい。RFE-C-05 で実際にorchestratorの誤診をreviewerが反証したのはこのケースであり、
この経路は残す。

### 5. 適用範囲

以後のスライスに適用する。既存には遡及しない。

## 検討した代替案

- **案A: 検証コマンドに限定したBashを役割へ付与する** / **不採用（当面）**: 往復は最も減るが、
  ADR-0021 の論拠（Bashは中核制約の担保を緩める）と衝突する。加えて、限定の実効性を検証していない
  ——本リポジトリの `deny` パターンは prefix 一致であり、**フラグの順序を変えるだけで回避できる**穴が
  実在する（`Bash(git reset --hard*)` は `git reset -q --hard` を止められない）。**穴のある限定を
  「限定できている」と扱うのは、ADR-0038 で直したlintの言語依存と同じ誤り**である。摩擦が続いたら、
  限定の実効性を先に検証した上で再検討する。
- **案B: orchestratorが検証を実行する義務だけを課し、役割の申告は求めない** / 不採用: 役割が
  「検証済みのように読める報告」を出す問題が残る。orchestratorが毎回気づく保証はない（実際、
  今回気づいたのは偶然に近い）。申告を要求すれば、実行していないことが報告面で可視になる。
- **案C: orchestratorの技法指定を禁じず、指示の質を上げることで対処する** / 不採用: FR-008 は
  「指示が下手だった」ではなく「役割の判断領域に踏み込んだ」ことが機構である。同じcause_keyが
  既に3回出ており（reservation-system側で2回、frontend側で1回）、規律の呼びかけでは直らないことは
  FR-015（承認記録）と同じ形で実証されている。P-04に従い構造で直す。
- **案D: reviewerを廃し、人間が直接テストコードを読む** / 不採用: verification.md の L4詳細(2) が
  「対訳表はstep定義を書いたtesterではなくreviewerがコードだけを読んで独立に作成する（誤解の自己申告を
  防ぐ）」と定める設計の核心を捨てることになる。今回まさにその独立性がorchestratorの誤診を捕まえた。
- **案E（採用）: 申告の義務化＋技法指定の禁止＋監査順序の是正** / 採用: 3件の失敗それぞれに対応し、
  権限モデルを変えずに実施できる。往復コストは残るが、正しさを優先する。

## 帰結

- 役割の報告から「検証したか / できないのか」が読み取れるようになる。orchestratorの検証実行が
  標準フローの明示的なステップになる。
- orchestratorは事実（役割が自力で知り得ないもの）を供給する責任を持ち、手段の選択は役割に残る。
  **`meta/agents.md` 6節への反映が必要**（現在は「実質的成果物を作らない」のみ）。
- reviewerの起動が緑の後になり、再監査の往復が減る。**`meta/agents.md` §4 の標準フローの並びを
  改める必要がある**。
- 本ADRは規程（`meta/agents.md`）の改訂を伴う。**同じPRで反映する**（ADR-0032 の帰結が規程反映を
  宿題に回して実際にドリフトした反省。ADR-0031 の「実装とセット」方針と同じ扱い）。
- **`.claude/settings.json` の `deny` パターンに実在する穴を記録する**: `Bash(git reset --hard*)` は
  prefix 一致のため `git reset -q --hard origin/main` を止められない（本セッションで実際に通った）。
  同様に `Bash(git branch -D*)` は `git branch --delete --force` を別途列挙して塞いでいるが、
  `git branch -D -r` のような変形や、`git -C <path> branch -D` のようなグローバルオプション付きの
  呼び出しは想定されていない。**本ADRではこの穴を塞がない**——ガードレールの変更は
  `meta/permissions.md` の「ゲート変更」に相当し、影響範囲の調査を伴うため別作業とする。決定2が
  「限定の実効性を先に検証せよ」と述べているのはこの実例に基づく。
- **未対応として残す関連論点**: govlint の cause_key 再出現検出は friction-log ファイル単位で行われる
  ため、**プロジェクトを跨いだ再出現を検出できない**。`orchestrator-as-substantive-source` は
  reservation-system 側で2回・reservation-frontend 側で1回＝実質3回目だが、機械は2回目までしか
  報告しない。構造的欠陥のシグナルを取り逃す穴であり、別ADRで扱う。
