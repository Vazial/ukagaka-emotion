# ADR-0062: 役割定義は「セッション」ではなく「作業ツリー」から読まれる（ADR-0059 決定1の訂正）

> **承認者向けサマリ**
>
> このリポジトリは、AIの役割（画面を設計する役、実装する役など）を `.claude/agents/` の下の
> ファイル1枚ずつで定義している。
>
> 前日、その定義を書き換えてもAIに届かない事故が起きた。原因を「定義はセッションを開いた時点で
> 読み込まれ、走っている間は更新されない」と診断し、対処として「定義を変えたらセッションを
> 開き直す」を規程に入れた（`meta/adr/0059` 決定1）。
>
> **この診断は間違っていた。** 翌日、同じセッションの中で役割を起動したところ、書き換えた後の
> 定義と道具が正しく渡った。定義は**起動のたびにディスクから読まれている**。
>
> 本当の原因は作業ツリーだった。このリポジトリは複数のセッションで同じ作業ツリーを共有しており、
> 事故のときツリーは別のブランチに乗っていて、ディスク上のファイルが古いままだった。証拠もある——
> 起動した役が「`meta/adr/0059` が見当たらない。最大番号は 0057 だ」と報告してきた。マージ済みの
> ADRが2本見えていない、つまり**古いツリーを読んでいた**。
>
> 決定は3点。
>
> 1. `meta/adr/0059` 決定1（セッションを開き直す）を撤回し、**作業ツリーがその定義を含んでいることを
>    確かめてから起動する**に置き換える
> 2. `meta/adr/0059` 決定2（役割agentが起動時に自分の道具立てを定義と突き合わせる）は**残す**。
>    原因が変わっても、この確認は古いツリーの場合も同じように効く
> 3. 役割agentを起動するときは、**その役が読むべき作業ツリーの場所を指示に書く**
>
> 払うもの: 起動のたびに作業ツリーの確認が1回増える。

## 文脈

### 1. 何が起きたか

2026-08-22、designer の役割定義を書き換える変更をマージした直後に designer を起動したところ、
書き換える前の定義と、書き換える前の道具の一覧が渡った。新しい定義は「`/design` という道具で画面を
作れ」と定めているのに、その道具が渡っていなかった。

このとき原因を「役割定義はセッションを開いた時点で読み込まれ、走っている間は更新されない」と診断し、
`meta/adr/0059` にそう記録した。対処として決定1（役割定義を変えるPRをマージしたら、その役を起動する前に
セッションを開き直す）を `meta/guardrails.md` に入れた。

### 2. 診断が間違っていたと分かった経緯

2026-08-23、**同じセッションのまま** designer を起動した。designer は7つの道具すべてを受け取り、
`/design` を自分で実行して成果物を発行した。セッションは開き直していない。

つまり役割定義は**起動のたびにディスクから読まれている**。セッション単位で固定されるという診断は
成り立たない。

### 3. 本当の原因

同じ起動で designer が別のことも報告した——「`meta/adr/0059` がリポジトリに見当たらない。`meta/adr/` の
最大番号は 0057 だ」。ところが 0058 と 0059 はどちらもマージ済みである。

作業ツリーを調べると、`meta/govlint-counts-adr-style` という別のブランチに乗っていた。このリポジトリは
複数のセッションが同じ作業ツリーを共有しており、他のセッションが別のブランチへ切り替えたまま作業して
いた。**designer はその古いツリーを読んでいた。**

事故のときも同じである。マージはGitHub上で完了していたが、ディスク上の `.claude/agents/designer.md` は
まだ古い版だった。だから古い道具の一覧が渡った——セッションが古かったのではなく、**ファイルが古かった**。

### 4. なぜ間違えたか

症状（旧定義・旧道具）とセッションの継続が同時に成立していたため、セッションを疑った。**ディスク上の
ファイルが実際に何であるかを確かめなかった**。確かめる方法はあった（`git log -1 -- .claude/agents/…` を
見る、ブランチを見る）。1回のコマンドで判明したはずである。

## 決定

1. **`meta/adr/0059` 決定1 を撤回する。** 「役割定義を変えるPRをマージしたら、その役を起動する前に
   セッションを開き直す」をやめ、**「作業ツリーがその定義を含んでいることを確かめてから起動する」**に
   置き換える。確認は `git log -1 --format=%h -- .claude/agents/<役>.md` と現在のブランチを見れば足りる。
   作業ツリーが他のセッションに使われていて古い場合は、**別の作業ツリーを切って**そちらを使う。

2. **`meta/adr/0059` 決定2 は残す。** 役割agentが起動時に自分に渡された道具を定義の `tools:` 行と
   突き合わせる確認は、原因が「古いツリー」に変わっても同じように効く。実際、事故を捕まえたのは
   この確認だった。

3. **役割agentを起動するときは、その役が読むべき作業ツリーの場所を指示に書く。** 既定の作業ツリーが
   他のセッションに占められていることは日常的に起きるので、起動側が明示する。

`meta/adr/0059` の決定3〜6（一過性のズレへの回避策を役割契約に書かない／機械検査は置かない／designer の
寸法は常に未実測／designer が実装コードの代わりに読むもの）は影響を受けず、そのまま有効である。
`meta/adr/0059` 本体は書き換えない（`meta/adr/0053` 決定4）。

## 帰結

- `meta/friction-log.md` の `FR-003` は誤った原因を記録している。訂正を追記する。
  cause_key を `role-definition-not-live-until-fresh-session` から
  `stale-working-tree-serves-old-definitions` へ改める。
- 「セッションを開き直す」ための中断が不要になる。
- 作業ツリーの共有そのものは解消していない。別のセッションが握っているツリーで作業を続けると、
  役割定義に限らず**あらゆるファイルが古く見える**。別の作業ツリーを切るのが確実な回避である。
