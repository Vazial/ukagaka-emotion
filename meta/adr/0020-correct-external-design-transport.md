# ADR-0020: designerの外部AI連携の伝送方式を訂正し、成果物形式・ブリーフ構成を精緻化する

## 文脈

ADR-0019は、designerの(b)外部AI実行をGemini CLI（`@google/gemini-cli`）のヘッドレス実行
（`gemini -p ... -o text --skip-trust`）で自動化すると規定した。**この規定は誤りだった**。

実測の結果:
- `@google/gemini-cli`は**エージェント型のコーディングCLI**（Claude Codeと同種）であり、「計画を
  立てて実装しにいく」道具である。デザインブリーフを渡すと、設計成果物ではなく**実装計画＋「進めて
  よいか」の確認**を返した（実際にそうなった。genericな部品リストのみで視覚的発想ゼロ）。**設計を
  委託する用途に適さない**
- 正しい伝送は**Generative Language APIの`generateContent`を直接呼ぶ**こと。エージェント的枠組みが
  一切入らない、純粋な「プロンプト→テキスト」の呼び出しであり、モデルも確実に指定できる。これに
  切り替えたところ、同じブリーフで実用水準の設計が返った（再現済み・複数モデルで確認）
- 傍証: 人間がGeminiアプリ（チャット）で試したところ、flash-liteでも十分な設計が返った。**モデルの
  問題ではなく伝送の問題**だったことを裏付ける

この事象はprojects/reservation-frontend/friction-log.md FR-003として記録した（原因の仮説: 「ツールが
動作すること」の確認と、「そのツールが目的に適した出力を返すこと」の確認は別の検証軸であり、ADR-0019
起草時は前者のみ確認して後者を確認しないまま規定してしまった）。

あわせて、今セッションでさらに3点が判明・決定された:

1. **成果物の形式**: 自己完結HTML（CDN版）はレビューには忠実だが実装スタックとは別物であり、実装時に
   人間が翻訳する過程で**デザインが変容する**リスクがある。実プロジェクトの「受け皿」でTSXとして描画
   すれば、レビューした絵がそのまま実装の出発点になる
2. **ブリーフ構成の精緻化**: 「型が複雑すぎる。欲しいのは画面のソースだけで、ほかはarchitectの責務」
   という指摘。「リッチ＝網羅」ではなく、外部AIにしか出せないもの（画面）に出力予算を集中させ、
   architectの領分（契約の精度・エッジケース網羅・API設計）はブリーフに載せないほうがよい
3. **無料枠の実測の精緻化**: モデルごとの利用可否・枠の挙動が、ADR-0019の記述より詳細に判明した

本ADRは**ADR-0019をsupersedeする**（P-06: 決定は更新せず、新しい決定で置き換える。誤りを含む決定は
なおのこと、本文を書き換えずsupersedeで置き換える）。ADR-0019の運用規約（学習利用の可能性・PII禁止・
有料/Vertexへの切替の方針、Pro系モデルが無料枠で使えないこと）は引き続き有効であり、本ADRに引き継ぐ。
伝送方式（Gemini CLI経由の自動実行）とdeveloper宿題（CLIラッパ`commission-design.sh`）は**取り下げ**、
本ADRが定める内容に置き換える。

## 決定

### 1. 伝送方式の訂正

designerの(b)外部AI実行は、**Generative Language APIの`generateContent`エンドポイントを直接呼ぶ**
（`POST /v1beta/models/{model}:generateContent`）。エージェント型CLI（Gemini CLI等）は、設計の委託
という用途には**適さない**（実装計画を返そうとしてしまうため。上記「文脈」参照）。参照実装（スパイク）
はPython標準ライブラリのみで実装され、APIキーは`x-goog-api-key`ヘッダで渡す（URLに載せない）。
`~/.gemini/.env`から読む方式はADR-0019から維持する。

CLI経由の自動実行（ADR-0019案A）という選択肢そのものは**取り下げる**。人間-in-the-loop（人間が
Geminiアプリ等で実行し結果を持ち帰る）は引き続き有効な代替経路として残る。

### 2. 成果物の形式と受け皿

designerの(d)仕上げの成果物は、**実プロジェクトにそのまま置いて動くshadcn/uiベースのTSX**とする
（旧ADR-0019: 自己完結の静的HTML/CSS）。

理由: 自己完結HTML（CDN版）はレビューには忠実だが実装スタックとは別物であり、実装時に人間が翻訳する
過程でデザインが変容するリスクがある。実プロジェクトの「受け皿」でTSXとして描画すれば、レビューした
絵がそのまま実装の出発点になる。

**受け皿**: `projects/reservation-frontend/src/design-preview/`（Vite+React+TS+Tailwind+shadcn/ui、
`@/*`エイリアス、主要13コンポーネント導入済み）。外部AIの成果物を**無改変**でこの受け皿に置き、
devサーバで描画してレビューする。この経路で実際に描画・レビュー・人間承認（「原案としてOKな水準」）
まで到達した（reservation-frontend、2026-07-20）。

**禁止事項（明記）**: **agent（designerに限らず、architect・orchestratorを含む）は、外部AIの成果物を
手で静的HTMLや別形式に書き直してレビューしてはならない**。実際にこれを行った結果、人間から「ダサい／
本当にそのまま描画しているのか」と指摘された。再実装は設計を変容させ、デザインセンスの無い側（agent）
の絵に化けてしまう。**成果物は無改変でそのまま描画する**ことが、レビューの前提条件である。

#### ADR-0004（画面モック承認プロセス）との接続

designerの成果物が「`src/`配下のTSX」になったことで、projects/reservation-frontend/adr/0004が定めた
「実装コード禁止事項との切り分け」の3条件（出荷経路に乗らない・振る舞いを持たない・検証パイプラインに
乗らない）のうち、**条件1（`src/`配下のビルド・バンドル対象に一切含めない）はそのままでは成立しなく
なる**。本ADRはこの接続を次のように整理する（プロジェクト側ADR-0004の詳細な条文改訂は、本ADRでは
行わず別途行う。下記「帰結」参照）:

- `src/design-preview/`は、**実際にユーザーに配信される本番ルート・ビルド成果物には含まれない**
  「査読専用の受け皿」と位置づける。実アプリの画面（`src/screens/`等）からは参照されない
- 条件1（出荷経路に乗らない）は、「`src/`配下に置かない」から「**本番の配信ルート・ビルドに含まれ
  ない**」へ読み替える。技術的にこれを保証する具体的な仕組み（別entry・ビルド設定での除外・import境界
  lintでの禁止等）は**developerが実装判断で定める**（L2構造検証の実装はdeveloperの領分。
  meta/verification.md）
- 条件2（振る舞いを持たない）は、設計プレビュー用のTSXが実際のバックエンドAPIを呼ばない・実データの
  状態管理を持たない、という制約として引き継ぐ（外部AIへのブリーフで、モックデータ・静的propsでの
  描画を指定する）
- 条件3（検証パイプラインに乗らない）は、design-preview配下がL1〜L4の通常のテスト・カバレッジ対象で
  ないという扱いを維持する（型検査・lintは同一TSプロジェクトである以上受けうるが、単体テスト・受け入れ
  テストの対象にはしない）

この整理はarchitectの判断であり、**ADR-0004本体（§1「実装コード禁止事項との切り分け」）の正式な
改訂は別途行う**（本ADRでは軽微なポインタ追記のみ行う。下記「帰結」）。

### 3. ブリーフ構成の精緻化（「リッチ」の意味の限定）

ADR-0019は「ブリーフの豊かさが下流品質を決める」と定めたが、**「リッチ＝網羅」ではない**。**外部AI
にしか出せないもの（画面の発想・視覚的構成）に出力予算を集中させ、architectの領分（契約の精度・
エッジケース網羅・API設計の細部）はブリーフに載せない**。

有効だった構成（約50行）:
- 目的
- 対象ユースケース
- ドメインルール（**最小限**。詳細な業務規則の列挙はしない）
- **現在のバックエンドAPIの列挙＋「無いAPIは指摘してよい」という指示**
- 解決したい問題（不満点）
- 制約からの解放
- 技術前提
- 成果物の指定（TSX＋新規APIの列挙）

**「不満点」は必須ではない**: 実測で、不満点を書かないフラットなブリーフでも、まともなモデルは
タイムライン可視化・空き枠クリックでの直接予約・自分の予約管理に**自力で到達した**。ADR-0019は
「現状の不満点を要件として明示する」ことを必須要素としていたが、**必須ではなく「あると確実性が上がる」
任意要素に格下げする**。この事実は「不満点は人間しか供給できないため、パイプラインの限界になる」と
いう懸念を否定する材料であり、CLI自動化の失敗（伝送の問題）とは別の学びとして記録する（本ADRの文脈で
記述するにとどめ、friction-logへの別立ての起票はしない。人間の判断で明確な事故・迷いではなく、良い方向
の発見であるため）。

`meta/templates/design-brief.md`をこの構成に合わせて改訂する（エッジケース網羅・重い新規API列挙節を
求めない、現行API列挙節を追加する、不満点を任意要素に格下げする）。

### 4. 無料枠の実測（運用規約の訂正・補強）

- Pro系モデル（2.5-pro / 3.x-pro）は無料枠では`limit: 0`＝**有料専用**（ADR-0019の記述通り。維持）
- **gemini-2.5-flashは新規ユーザーへの提供が終了している**（HTTP 404で確認）
- **gemini-3.5-flashは20リクエスト/日**。かつ**暦日リセットでなくローリング24時間**の挙動を確認した
  （反復検証だとすぐ枯れる）
- **gemini-3.1-flash-liteは別バケットで枠が生きており、実用可能**（日常運用の現実解）
- モデル指定は、CLIでは`-m`フラグが必要（環境変数だけでは効かない）だったが、**API直叩きでは
  URLパスのモデル名で確実に指定できる**（伝送方式訂正の副次的な利点）
- 学習利用・PII禁止・有料/Vertexへの切替の規約は、ADR-0019からそのまま維持する

### 5. developer宿題の差し替え

ADR-0019が指定した`meta/tools/commission-design.sh`（Gemini CLIラッパ）は**取り下げる**。伝送方式の
訂正に伴い、developer宿題を次に差し替える:

- `meta/tools/commission_design_api.py`（またはproject固有の対応物）: ブリーフファイルを受け取り、
  Generative Language APIの`generateContent`を直接呼び出し（`x-goog-api-key`ヘッダ、`~/.gemini/.env`
  からAPIキーを読む）、設計成果物をファイルに保存する
- モデル選択: `gemini-3.1-flash-lite`をデフォルトの現実解として実装し、モデル名を引数で上書き可能に
  する（developerの実装判断）
- 上記「運用規約」（無料/有料切替・Pro系不可・モデルごとの利用可否・日次上限のローリング挙動）を、
  スクリプトのドキュメント・エラーメッセージ等にどう反映するかはdeveloperの実装判断
- smokeテスト: 実際にAPIを叩かない、または最小限のモック呼び出しで動作確認する形を想定
- **（新規）`src/design-preview/`の出荷経路除外の保証**: 上記「ADR-0004との接続」で述べた通り、
  design-preview配下が本番ビルド・配信ルートに含まれないことを保証する具体的な仕組み（別entry・
  ビルド設定・import境界lint等）の実装判断もdeveloperに委ねる
- 本ADRは指定のみを行い、実装しない（architectの禁止事項: 実装コードを書かない。meta/adr/0014）

## 検討した代替案

- 案P: ADR-0019のCLI自動化方式を維持しつつ、プロンプトの工夫でエージェント的挙動を抑制する / 不採用:
  実測でGemini CLIは実装計画を返す挙動が固定的であり（「進めてよいか」の確認を返す構造自体がエージェント
  型CLIの設計）、プロンプト調整で設計特化の出力に変えられる保証がない。API直叩きという、より単純で
  確実な代替が既に動作確認済みのため、そちらを採用する
- 案Q: 成果物を自己完結HTML（CDN版）のまま維持する / 不採用: 実装時の人手翻訳でデザインが変容する
  リスクが実証された（agentが静的HTMLに書き直した結果「ダサい」と指摘された事例）。実プロジェクトの
  受け皿でTSXとして描画する方が、レビューした絵をそのまま実装の出発点にできる
- 案R: ブリーフに「現状の不満点」を必須要素のまま維持する / 不採用: 実測で、不満点を書かないブリーフ
  でも実用水準の設計に到達した。必須要素を絞り込み、外部AIにしか出せないもの（画面）に出力予算を
  集中させる方が、ADR-0019自身の「型が複雑すぎる」という指摘に応える
- 案S: developer宿題（CLIラッパ）をそのまま残し、API直叩き版を別途追加する / 不採用: CLIラッパは
  そもそも動作しない（設計目的に使えない）ことが実測で判明しており、残す理由がない。宿題を差し替える
  （取り下げを明記する）方が誠実
- 案T: ADR-0019をsupersedeせず、relates_toで訂正内容を追加するにとどめる（0018→0019の前例に倣う） /
  不採用: 0018→0019の関係は「既存決定への拡張」（人間-in-the-loopの前提はそのまま、CLI自動化という
  選択肢を追加）だった。本件は**ADR-0019の中心的な決定（伝送方式そのもの）が誤りだった**ケースであり、
  性質が異なる。誤りを含む決定を「関連する」とだけ記録すると、どちらが現在の正しい規定か読者が判別
  しにくい。supersedeで明確に置き換える方が、P-06の「古い記述を信じる事故を構造的に防ぐ」という趣旨に
  忠実
