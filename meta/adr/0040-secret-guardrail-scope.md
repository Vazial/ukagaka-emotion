# ADR-0040: 機密ガードレールの守備範囲を直す——`Write` を塞ぎ、`.gitignore` を実在させ、テンプレートを `.env*` の外へ出す

> **承認者向けサマリ**: `.claude/settings.json` の deny 設定に**3つの穴**が見つかった。**(1) `Write` が
> 1件も deny されていない**——`Read`×11・`Edit`×8・`Bash`×14 に対し `Write`×0 で、読めず編集もできない
> ファイル（実 `.env`・秘密鍵・`secrets/**`）を**丸ごと上書き・新規作成できる**状態だった。**(2)
> `.gitignore` に機密ファイルの記述が1件も無い**——deny は「AIが読む」ことを止めるだけで「gitに入る」
> ことは何も止めない。機密保護としてはこちらが本命であり、しかも `.env.example` 自身が
> 「`.env.local`（gitignore対象）にコピーせよ」と、**存在しない保護を案内していた**。**(3) `.env.*` が
> 広すぎて `.env.example` を巻き込み、保守が実際に止まった**——3本目・4本目の実接続でフラグの追記が
> 漏れた。決定は3点——**機密でないテンプレートを `.env*` の名前空間から出す**（`.env.example` →
> `env.example`）／**`Read`・`Edit`・`Write` を対称に deny する**（`.env*` へ拡張し default-deny を
> むしろ強める）／**`.gitignore` に機密の実ファイルを追加する**。**default-deny は1ミリも緩めない。**
> 権限機構の実測結果（**deny は allow で上書きできず、除外構文も無い**）を証跡として本ADRに残す。

## 文脈

### 1. 発覚の経緯

4本目の実接続（キャンセル）の完了後、`.env.example` に環境変数を追記しようとしたところ、Read/Edit の
いずれも権限設定で拒否された。3本目でも同じ壁に当たっており、**2スライス連続でテンプレートの保守が
止まっていた**（FR-019）。

人間が「`.env.example` は機密ではないのに、なぜ deny なのか」と問うたことから調査に入った。

### 2. deny リストの出所

Claude Code のドキュメントが示す permissions の例は次の形である:

```json
"deny": ["Bash(curl *)", "Read(./.env)", "Read(./.env.*)", "Read(./secrets/**)"]
```

本リポジトリの `Read(./.env)` / `Read(./.env.*)` は**これと完全に一致する**。そこに `./**/` 変種と
`Edit(` を足したのが現状だった。つまり deny リストは**熟慮された方針ではなく、例文の拡張**である。
例文が `Read` だけだったため `Edit` までは足されたが、**`Write` に気づかなかった**。

### 3. 測定した3つの穴

| 穴 | 実測 |
|---|---|
| **`Write` が deny されていない** | `"Bash("`×14・`"Edit("`×8・`"Read("`×11 に対し `"Write("`×**0** |
| **`.gitignore` に機密の記述が無い** | env/鍵/secrets いずれも0件。追跡中の env 系ファイルは `.env.example` のみ |
| **`.env.*` が `.env.example` を巻き込む** | 1本目・2本目は更新されたが、3本目（2026-07-30）・4本目で**更新が漏れた** |

`Write` の穴が最も重い。`Read`・`Edit` を塞いだ意図は「機密ファイルに触らせない」ことだが、`Write` は
**内容を読まずに丸ごと置き換えられる**ため、機密の破壊（および新規作成による混入）が可能だった。

`.gitignore` の穴も軽くない。deny は AI の読み取りを止めるだけで、**人間・CI・他ランタイムが実 `.env`
をコミットすることを何も妨げない**。さらに `.env.example` 自身が「`.env.local`（gitignore対象、
`*.local`）にコピーする」と案内しており、**文書が存在しない保護を約束していた**。

### 4. 権限機構の実測（証跡）

「default-deny を保ったまま `.env.example` だけ通す」（ホワイトリスト）が可能かを実地検証した。
**対照実験を先に行い、設定変更がセッション中に反映されることを確認した上で**測定している。

| 試行 | 結果 |
|---|---|
| **対照**: `Read(./CONTROL-PROBE.md)` を deny に追加 → 読む | **拒否された**（＝設定はセッション中に反映される） |
| `!Read(./**/.env.example)` を deny に追加 → `.env.example` を読む | **拒否された**（除外構文は効かない） |
| `Read(./**/.env.example)` を **allow** に追加 → 同上 | **拒否された**（allow は deny を上書きしない） |

公式ドキュメントに除外構文の記載が無いのは、単に**存在しないから**だった。すなわち
**「deny に例外を作る」形のホワイトリストは、この権限機構では表現できない**。

## 決定

### 1. 機密でないテンプレートを `.env*` の名前空間から出す

`projects/reservation-frontend/.env.example` を **`env.example`** にリネームする（先頭のドットを外す）。

- deny 側は `.env*` を**むしろ広く**保てる（決定2）。**default-deny を1ミリも緩めない**
- `env.example` はどの deny パターンにも一致せず、AIが保守できる
- **`.env.example` は Vite が読み込まないただのテンプレート**（Viteが読むのは `.env`・`.env.local`・
  `.env.[mode]`・`.env.[mode].local`）なので、**機能影響はゼロ**

これは権限機構に依存しない**構造としてのホワイトリスト**である——「機密は全部NG／AIが保守してよいものは
そもそも危険地帯に置かない」。

代償は `.env.example` という慣習からの逸脱だが、`env.example` を使う実プロジェクトは存在し、
ファイル冒頭に理由を明記すれば迷いは生じない。**「AIが保守できない `.env.example`」を持ち続ける実害
（2スライス分の追記漏れ）の方が大きい。**

### 2. `Read`・`Edit`・`Write` を対称に deny し、`.env` パターンを広げる

3つのツールに**同一の8パターン**を適用する。あわせて `.env` 系を `./**/.env*` の1本に統合し、
`.env`・`.env.local`・`.env.production`・**将来の未知の変種**をすべて捕捉する（従来の `./.env` と
`./.env.*` の2本立てでは `.env` 直下と変種を別々に列挙する必要があり、漏れの余地があった）。

対象: `.env*` ／ `*.pem` ／ `*.key` ／ `id_rsa*` ／ `id_ed25519*` ／ `secrets/**` ／
`credentials.json` ／ `*credentials*.json`

**従来 `Edit` にだけ無かったパターン**（`id_rsa*`・`id_ed25519*`・`*credentials*.json`）も揃える。

### 3. `.gitignore` に機密の実ファイルを追加する

`.env` ／ `.env.*` ／ `*.pem` ／ `*.key` ／ `secrets/` ／ `credentials.json` ／ `*credentials*.json`。

**deny より本質的な防御である**——deny は AI の1経路を塞ぐだけだが、`.gitignore` は人間・CI・他ランタイムを
含む全経路でリポジトリへの混入を防ぐ。決定1により共有テンプレートは `.env*` の外にあるため、
`!` による除外は不要。

### 4. 適用範囲

本ADRは `.claude/settings.json`・`.gitignore`・`projects/reservation-frontend/env.example` を変更する。
**他プロジェクトの `.env.example` は現時点で存在しない**ため、リネームの対象は1件のみ。今後新設する
プロジェクトも `env.example` を用いる。

## 検討した代替案

- **案A: deny に除外構文（`!`）で `.env.example` を通す** / **不採用（機構が存在しない）**: 実測で
  `!Read(...)` も allow による上書きも効かないことを確認した（文脈4）。**採れないことを測定で確定させた**
  のであって、推測で捨てたのではない。
- **案B: 危険な変種を列挙する**（`.env.local`・`.env.production`… を deny し `.env.example` は自然に通す）
  / 不採用: **default-deny → default-allow への反転**になる。未知の変種（`.env.prod` 等）が漏れる。
  人間の方針（「基本 `.env` はNG、機密でないものだけ通す」）と逆方向。
- **案C: `.env.example` を人間・他ランタイム専用の保守対象として残す** / 不採用: 現に2スライス連続で
  漏れた。P-04（口頭ルールにせず構造で強制する）に反し、**漏れても誰も気づかない**（機械検査が無い）。
- **案D（採用）: テンプレートを名前空間の外へ出す＋Write対称化＋gitignore** / 採用: default-deny を
  緩めず、AIの保守経路を回復し、より本質的な防御（gitignore）を足す。3点は独立に効き、互いを弱めない。

## 帰結

- `env.example` はAIが保守できるようになった。**本PRで、3本目・4本目で漏れていた
  `VITE_USE_REAL_RESERVATIONS_API` と `VITE_USE_REAL_RESERVATIONS_CANCEL_API` を追記済み**
  （4本すべてを `true` にして初めてループが実物で通る、という組み合わせ制約も明記した）。
- 機密ファイルの `Write` が塞がった。読めず編集もできないファイルを上書き・新規作成できる状態は解消。
- 機密ファイルがコミットされなくなった。`.env.example` が案内していた「`.env.local` はgitignore対象」が
  **実際に真になった**。
- 権限機構の性質（deny絶対優先・除外構文なし・設定はセッション中に反映される）を証跡として残した。
  同じ問いが再発しても再検証は不要。
- **未対応として残る**: `Bash` の deny が prefix 一致であり、フラグの順序を変えると回避できる
  （`Bash(git reset --hard*)` は `git reset -q --hard` を止められない。ADR-0039 帰結で記録済み）。
  本ADRでは扱わない——ツールごとに機構が異なり、`Bash` 側は引数の組み合わせが爆発するため、別途
  設計が要る。
- **確認事項**: 本ADRは `meta/guardrails.md` §3（`.env`・認証情報・秘密鍵はAI読み取り禁止）の
  記述と整合するが、同§は「読み取り禁止」としか書いておらず**書き込み・コミットに触れていない**。
  §3の条文改訂を本PRに含めるか別途とするかは、規程本体への反映（ADR-0039 の帰結で「宿題に回すと
  ドリフトする」と学んだ点）に照らせば同一PRが望ましい。**本PRでは §3 も同時に改訂する**。
