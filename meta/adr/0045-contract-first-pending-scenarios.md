# ADR-0045: 未実装のシナリオに印を付けてL4から外し、契約だけを先にmainへ載せられるようにする

> **承認者向けサマリ**: **「作る前に人が契約を承認する」（ADR-0022 の断面①）が、機械の都合で実行
> 不可能だった。** シナリオIDという同じ識別子が L0（契約の参照整合）と L4（実装の網羅）を結合して
> おり、契約だけを先に置くと必ずどちらかが落ちる——`.feature` を置かないと L0 が「参照先が無い」で
> 落ち、置くと L4 が `UndefinedStepException` で落ちる。**FR-014 が10日前にこれを記録したが status は
> 「未対応」のままで、当時の押し込みは「受け入れシナリオは実装スライスと必ず同じ粒度で land させる」
> という運用回避だった。これは ADR-0022 の断面①と正面から矛盾する。** そして RSV-T（会議室の登録）で
> 実際に再び踏んだ。**同じ原因の2回目は構造で直す**（P-04・このリポジトリ自身のルール）に従い、人間は
> 構造を直す方を選んだ。決定は3点——**未実装のシナリオに `@pending-implementation` タグを付け L4 の
> 実行対象から外す**／**govlint が印の付いたシナリオを棚卸しREPORTに出す**（ERROR にはしない）／
> **L0 の参照整合は一切緩めない**。あわせて **`build.gradle` の所有者記述が `meta/agents.md` §6 と
> 矛盾していた**のを是正する。

## 文脈

### 1. 何が不可能だったか

`meta/adr/0022` は断面①（契約の形に人間が合意）→断面②（動く実装に人間が合意）の順序を定めている。
ところがこの順序は**機械的に実行できなかった**。

```
L0 govlint: API仕様が参照するシナリオIDは .feature に定義必須 → .feature を置かないと落ちる
L4 Cucumber: .feature にシナリオがあれば step 定義が必須 → 実装が無いと UndefinedStepException
```

**シナリオIDという同じ識別子が、契約側の参照整合と実装側の網羅という別々の検証層を結合している。**
結果、「契約だけを先に main へ載せる」という中間状態が構造的に作れない。

### 2. FR-014 が予告し、運用回避で済ませていた

`projects/reservation-system/friction-log.md` の **FR-014**（2026-07-22、`status: 未対応`）がこの構造を
正確に記録している。当時の押し込み先はこうだった:

> 今回は当面の運用規律で回避——受け入れシナリオは実装スライスと必ず同じ粒度で land させる

**この回避策は ADR-0022 の断面①と正面から矛盾する。** 契約と実装を同時に land させるなら、契約の承認は
実装の承認と分離できない。両方の規程が矛盾したまま生きていた。

### 3. 誤った帰責を訂正する

`meta/adr/0043` は、RFE-B（フロントの予約スライス）が契約と実装を同一コミットで入れたことを
「ADR-0022 の断面①→②の順序を通っていない」と記録した。**この記述は不正確である。** RFE-B は
**FR-014 が処方した運用回避に従った結果**であり、順序を守れなかったのは規律の問題ではなく
**機械がそれを許さなかったから**である。本ADRはこの帰責を訂正する。

### 4. RSV-T で実際に再び踏んだ

会議室の登録（RSV-T）の契約だけを載せた PR で、**L4 が `UndefinedStepException` で4シナリオ落ちた**
（`35 tests completed, 4 failed`）。10日前と同じ場所である。

**同じ原因のFRが2回出たら構造的欠陥**（friction-log 冒頭の規約）に該当する。人間は運用回避の踏襲では
なく構造を直す方を選んだ（2026-08-01）。

## 決定

### 1. 未実装のシナリオに `@pending-implementation` を付け、L4 の実行対象から外す

Gherkin のタグを印として使う。`Scenario:` / `Scenario Outline:` の直上に置く（コメント行が間に
挟まってよいが、**空行を挟むと関連付けは切れる**——離れた位置のタグが無関係なシナリオを覆わないため）。

L4 の除外は Cucumber の `cucumber.filter.tags` で行う（`not @pending-implementation`）。
`-D` で上書きできるため、印付きシナリオだけを狙って実行することも可能である。

**タグを選んだ理由**: Gherkin ネイティブの「このシナリオは特別」という機構であり、新しいファイル形式も
パーサも要らない。**シナリオ単位の粒度**を持つため、4本のうち2本だけ実装した中間状態も表現できる。

**「除外」の正確な意味**: 印付きシナリオは Cucumber に**発見はされ、`skipped` として報告される**
（実行されない・失敗しない）。**見えないまま消えるのではなく、見えるが走らない**——この方が正直である。

**印を外せば通常通り落ちる。** 既存の検査は一切弱まらない（実測で確認済み）。

### 2. govlint が印の付いたシナリオを棚卸しREPORTに出す

`[REPORT] 実装待ち（@pending-implementation）のまま残っているシナリオ`。既存の2つのREPORT
（提案中ADR＝ADR-0035、承認待ち契約＝ADR-0043）と同じ扱いで、**ERROR にはしない**。

**ERROR にしない理由**: 実装待ちは正当な状態である。ERROR 化すると、CI を通すために**印を外す**という
誘因が生まれる——印を外せば L4 が落ちるので、結局「契約と実装を同時に」に戻る。**罰すると回避され、
回避されると元の問題に戻る**という構造なので、可視化に留めるのが正しい強制レベル（P-04）。

### 3. L0 の参照整合は一切緩めない

印が付いていても、そのシナリオIDは L0 上「定義済み」として扱われる。API仕様からの参照は今まで通り
解決する。**目的は契約を先に置けるようにすることであって、参照整合を緩めることではない。**

### 4. `build.gradle` の所有者記述を是正する

`projects/reservation-system/build.gradle` の冒頭は「orchestratorが管理する。developer/testerは原則
ここを変更しない」と書いているが、**`meta/agents.md` §6（meta/adr/0014）は「検証インフラのうち
ロジックを持つもの（build.gradle・govlint等）はdeveloperの領分（テスト付き）」と定めている**。
両者は矛盾しており、本作業で developer が実際にこの矛盾に直面した。

**`meta/agents.md` §6 を正とし、`build.gradle` のヘッダを是正する**——後から書かれた規程（ADR-0014）が
上位であり、かつ「orchestratorが検証インフラを直接いじらない」方が ADR-0039 の趣旨とも整合する。

## 検討した代替案

- **案A: FR-014 の運用回避を踏襲する（契約と実装を常に同時に land）** / 不採用: **ADR-0022 の断面①が
  「制度としては存在するが実行不可能」という状態が固定される**。このテンプレートの核（作る前に人が
  承認する）が看板だけになる。人間が明示的にこちらを退けた。
- **案B: L4 から `.feature` の自動探索をやめ、実装済みシナリオを明示列挙する** / 不採用: 列挙漏れが
  「テストが無いのに緑」を生む。**印の付け忘れ（落ちる）より、列挙漏れ（気づかず緑）の方が危険**である。
- **案C: 印付きシナリオを ERROR にして期限を切る** / 不採用: 決定2の理由の通り、罰すると印を外す誘因が
  生まれ元の問題に戻る。ADR-0035（提案中ADR）・ADR-0043（承認待ち契約）と同じ設計判断。
- **案D: L0 の参照整合を緩め、`.feature` 無しでも API仕様が シナリオIDを参照できるようにする** /
  不採用: 参照先が実在しないIDを許すと、誤記・消滅を検出できなくなる。ADR-0038 で強化したばかりの
  検査を逆行させる。
- **案E（採用）: 印＋L4除外＋REPORT、L0は不変** / 採用: 契約先行を可能にしつつ、既存の検査を1つも
  弱めない。印の滞留は機械が可視化する。

## 帰結

- **ADR-0022 の断面①が初めて実際に機能する。** 契約だけを載せた PR がマージできるようになる。
- 印の滞留は毎回のCIに見える。契約先行が「書いたまま忘れる」に堕ちない。
- **FR-014 を `未対応` → `対応済み` に更新する**（10日前の記録が本ADRで解消される）。
- **ADR-0043 の RFE-B に関する記述を訂正する**（規律違反ではなく機械的制約が原因だった）。
- `build.gradle` のヘッダと `meta/agents.md` §6 の矛盾が解消される。
- **未対応として残す**: 印を付ける主体と外す主体の規定。今回は orchestrator の依頼で developer が
  付けたが、本来は**契約を起草した architect が付け、実装した developer が外す**のが自然に見える。
  ただし architect は実装の有無を判断できる立場か（実装済みかどうかは実装側の事実）という論点があり、
  本ADRでは決めない。運用で摩擦が出てから定める（P-05）。
