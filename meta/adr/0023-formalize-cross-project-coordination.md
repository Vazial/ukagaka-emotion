# ADR-0023: クロスプロジェクトの協調(consumer-driven契約・縦順序・越境の実行主体)を正式化する

> **承認者向けサマリ**: reservation-frontend(会議室予約フロントエンド)の設計が、今回初めて
> reservation-system(バックエンド)の契約(`GET /rooms`、`reservation-system/adr/0007`)を実際に
> 駆動した。この初の実連動から得た「プロジェクトをまたいでどう協調して作るか」の学びを、人間が3点の
> 決定として制度化することを決めた: **(1)UIの設計がバックエンド契約の形を駆動してよい
> (consumer-driven contract)**、**(2)フロントは契約に対して作り・バック実装は独立トラックとする、
> 両者が交わるのは契約とE2E結合の2点だけ、プロジェクトをまたいでPRを交互に出さない(縦順序)**、
> **(3)AIは人間の決定なしに自動で越境編集しないというガードは維持しつつ、人間が「バックに持ち込む」
> と決定(authorize)したらarchitectが直接バックエンド契約を起草してよい(越境の実行主体の精緻化。
> 旧reservation-frontend/activeContext.mdの「人間が転記」ルールを更新)**。既存決定
> (reservation-frontend/adr/0002の非統合、meta/adr/0022の2断面、meta/adr/0017の並行モデル、
> PRINCIPLES.md P-02の縦切り)とは矛盾せず、直交・補完する。承認いただきたいのはこの3点の制度化
> そのものと、reservation-frontend/activeContext.mdの該当ルール更新(本ADRに同梱)への追認。

## 文脈

2026-07-22〜23、reservation-frontendの設計(designerの外部AI成果物とarchitectのreconciliation)が、
初めてreservation-system側のバックエンド契約を実際に駆動した。フロントのタイムライン画面が会議室一覧
(`id`・表示名・定員・営業時間)を必要とし、既存契約にこれが無いことがreconciliationで判明、人間が
「`GET /rooms`をreservation-systemに追加する・フロントの必要から形を決める(consumer-driven
contract)」と決定し、architectが`reservation-system/adr/0007`と`contracts/reservation-api.yaml`の
API形状追記をドラフトした(`projects/reservation-system/friction-log.md` FR-014が記録する通り、この
過程で受け入れシナリオを実装より先に置けないという構造的制約も同時に発見された)。

この初の実連動は2つのことを露呈した。

1. **コミット境界の混乱**: 契約(バックエンド)とモック(フロントエンド)という異なる位相の成果物が
   並行して動いたため、「どの成果物をいつmainに載せてよいか」が一時的に曖昧になった。これは
   meta/adr/0022(断面①骨格合意・断面②実装合意の2断面)で解決済み
2. **既存の「人間が転記」ルールと実態の乖離**: reservation-frontend/activeContext.mdが定めていた運用
   (「フロントエンド側でactiveContext.mdに記録し、backend側への転記・優先度判断は人間が行う」)は、
   実際にはarchitectがbackend側のADR・API仕様を直接起草する形で進んだ。ルールが実態を追認していない

加えて、この越境がガードレール(「AIは自動で越境編集しない」)を壊さずに機能したという**肯定的な観測**
も得られた: 表示名(`name`)フィールドは`design.md`のroomsテーブル定義・`test-support-api.yaml`に既に
存在しており、データモデルの衝突は無かった。`/rooms`(一覧)と`/rooms/{roomId}/rules`(予約前詳細)の
役割分担も、追加の人間裁定なしにADR-0007内で自律的に解決した。

決定・成果物そのもののADR化(0007・0022)は進んだが、**「どう協調して作るか」という手続き上の学習が、
まだどの規程にも定着していない**。本ADRはこれを埋める。

参照した既存決定:
- `projects/reservation-frontend/adr/0002`(会議室予約フロントエンドを独立プロジェクトとして新設。
  統合しない)
- `meta/adr/0022`(パイプラインのコミット/マージを2断面に正式化)
- `meta/adr/0017`(designerをarchitectと並行に置くモデル。ADR-0018で「design integrator」へ
  再定義されたが並行モデル自体・reconciliation工程は継続)
- `meta/PRINCIPLES.md` P-02(契約はスライス単位で先に確定する。イテレーションの単位は縦切りの
  1ユースケース)
- `projects/reservation-system/friction-log.md` FR-014(シナリオIDがL0とL4を結合し、契約とシナリオの
  間に時間差を作れない構造的制約)
- `projects/reservation-frontend/activeContext.md`(「フロントが必要とする能力がバックエンド契約に
  無い場合の運用」の旧ルール)
- `projects/reservation-system/contracts/reservation-api.yaml`の`GET /rooms`、
  `projects/reservation-system/adr/0007`(consumer-drivenの実例)

## 決定

以下4点は人間確定であり、architectはこれを再導出・再検討しない(meta/adr/0011の精神: orchestrator
が人間決定をそのまま運んだものは、architectが内容そのものを検討し直さない)。

### 1. Consumer-driven contract(消費者駆動の契約)

**UIプロジェクトの設計(モック)が、必要なバックエンド契約の"形"を駆動してよい。** designerの
(c)reconciliationが不足契約を炙り出し、それが契約の形の起点になる。

実例: `GET /rooms`は、フロントの必要(会議室の`id`・表示名・定員・営業時間)から形が決まった
(`reservation-system/adr/0007`)。この決定は`reservation-frontend/adr/0002`(非統合・独立
プロジェクト)と両立する——プロジェクト間は組織的に統合されるのではなく、**契約で交わる**。非統合の
決定は「同じディレクトリ・同じADR系列に同居しない」ことを定めたのであって、「契約が互いを駆動しない」
ことを定めたのではない。

### 2. クロスプロジェクトのbuild順序(縦順序)

- **フロントは"契約に対して"作る**。動くバックエンド実装の完成を待たない。バックエンドはモック/
  スタブで代用する。これは`reservation-frontend/adr/0002`の非統合思想(バックエンドとフロントエンドは
  別々に、それぞれの都合で動ける)に忠実な帰結である
- **バックエンド実装は独立トラック**である。フロントエンド実装と並行に進めても、前後どちらの順序で
  進めてもよい
- 両者が**交わる点は2つだけ**に限定する: **(a)契約**(設計時にreconciliationで既に噛み合わせ済み)、
  **(b)最後のE2E結合**(動くフロントと動くバックエンドを実際につなぐ結合テスト)
- **プロジェクトをまたいでPRを交互に出さない。** 設計フェーズ(断面①、meta/adr/0022)を両プロジェクト
  で閉じてから、実装フェーズ(断面②)に入る、という順序を守る。これは今回、契約とモックの位相が混在
  したPRの往復が混乱・出戻りを生んだという実体験(上記「文脈」1.)に基づく

この決定は、`meta/PRINCIPLES.md` P-02(契約はスライス単位で先に確定する。イテレーションの単位は
縦切りの1ユースケース)を**単一プロジェクト内の規律として変えるものではなく**、その規律をプロジェクト
をまたぐ次元に拡張する運用上の敷衍である。PRINCIPLES.md本文(P-02)は編集しない——本ADRが定めるのは
「プロジェクトをまたぐ時、縦切りの順序をどう保つか」という運用規約であり、P-02自体が持つ独立した
公理性を増減させない(meta/adr/0016が同型の判断をP-01に対して行った先例に倣う)。

### 3. 越境の実行主体の精緻化(旧「人間が転記」ルールの更新)

**旧ルール**(`reservation-frontend/activeContext.md`「フロントが必要とする能力がバックエンド契約に
無い場合の運用」): フロントエンド側でactiveContext.mdの「未解決の論点」に記録し、backend側
(`reservation-system/activeContext.md`)への転記・優先度判断は人間が行う(AIが自動で越境編集
しない)。

**新ルール**: **AIは人間の決定なしに自動で越境編集しない**(ガードそのものは維持する——architectが
独断でプロジェクトをまたいで契約を書き換えてよい、という話ではない)。ただし**人間が「バックに
持ち込む」と決定(authorize)したら、architectが直接バックエンド契約(API仕様・ADR)を起草してよい**。
人間が物理的にactiveContextへ転記する作業を担う必要はない。

効果: consumer-driven契約の越境が、**人間の判断ゲート(authorize)付きで軽く回る**。ゲートは「転記
作業を人間が行うか」から「越境してよいという決定を人間が下すか」に移る——人間の関与は「意図の表明と
重要判断の承認に集中する」というP-01の精神に、より忠実になる。

実例: `GET /rooms`の起草がこの経路の初適用である。人間が「`GET /rooms`をreservation-systemに追加
する」と決定した後、architectが`reservation-system/adr/0007`とAPI形状のドラフトを直接起草した
(転記作業を人間が行っていない)。

### 4. 越境コーディネーションが機能したという肯定データ(記録)

初の実連動で得られた、越境が安全に機能したことを示す肯定データを記録する:

- 表示名(`name`)フィールドは`design.md`のroomsテーブル定義・`test-support-api.yaml`に2026-07-13
  時点から既に存在しており、越境によるデータモデルの衝突は**ゼロ**だった
- `GET /rooms`(一覧・概要)と既存`GET /rooms/{roomId}/rules`(予約前詳細)の役割分担は、追加の人間
  裁定を要さず`reservation-system/adr/0007`内で自律的に解決した

これは**consumer-drivenの越境コーディネーションが成立するという実証**であり、(1)〜(3)の決定を
裏付ける根拠として記録する(将来、越境コーディネーションの要否・設計を再検討する際の参照データと
する)。

## 検討した代替案

- 案A: 旧ルールのまま(越境は必ず人間が転記して行う)を維持する / 不採用: 実態(architectが直接
  バックエンド契約を起草した)と乖離しており、ルールが機能を果たしていない。転記という物理作業に
  人間の時間を使わせる一方、本質的な判断(越境してよいか)は結局人間が下しているため、転記作業自体に
  検証上の価値が無い
- 案B: architectに越境編集の常時権限を与える(人間のauthorizeゲートを外す) / 不採用: 「AIは人間の
  決定なしに自動で越境編集しない」というガードはP-08(契約を満たせない時は止まって報告する)・
  P-07(契約を確定できるのは人間だけ)の精神そのものであり、外すとプロジェクト間の非統合
  (reservation-frontend/adr/0002)が事実上の統合に近づいてしまう。ゲートは軽くする(転記→
  authorize)が、無くさない
- 案C: プロジェクトをまたぐPRの往復(設計と実装の位相混在)を許容する運用のまま続ける / 不採用:
  今回、契約とモックの位相混在が実際に混乱・出戻りを生んだ(meta/adr/0022はこの混乱の事後整理として
  生まれた)。断面①を閉じてから断面②に入るという縦順序を、プロジェクトをまたぐ次元でも明文の規律に
  する方が、次のスライスで同じ混乱を再発させない
- 案D: この決定をPRINCIPLES.mdに新しい原則(P-12)として追加する / 不採用: meta/adr/0016が同型の
  判断で示した基準(「独立した公理か、既存原則の運用規約か」)に照らすと、本ADRの内容はP-02(縦切りの
  規律)の運用上の敷衍であり、それ自体が独立した公理ではない。ADR層(本ADR)に置き、PRINCIPLES.mdは
  編集しない

## 帰結

**フロント↔契約↔バックの交わり(縦順序の図)**:

```
reservation-frontend (UI設計)              reservation-system (バックエンド)
  designer: ブリーフ→外部AI→reconciliation
        │ (c)reconciliationが不足契約を検知
        ▼
  ① 人間: 「バックに持ち込む」と決定(authorize)
        │
        ▼
  architectがバックエンド契約を直接起草 ───────▶ API形状 + ADR(例: GET /rooms, adr/0007)
        │                                            │
        │◀── 契約の形はここで両者が交わる(1点目) ──┘
        │                                            │
  フロント: 契約に対して実装(断面②)          バック: 独立トラックで実装(断面②)
   (動くバックエンドを待たない)                (フロント実装の前後どちらでもよい)
        │                                            │
        └──────── 最後のE2E結合(2点目) ──────────────┘
```
