# ADR-0076: LinearのGitHub連携は接続済みと確認し、人間への完了報告はPRでなくLinearチケットを示す

> **承認者向けサマリ**
>
> KEN-34（Orca・Linear・GitHubの連携を考えたいというチケット）の作業中、直前のKEN-33対応
> （PR #225）が「このリポジトリ群にLinearのGitHub公式連携アプリが繋がっていない」と書いていた
> 前提が誤りだったと分かった。実際には接続済みで、ブランチ名がLinearの命名規則に一致していれば
> PRを開いた時点でLinearのアクティビティへ自動でリンクが貼られる（本ADRの元になったKEN-34自身の
> PR #226で実測）。
>
> あわせて、人間から運用ルールの指摘を受けた——AIが作業完了をチャットで報告するとき、示すべきは
> PRのリンクではなくLinearチケットのリンクである。チケットがSSOTであり、PRは既にそこへ自動で
> 添付されているため、チケットを辿ればPRにも行き着く。
>
> 決定は2点。ともに`meta/orchestration.md`（template-syncで派生リポジトリへ配布される）に書き、
> このリポジトリと派生リポジトリ全部に及ぶルールにする。
>
> 1. `.github/pull_request_template.md`の「連携アプリを繋いでいない」という誤記は訂正済み
>    （PR #226）。`orca linear attach`は保険として手順に残すが、ブランチ名がLinearの命名規則に
>    一致していれば通常は不要（自動で添付される）
> 2. 人間へ作業完了・節目を報告するときは、PRのURLではなくLinearチケットのURLを示す

## 文脈

KEN-34「Orca + Linear + Githubの運用考えたい」に着手し、まず`.github/pull_request_template.md`の
「GitHubのLinear連携アプリを繋いでいないリポジトリでは、これがPRとチケットを結ぶ唯一の見た目の
手がかりになる」という一文を根拠にPRタイトルの手引きを説明した。人間から「Web上ではLinearと
Githubはつないでるんだけど、認識していない？」と指摘を受け、調べ直した。

KEN-33チケット（直前にこの誤った前提を書いたチケット自身）のアクティビティログを確認すると、
PR #225を開いた2分後に「Linear」ボット（`type: workflow`）がPRを自動添付し、「GitHub」ボット
（`type: integration, subType: github`）がアサイニーを自動設定していた記録が残っていた。KEN-34
自身でも同じ現象を再現できた——PR #226を開いた直後、こちらが`orca linear attach`を呼ぶ前に
自動添付されていた。ブランチ名が`orca worktree create --linear-issue`で作られる
Linearの命名規則（`<ユーザー>/<チケット番号>-<スラッグ>`）に一致していたことが条件と見られる。

この訂正を反映したPR #226を作り、チャットで完了を報告した際、PRのリンクを主に示す報告の仕方を
した。人間から「やったこと、はわかったけど、作業が終わったら見せるべきはPRではなくLinearの
チケットですよね」と指摘され、あわせて「ここで決めたことはこのリポジトリと派生するリポジトリ
すべてのルールにしましょう」と、恒久ルール化の指示を受けた。

## 決定

### 1. LinearのGitHub連携は接続済みという事実を運用文書に反映する

`.github/pull_request_template.md`の誤記はPR #226で訂正済み（「連携アプリを繋いでいない」→
「接続済みで、ブランチ名が一致すれば自動でリンクが貼られる」）。

`meta/orchestration.md` §3手順6「Draft PR にする」の`orca linear attach`の扱いを、「必須の手順」
から「自動添付されなかった場合の保険」に位置づけ直す。ブランチ名がLinearの命名規則に一致して
いれば通常は不要だが、手で作ったブランチ等で一致しない場合の保険として手順には残す。

### 2. 人間への完了報告はLinearチケットのURLを示す

チャットであれ自動実行であれ、AIが人間に対して作業の完了・節目を報告するときは、PRのURLでは
なくLinearチケットのURLを示す。理由は2つ——

- Linearチケットが状態のSSOT（§1）であり、PRは決定1のとおり自動でそこに添付される。チケットを
  辿ればPRにも行き着くが、逆にPRからチケットの状態やコメント履歴は辿りにくい
- 派生リポジトリを含め複数のリポジトリを横断する人間にとって、確認する場所が「チケット1箇所」に
  揃う方が負荷が低い（KEN-34の元々の狙い「人間の操作の負荷を下げたい」に対応する）

`meta/orchestration.md` §3手順7「節目ごとに書く」に、この報告先のルールを明文化する。

## 検討した代替案

- PRのURLとLinearチケットのURLを両方示す／不採用の理由: 人間から「PRではなくチケット」と
  明確な指示があった。チケット側からPRへは自動リンクで辿れるため、両方示す実益が薄い
- `orca linear attach`の手順をorchestration.mdから削除する／不採用の理由: 自動添付の条件
  （ブランチ名の一致）が崩れるケース（手動でブランチを切った、Linearの連携設定が将来変わる等）
  への保険が要る。文言を「必須」から「保険」に弱めるに留めた

## 帰結

- `meta/orchestration.md`はtemplate-sync（ADR-0069）で派生リポジトリへ配布されるため、この2つの
  ルールは次回の週1取り込みでこのリポジトリと派生リポジトリ全部に及ぶ
- 以後、AIが人間に完了報告をするときはLinearチケットのURLを主に示す
- `.github/pull_request_template.md`の訂正（PR #226）と合わせて、KEN-34の最低限の要望
  （PRを出したらアクティビティにリンクを貼る）は既に満たされていたと確認できた
