# ADR-0012: 統治文書のメタデータをスキーマ化し、手作業の判定を機械化する

## 文脈

P-03は「SSOTの優先順位は実行可能 > 機械検証可能 > 人間可読」、P-04は「ルール化できるものを文章で書かない」と定める。契約（Gherkin・OpenAPI）、依存制約（ArchUnit）、業務ルール（ドメインコード）にはこれを適用してきた。しかし**テンプレート自身の統治文書（ADR・friction-log）はprose のままで、そこに書かれたルールを人間とorchestratorが目視で運用している**。

具体的な破綻:
- friction-logの運用ルール「同じ原因のFRが2回出たら構造的欠陥」は、orchestratorがパターンを目で探している。**実際に1回取りこぼした**（FR-006に「1回目はfriction-logに記録し損ねていた。これ自体も反省点」と自白がある）
- 「未対応のFRが放置されていないか」の棚卸しも目視
- ADRの状態（提案中/承認済み/superseded）、置き換えリンク、参照先（`adr/0006`等）の実在は誰も検証していない
- 契約⇔ADR⇔シナリオIDの相互参照も手作業（RSV-AでシナリオIDの繰り上げをorchestratorが手で行った）

規模が閾値を超えた: meta ADR 11本・project ADR 6本・FR 9件。目視での整合維持は既に信頼できない。

## 決定

統治文書を**ハイブリッド構造**にする。**メタデータは機械可読なスキーマ、推論はprose**。

1. **ADR**: ファイル冒頭にYAML frontmatterを置く（id / scope / status / date / approved_by / supersedes / superseded_by / relates_to）。`## 文脈` `## 決定` `## 検討した代替案` `## 帰結` の本文はproseのまま
2. **friction-log**: 各エントリの見出し直後に ```yaml ブロックを置く（id / date / found_at / slice / agents / cause_category / **cause_key** / pushed_to / status / principles）。事象・原因の考察・押し込み先の説明はproseのまま
3. **lint**（`meta/tools/govlint.py`）をCIに追加し、次を機械検証する:
   - スキーマ妥当性（必須フィールド・値の妥当性）
   - 参照整合（supersedes/superseded_by/pushed_to/relates_to の参照先が実在するか、superseded関係が対称か）
   - **同一 cause_key の再出現を検出**（2回目以降＝構造的欠陥のシグナル）
   - 未対応FRの棚卸し
   - シナリオIDの整合（.feature内で一意か、API仕様が参照するIDが実在するか）

**proseを残す理由**: P-03自身が「文章のドキュメントには、上位2つで表現できないもの（理由・経緯・判断）だけを置く」と定める。ADRの`文脈`や`検討した代替案`は推論であり、スキーマ化すると価値が失われる。構造化するのはメタデータだけである。

**cause_key について**: 原因カテゴリ（`規程の欠落`等）だけでは粒度が粗すぎて機能しない（現に5件が「規程の欠落」に該当し、これで警告すると常時鳴って無意味になる）。そこで「どの具体的な欠落か」を示すkebab-caseのキーを別に持つ。lintは**完全一致の再出現**を検出する。キーの選定自体は書き手の判断が残るが、(a)検出と警告が機械化され、(b)既存キーの一覧が可視化されるため「同じ原因か」の判断材料が揃う。取りこぼしの主因（記録漏れ・パターンの見落とし）はこれで塞がる。

## 検討した代替案

- 案A: 現状維持（prose + 目視） / 不採用: 既に取りこぼしの実績があり、規模が増えるほど悪化する。P-04違反そのもの
- 案B: 全文をスキーマ化（推論も構造化フィールドに） / 不採用: P-03に反する。理由・経緯はproseでしか表現できず、構造化は情報を殺す
- 案C: cause_keyを固定enumにする / 不採用: 新しい原因が出るたびenum更新のPRが要り、記録の摩擦を上げる。自由なslug + 一覧の可視化で足りる
- 案D: friction-logを1エントリ1ファイルに分割（ADRと同じ形） / 不採用: 「1ファイルを追記で読む」性質は運用上有用。fenced yamlブロックで同じ機械可読性が得られる

## 帰結

- 既存の全ADR（meta 11 + project 6）とFR 9件にメタデータを付与する（本PRで移行）
- lintがCIの1ジョブとして走る。**cause_keyの重複は失敗させず「報告」する**（構造的欠陥のシグナルであって、その場で直すべきエラーではない。判断は人間が行う）
- 参照切れ・スキーマ不正は**失敗させる**（機械的に直せる誤りのため）
- meta/templates/adr.md と friction-log.md を新様式に更新する
- 移行によって、既存FRの cause_key 重複が初めて機械的に可視化される
