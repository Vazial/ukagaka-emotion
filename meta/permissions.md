# permissions.md — 権限規程

> 対象: 全agent。成果物に触れる前に該当行を確認する。
> 原則の根拠: P-01, P-07, P-08

## 1. 権限マトリクス

全成果物の起案・執筆はAIが行う。区別するのは「人間がどう関与し、何をもって確定するか」。

| 成果物 | 人間の関与 | 確定条件 | 機械検証 |
|---|---|---|---|
| 契約（受け入れシナリオ・API仕様） | 意図を語る。ドラフトを承認する | **人間の承認** | スキーマlint |
| 制約のADR（次にAIが何をしてよいかが変わるADR。meta/adr/0061 決定1） | ドラフトを承認する | **人間の承認** | スキーマlint |
| 記録のADR（すでに決まったことを書き留めるADR。同上） | いつでも閲覧できる。あとから新しいADRで覆せる | **AIが自律更新可**（承認不要） | スキーマlint |
| 設計骨格（モジュール境界・データモデル） | 提案を承認する | **人間の承認** | 構造検証 |
| 実装コード | 原則関与しない | テスト+lint通過 | フル |
| 単体テスト | 原則関与しない | カバレッジ基準+契約対応表 | フル |
| ビルド設定・検証ツール（build.gradle・govlint等） | **ゲート（判定ロジック）の変更時のみ承認**。AIが書き込もうとすると確認プロンプトが出る（meta/adr/0054） | 承認後、developerがテスト付きで実装する。保護が`permissions.ask`に載っていることをgovlintがERRORで検証する | フル |
| CIワークフロー（.github/workflows/） | **ゲート（必須チェック）の変更時のみ承認** | orchestratorが編集。ゲート変更は人間承認 | 自己検証（PRのCI） |
| 受け入れテストのstep実装 | 翻訳の正しさをレビューする | **人間の承認** | テスト実行 |
| 信条・規程（PRINCIPLES.md、本ファイル等） | ドラフトを承認する。変更はADR必須 | **人間の承認** | — |
| HANDOFF.md（不変のオンボーディング） | ドラフトを承認する。変更はADR必須 | **人間の承認** | — |
| activeContext.md・friction log（`meta/friction-log.md` と `projects/<p>/friction-log.md`。meta/adr/0058） | いつでも閲覧・上書きできる | **AIが自律更新可**（承認不要） | 形式lint |
| ARCHITECTURE.md（設計の現在） | PR差分で確認できる | **AIが自律更新可**。ただし承認済み決定の投影のみ。新規決定の持ち込み禁止 | — |
| design.md（現在の設計の地図） | 設計骨格の承認に随伴して確認する | architectが上書き維持（骨格自体の承認は済んでいる前提） | — |

人間の承認ポイント: **契約 / 設計骨格 / step実装 / 信条・規程の変更** の4箇所。「信条・規程の変更」は`meta/PRINCIPLES.md`・`meta/permissions.md`・`meta/guardrails.md`・`.claude/agents/**`・`HANDOFF.md`の5文書に限る。それ以外の運用手順書・台帳・道具・ADR自体はAIが自律的に扱ってよい（meta/adr/0075）。
「ビルド設定・検証ツール」と「CIワークフロー」のゲート変更は**5つ目の承認ポイントではなく**、4つ目（信条・規程の変更）に含まれる——**何を正しいと判定するかを変えることは、規程を変えること**である（meta/adr/0046 決定2）。
各承認ポイントの成果物は、冒頭に承認者向けサマリを置く（結論・要点を平易な言葉で先頭に集約し、証跡・詳細は後続の節に分離する。meta/adr/0016）。

### 人間判断の記録ルール（meta/adr/0061。0003を置き換え）

設計骨格の承認以降に人間の判断（承認済み決定からの逸脱・契約の解釈の裁定・矛盾の解決）が発生したら、判断の大小を問わず**ADRとして記録する**。チャット上のやりとりだけで済ませて歴史から消さない。

**記録することと、承認を求めることは別である**（meta/adr/0061）。

- **記録のADR**（すでに人間が決めたことを書き留めるもの。プロジェクトの設計判断・方式の選定の結果・契約の解釈の裁定）は、**承認を待たずに書いて作業を続ける**。`approved_by` にどのやりとりで決まったかを書く（例: `人間裁定（2026-08-23 チャット。窓の幅を7日にする）`）。間違っていたら人間があとから新しいADRで覆す——覆すことは正規の運用である（P-06）
- **制約のADR**（次にAIが何をしてよいかが変わるもの）のうち、**次の5文書のいずれかが変わる決定**は、**合意を取ってから進む**。これは承認ポイント4つ目（信条・規程の変更）に含まれる（meta/adr/0075）
  - `meta/PRINCIPLES.md`・`meta/permissions.md`（本ファイル）・`meta/guardrails.md`・`.claude/agents/**`・`HANDOFF.md`
- **上記5文書に触れない制約のADR**（`meta/orchestration.md`のような運用手順書・`meta/derived-repos.md`のような台帳・道具・ADR自体の起票や改廃）は、**AIが自分で起票・実装し、L0が緑であることを確認してマージまで自律的に行ってよい**。事前の合意は不要。行った変更はactiveContextで事後に分かるようにする（meta/adr/0075。0072が定めた記録PRの自己マージを包含し置き換える）
- どちらに当たるか判断できないときは、5文書側（合意が要る側）として扱う

### 合意をどこで取り、どこに書くか（meta/adr/0064。0006を置き換え）

合意は**チャットで取る**。PR本文で初めて問わない。PR本文は一方通行で、読み手が途中で聞き返せないため、承認材料が読めないという摩擦が6回くり返された。

合意が成立したら**待たずに** `approved_by` へ書き込む。記録のADRも制約のADRも書式は同じである。

```yaml
status: 承認済み
approved_by: "人間裁定（YYYY-MM-DD チャット: 裁定の要旨）"
```

**マージは承認行為ではなく、決まったことを公表する操作である**。マージ前に人間が確かめるのは「これを承認してよいか」ではなく「**この差分は、合意したものと一致しているか**」。

- 「本PRのマージをもって承認」とは書かない。この形のまま `status: 承認済み` になっているADRと契約は、govlintがERRORにする（meta/adr/0064 決定3）
- 承認をまだ取らないなら `status: 提案中` ・ `approved_by: null` のまま出す。判断を意図して保留する場合に限る（meta/adr/0035 方式(ii)）
- 契約（`.feature`）のステータス行も同じ形にする（meta/adr/0043 方式(i)の書式を差し替え）
- **マージ操作そのものは人間に残る**（meta/guardrails.md §1）。AIに移す条件は meta/adr/0064 決定4

friction-logへの記録は別判定: 人間判断の発生そのものはfrictionではない（エスカレーションは正常動作）。**AIの迷い・誤り・見逃しが関与した場合のみ**friction-logにも記録する。
記録先は、プロジェクトの実装・契約・設計の話なら `projects/<p>/friction-log.md`、テンプレート本体（規程・雛形・道具・ADR・PR本文）の話なら `meta/friction-log.md`（meta/adr/0058）。**どのプロジェクトにも属さないから書けない、は理由にならない**——A層の台帳が無かった期間に、同じ原因の再発が2回記録されないまま通り過ぎた（meta/adr/0058 文脈3）。

### Linearのチケットで範囲を合意する（meta/adr/0068）

- 人間がLinearのチケットを「Todo」へ移したら、その説明欄を実装の範囲の合意とみなす。AIはチャットの返事を待たずにDraft PRまで進めてよい
- チケットに無い判断が出たら止まり、チケットのコメントに§2の型で問いを書く
- これは範囲の合意であって、承認点の代わりにはならない。契約・設計骨格・step実装・規程の変更は、上のとおりチャットで合意を取る
- AIはチケットを「Todo」へ移さない。マージもしない

### メモリ系ファイルの自律更新ルール
- 更新タイミング: スライスの区切り、エスカレーション発生時
- activeContext.mdは追記ではなく上書き（P-11）。friction logは追記のみ
- ARCHITECTURE.mdはarchitectが構造変更時に更新する。「設計の現在」を映す記述的な地図であり、ADR（判断の歴史）と対をなす
- AIが自律更新できるのはこの3ファイルと**記録のADR**（meta/adr/0061 決定2）のみ。信条・規程・契約への波及が必要だと判断した場合は、直接編集せず変更提案を出す

## 2. 人間に判断を仰ぐときの型（meta/adr/0051）

AIが人間に判断を仰ぐときは、次の4点を**揃えて**出す。人間が聞き返さなくても、その場で選べる状態にすること。

1. **決めること**を一文で（何が決まっていないから止まっているのか）
2. **選択肢**を具体的に。AIが把握している範囲で網羅する。「今は決めない／現状維持」が成立するなら、それも1つに数えて明示する
3. **各選択肢のトレードオフ**（何を得て何を失うか）
4. **推奨**（あれば。理由を添える）。ただし**命令にしない**——推すことと決めることは違う

**適用する**: 承認済み決定からの逸脱・契約の解釈の裁定・矛盾の解決（＝下記「人間判断の記録ルール」がADR起票を求める判断）に加え、方式の選定・スコープの取捨・優先順位・やる/やらないの判断。

**適用しない**: (i) **意図の聞き取り**——選択肢を並べるとAIが用意した枠の中にしか人間の意図が入らなくなる（P-07が守ろうとしている自由度）。開いた問いのままにする。(ii) **事実の確認**。(iii) **AIが自分で決めてよいこと**——判断依頼を増やすこと自体がP-01に反する。**選択肢が1つしかないなら、それは判断依頼ではなく報告である**。

### 提示の仕方（meta/adr/0060）

上の4点は「何を揃えるか」を定める。ここは「どう出すか」を定める。実際に人間が答えられなかった
文面（およそ2000字の調査報告＋自由記述の質問3つ）を受けての追加である。

1. **会話に出すのは、結論と判断と次の一手だけ**。調査の経過・件数・ファイルの一覧・差分の分類は
   会話の本文に貼らず、ファイルかPR本文に置いてリンクだけ渡す。判断を仰ぐ前の前置きは10行が目安で、
   超えるならファイルへ移す
2. **判断は選択ボタン（`AskUserQuestion`）で出す**。地の文に「どうしますか」と書いて問わない。
   道具の側が短い質問文・2〜4個の選択肢・選択肢ごとの説明を必須にするため、上の4点のうち3点が
   仕組みで強制される。一度に出す質問は2問まで
3. **選択肢の文面に、このリポジトリを知らない人に通じない語を入れない**。ADR番号・FR番号・信条の
   番号・ファイルパス・社内語は禁止。説明にはそれを選ぶと何が起きるかを書く
4. **「わからない」と返ってきたら、説明を足さずに言葉を替えて出し直す**。それは選択肢の文面が
   失敗した合図である。出し直しても通らなければ、推奨案で仮決めして進み、覆したいときの参照先を
   記録に残す。人間を待たせて止まらない

すり抜けたときの救済として `/eli5`（直前の説明を中学生に通じる言葉で言い直す）を置く。
Codexには選択ボタンが無いため、2は運用で代替し、1・3・4を適用する。

chatでの提示の仕方は成果物に残らないため機械検証しない（P-04のできない側）。判断がADRになるときは、提示した選択肢と却下されたものが `approved_by` か `検討した代替案` 節のどちらかに残る。

## 3. エスカレーションプロトコル（§2の特殊例）

AIが契約を満たせないと判断した場合:

1. **実装を止める**。仮定で突き進まない。契約を書き換えない
2. **矛盾分析レポートを提出する**
   - どのシナリオとどの制約が衝突しているか
   - 修正案A/B（それぞれのトレードオフ付き）
3. **人間が判断する**。契約側を直す場合はADRを1枚追加（なぜ契約が間違っていたかの記録）
4. **AIが再開する**

契約の変更提案はIssue/コメントとして出す。AIによる契約ファイルの直接変更は禁止。

## 4. 矛盾分析レポートの型

```
## 矛盾分析: <スライスID>
- 衝突: <シナリオ/制約X> と <シナリオ/制約Y>
- 事象: <何を実装しようとして何が成立しなかったか>
- 案A: <内容> / トレードオフ: <...>
- 案B: <内容> / トレードオフ: <...>
- 推奨: <A or B> / 理由: <...>
```
