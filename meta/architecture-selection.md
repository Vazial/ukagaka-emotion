# architecture-selection.md — アーキテクチャ選定規程

> 対象: プロジェクト開始時のarchitect、および人間。
> 原則の根拠: P-09
> 形式: 選定の出力は**設計軸ごとの決定**である。「パックを1個選ぶ」形ではない（meta/adr/0056）。

## 1. 目的

アーキテクチャスタイルに汎用解はない。複雑度に対して過剰な設計は開発コストを、過少な設計は変更コストを膨張させる。
プロジェクト開始時に複雑度を評価し、そこから**そのシステムに固有の構成**を導く。

既製の型に当てはめる工程ではない。既製の型は事例として参照してよいが（5節）、選定の出力ではない。

## 2. 選定の流れ

1. AIが3節のチェックリストでプロジェクトの特性を評価する
2. AIがその評価から4節の**設計軸それぞれの決定**を導き、提案する
3. 人間が承認する
4. 決定を**ADR第1号**として記録する（後から構成を変える場合の判断材料になる）
5. 6節の成果物を揃える。対応するB層の実体（7節）があれば使う。なければinlineで自作してよい。採用にADRは不要

## 3. 複雑度評価チェックリスト

ここは**診断**であり、決定ではない。見たものをそのまま書く。

| 評価軸 | 見るもの |
|---|---|
| 不変条件の量 | 「同時にXであってはならない」「合計がYを超えてはならない」のような業務ルールの数 |
| 状態遷移の複雑さ | 状態の数と、遷移に条件が絡む度合い |
| ルールの変更頻度 | 業務ルールが今後も変わり続けるか、一度作れば安定するか |
| CRUD比率 | 処理の大半が単純な登録・参照・更新か |
| 連携中心か計算中心か | 外部システムの橋渡しが主か、独自の業務ロジックが主か |
| データ特性 | 大量データのバッチ・ストリーム処理が主戦場か |

## 4. 決めること（設計軸）

ADR第1号は、次の6軸それぞれについて**決定**・**根拠**（3節のどの評価から来たか）・**禁じる依存**を書く。

| 軸 | 決めること |
|---|---|
| 業務ルールの置き場 | 不変条件・判定・計算をどこが持つか（ドメインオブジェクト／サービス層／純関数モジュール／DB制約／画面） |
| 状態の持ち方 | 永続状態を持つか。持つならSSoTはどこか（自前DB／外部システム／持たない） |
| 外部との境界 | 外部I/Oをどこで閉じるか。provider固有形式の流出を許す範囲 |
| 層の厚み | いくつの層を通すか。ドメインと永続化の二重表現を持つか、圧縮するか |
| UIの厚み | 画面がロジックを持つか表示に徹するか。画面が無いなら「無し」と書く |
| 処理の駆動 | リクエスト駆動／スケジュール駆動／イベント駆動／手動 |

**禁じる依存は各軸に1つ以上添える。** これがそのままL2構造検証ルールの入力になる（meta/verification.md）。
禁じるものが無い軸は「無し」と書いてよいが、空欄は認めない。機械検証に落ちない決定は決定ではなく感想である（P-03）。

### この節で禁じること

- **消去法で決めない。** 「AでもBでもないからC」という形の論証を、構成決定の根拠にしない。各軸の決定は3節の評価から直接導く。
- **他プロジェクトのADR-0001を構成の根拠にしない。** 同じニックネームを名乗っていても、軸の決定は独立に導く。
  他プロジェクトから借りてよいのは「同じ問題に当たった時にどう対処したか」であって、構成そのものではない。

## 5. よくある組み合わせ（事例。候補の一覧ではない）

過去にこう組み合わせた、という**事例**である。**どの行にも当てはまらない構成を選んでよい。それが既定の選択肢である。**

| 呼び名 | そう組んだケース | 主な構成 |
|---|---|---|
| シンプルCRUD | CRUD比率が高く不変条件が少ない管理画面・社内ツール | Transaction Script、薄いサービス層、生成系ツール活用 |
| 軽量ドメインモデル | 不変条件・状態遷移は多いが、連携面が小さく永続化技術が単一の中複雑度システム | 値オブジェクト・集約・DB制約は維持し、層を圧縮（ポート/アダプタ分離とドメイン/ORM二重表現を省略）。構造検証は「ルールの置き場」に絞る（meta/adr/0005） |
| ドメインモデル | 不変条件・状態遷移が多く、ルールが変わり続け、境界の交換可能性も要る業務システム | 戦術的パターン（DDD等）+ヘキサゴナル、構造検証を厳格化 |
| パイプライン | データ変換・バッチ・連携が主 | 関数的なステージ構成、入出力スキーマ検証中心 |
| フロント主体 | ロジックの大半がUIにあるツール・可視化 | コンポーネント設計規約、状態管理規約中心 |

**呼び名は任意である。** 付けても付けなくてもよく、付ける場合もこの表から選ぶ必要はない。
名前は決定の要約であって、決定の供給元ではない——名前から構成を導いた瞬間、この規程は目的を失う。

## 6. 成果物（構成によらず共通）

どの構成でも以下を同じ形式で提供する（A層の規約に従う）:

- ディレクトリ構成規約
- 構造検証ルール（4節の「禁じる依存」を実行可能な形にしたもの → verification.md L2）
- テスト戦略（何をどの段でどこまでテストするか → verification.md）
- CLAUDE.md断片（そのプロジェクト固有の規約）

## 7. B層の位置づけ

B層は4〜6節（軸の決め方・成果物の形）をあるスタックで実現する具体配線（ArchUnit・ビルド設定・CI等）だけを持つ。
**A層はB層に依存しない**（domainがadapterに依存しないのと同型の制約）。4節の軸の決定は常に言語非依存のまま行う。

B層のカタログは予防的に作らない。同スタック・同型のプロジェクトが2本目に現れ、実プロジェクトの構造から重複が実証された時にだけ、汎用スケルトンとして「昇格」させる。特定プロジェクトを描写した複製ではなく、各プロジェクトがそこから派生する原本として作る（複製はドリフトする → meta/adr/0005、projects/reservation-system/friction-log.md FR-013）。

現状: カタログは空。reservation-system（java-spring × ドメインモデル）が最初の昇格候補。

## 8. 「設計パック」は廃語

meta/adr/0056 以前、この規程は5節の表を「設計パック」と呼び、その中から1個選ぶ形をとっていた。
**この語は廃止する。A層はもうこの語を使わない**——名前が構成の供給元として振る舞うのを止めるのが
本改訂の目的であり、名前を残せば同じことが起きる。

既存4本のADR-0001（reservation-system・reservation-frontend・connpass-session-radar・dining-radar）は
旧形式のまま「〜パック」を名乗っている。遡って書き直さない（P-06）。C層（`projects/**`）に残る
「〜パック」の記述は、その当時の決定を指す**歴史的な名前**として読むこと。
そのプロジェクトが次に構成を変える決定を出す時、新しいADRが4節の形式で書かれる。
