# meta/loop — 改善ループの道具

> friction-log は「その場で書く」ことを前提にしている（P-05・`meta/adr/0012`）。
> ここに置くのは、**書き損ねた分をセッションログから拾い直す**ための道具である。
> 根拠と決定は `meta/adr/0049`。

## `meta/tools/` ではなく `meta/loop/` である理由

`meta/adr/0046` が施錠したのは「**何を正しいと判定するか**」——ゲートである。
ここの道具は何も失敗させず、何も判定しない。したがってゲートではなく、施錠の対象ではない
（`meta/adr/0049` 決定5）。閾値の調整に人間の開錠は要らない。

**新しい道具をここに置く前に確認すること**: それは何かを不合格にするか。するなら
`meta/tools/` であり、施錠の内側である。

## harvest_friction.py

セッションログ（`~/.claude/projects/<slug>/*.jsonl`。worktree分を含む）を走査し、
「読むべき摩擦の瞬間」を候補として並べる。

```bash
python meta/loop/harvest_friction.py              # 前回の収穫以降
python meta/loop/harvest_friction.py --all        # 全期間
python meta/loop/harvest_friction.py --all --no-advance   # 収穫位置を進めずに試す
```

- **候補であってFRではない**。`friction-log.md` への追記は人間のGOのあと（`0049` 決定3）
- 閾値（既定8）未満のセッションは**報告しない**。軽量な修正はここで黙って落ちる
- 収穫位置は `.claude/harvest-state.json`（gitに入れない。各自の環境の事実）

### いつ走るか

`gh pr merge` の後に PostToolUse hook が自動で走る（`.claude/settings.json`）。
候補があればコンテキストに注入され、無ければ何も起きない。

**hook の `if` フィルタだけに頼っていない**。バッククォートで囲まれた文字列はコマンド置換
として解析され `if` に一致する——クォート付き heredoc の中でも同じ（実測: コミットメッセージに
`gh pr merge` と書いたら発火した）。誤発火は無害だが**収穫位置が黙って進んで蓄積を食う**ので、
スクリプト側でコマンド文字列を再検査し、一致しなければ収穫位置も進めない。

**Codexには届かない**——hook は Claude Code の機構である（`0049` 帰結）。

### シグナル

| 種別 | 何を見ているか | 重み |
|---|---|---|
| `human:*` | 人間が打ち直した否定・訂正（`違う`・`勝手に`・`戻して`・`規程` 等） | 2〜5 |
| `interrupted` | ツール実行を人間が拒否・割り込みした | 4 |
| `repeated-error xN` | 同一エラーが4回以上 | 2〜4 |
| `self-correction` | AI自身の自己訂正 | 2 |
| `edit-churn xN` | 同一ファイルへの書き込みが8回以上 | 2 |

重みは「人間が読む価値の見込み」であって、frictionの重さではない（`0049` 決定2）。

### テスト

```bash
python -m pytest meta/loop/test_harvest_friction.py -q
```

守っているのは主に**人間の発話の判別**。`role: user` には人間がタイプしていないものが
大量に混ざり（実測: task-notification 231件 / 人間の発話 522件）、ここを外すと候補は
無意味になる。

## friction_trend.py

摩擦率（人間が打ち直した訂正プロンプト ÷ 人間のプロンプト総数）を測り、
**悪化したときだけ知らせる**。

```bash
python meta/loop/friction_trend.py            # ベースラインと回帰判定
python meta/loop/friction_trend.py --weekly   # 週次の内訳（参考）
```

### 「ループが効いた」の証明には使えない

理由は2つある。どちらも運用で消えない。

1. **交絡が畳めない** — モデルが変わる／タスクの性質が変わる（初期は規程が無いので摩擦が
   多くて当然）／人間の指示も上手くなる。摩擦率が下がっても、ループの寄与は切り出せない
2. **流量が足りない** — 実測で週あたり約75プロンプト・摩擦率3.8%（訂正17件／450件）。
   この条件で検出できるものは:

   | 検出したい変化 | 片側に必要な件数 | 比較に要する総期間 |
   |---|---:|---|
   | 半減（3.8%→1.9%） | 1,207 | 約7.5か月 |
   | 3割減（3.8%→2.7%） | 3,789 | 約23か月 |
   | 2倍（3.8%→7.6%） | 585 | 約3.6か月 |
   | 3倍（3.8%→11.4%） | 190 | 約1.2か月 |

   **改善は現実的な期間では測れず、大きな悪化だけが測れる。**

だから週次の折れ線を読んではいけない（週あたりの訂正は1〜5件）。ツールは判定に足る件数が
貯まるまで「まだ判定できない」と言い、あと何件要るかを示す。

### 重複排除

セッションはフォーク・再開で分岐し、同じレコードが複数ファイルに入る（実測: 全レコードの
**21.7%**）。`uuid` で潰さずに率を出すと、分岐の多い週だけ分母が膨らんで**偽のトレンドが
出る**。`collect()` はここを必ず通す。

なお `harvest_friction.py` の候補一覧は**この重複を潰していない**——同じ摩擦が複数の
セッション行に現れることがある。候補は人間が読む前提なので実害は小さいが、**あの数字を
率として使ってはいけない**（率は本ツールが出す）。

## index_sessions.py — 正規化（層1）

分析より前に、生のログの癖を1箇所で畳む（`meta/adr/0049` 決定8）。

```bash
python meta/loop/index_sessions.py     # ~/.claude/session-index/<repo>.db を作り直す
```

冪等。毎回作り直すので、いつ走らせても壊れない。**出力先は作業ツリーの外**——DBはログ本文を
そのまま含み、閲覧したページ由来のメールアドレス（実測461件）やローカル開発用の資格情報が
写り込む。リポジトリ内に置くと `.gitignore` がブランチごとの版に依存し、別ブランチを
チェックアウトした作業ツリーでは untracked として現れてしまう。

### 畳んでいる3つの癖

| 癖 | 実測 | 畳み方 |
|---|---|---|
| フォークで重複する | 全レコードの **21.7%** | `uuid` で排除し、`sessionId` を出自とする |
| 役割agentは別ファイル | **108実行・77.8 MB**（メインとほぼ同量） | `.meta.json` の `toolUseId` で親に結合 |
| `role: user` は人間とは限らない | notification 231件 / 人間 522件 | 種別に分ける。**agentログに人間は登場しない** |

3つ目が特に効く。役割agentのログでの `role: user` は orchestrator のブリーフなので、
人間の発話として数えると**agentへの指示が「人間の訂正」になる**（実際に一度そうなった）。

### テーブル

| | 中身 |
|---|---|
| `session` | フォークを畳んだ論理セッション。どのファイルに散ったかを `source_files` に持つ |
| `agent_run` | 役割agentの実行。`agent_type`・**ブリーフ**・**成果**・ツール呼び出し数とエラー数 |
| `event` | 重複排除済みのイベント。`kind` が種別（`human_prompt` / `agent_brief` / `tool_use` …） |

`agent_run.brief` と `agent_run.outcome` が「どんな指示で、何が返ってきたか」の対になる。

### この層は判定しない

摩擦かどうかも良し悪しも決めない。形を揃えるだけである。判定は上の層（収穫・測定）が行う。

### 載せ替え済み

`harvest_friction.py` も `friction_trend.py` もこのインデックスを読む。生のログは
もう直接読まない。全再構築は約2秒なので、両方とも実行のたびに作り直してから走る。

載せ替えで初めて見えたもの:

- `repeated-error x23` **(architect)** — 「作業ディレクトリが違う」で23回続けて詰まっていた
- `agent-rework` **(tester)** — orchestrator が「**前回の私の指示が間違っていました**」と差し戻していた

どちらもメインのトランスクリプトだけを見ていたときは拾えていない。

## 二段構え（meta/adr/0055）

急性と慢性で、見えるものが違う。

| | いつ | 何が見える |
|---|---|---|
| **セッション内** `--hook` | PR作成の**直前**に自動 | **急性** — 今回のスライスで何が起きたか |
| **横断** `--recurring` | 手動・週次 | **慢性** — 同じ原因が何セッションに跨っているか |

```bash
python meta/loop/harvest_friction.py --recurring    # 横断。セッション数の多い順
python meta/loop/harvest_friction.py --all          # 全期間の総ざらい
```

### なぜPR作成の「直前」なのか

振り返りは終わるときにやるものだからである。そしてPRの作成は、このリポジトリで
「スライスを閉じて何が起きたかをまとめる」唯一の儀式である。

マージ後ではいけない理由もある。**マージ後はPRが閉じているので、摩擦を記録するには
2本目のPRが要る**——それは台帳で最も多く再発している摩擦（`record-update-needs-second-pr`、
7回）そのものであり、収穫の仕組みがその摩擦を自ら生むことになる。PR作成の直前なら、
起票は同じブランチへのコミットで済む。

実測でも、トリガとして成立するのはこちらだけだった（`gh pr create` 98回/30日 に対し
`gh pr merge` 12回/1日。マージは主に人間がGitHubの画面で行う操作である）。

### なぜ横断を自動にしないのか

毎回見るものではないし、締めの邪魔になる。ただし**ここにしか現れない欠陥がある**——
`File does not exist…working directory` は14セッション・124回起きていて、台帳51件に
1件も記録されていなかった（`projects/dining-radar/friction-log.md` の `FR-021`）。
1セッションの中では「エラーが何回か出た」にしか見えないためである。

週次で回すなら、登録先は各自の環境（`~/.claude/scheduled-tasks/`）に置く。
リポジトリには置かない——インデックスの置き場と同じ理由（個人環境に属する設定）。
