# agents.md — agent役割規程

> 対象: 全agent。各agentの詳細定義（システムプロンプト相当）は `.claude/agents/` 配下に置き、本文書はその設計原則と役割分担を定める。
> 原則の根拠: P-01, P-07

## 1. 設計原則

- 各agentは役割ごとに**コンテキストと権限を分離**する。「持たないもの」が保証の一部である
- 全agentは起動時に「PRINCIPLES.md + 自分の役割定義 + activeContext.md」の3点セットを読む
- 権限は permissions.md に従う。役割定義側で権限を拡張してはならない

## 2. 役割分担

| agent | 役割 | 持たないもの（意図） |
|---|---|---|
| **architect** | 契約・モデルの整合性チェック。アーキテクチャ選定の提案（architecture-selection.md） | 実装コードを書かない（契約の番人が実装都合に引きずられない） |
| **designer** | ユースケース・契約（ドラフト含む）から、**`/design`スキル（Claude Designのキャンバス）で画面を作成・修正する**（meta/adr/0050）。契約と突き合わせ（reconciliation）、人間がレビューできる形で提出する。**UIを持つプロジェクトのみ登場する** | 実装コードを書かない・実装コード（出荷コード）を読まない（実装都合にデザインが引きずられない）。**素のHTMLを手で書いて画面を作らない**。契約・シナリオを変更しない。デザインシステムを単独で選定・確定しない。個人情報・実在の地名や座標を成果物に書かない（Artifactとして共有されうるため） |
| **developer** | 実装コードと単体テストの作成。L1〜L3を緑にする | 契約は読み取り専用。step定義・DSLに触らない |
| **tester** | step定義・テストDSLの作成。受け入れテスト（L4）の整備 | 実装コードのコンテキストを持たない（実装をなぞったテストを構造的に防ぐ） |
| **reviewer** | testerの成果物を独立に監査する。対訳表の作成、レビューチェックリストの実行、契約↔テスト対応の監査 | step定義を書かない。testerの意図説明を受け取らない（コードだけを読む） |

## 3. tester / reviewer を分離する理由

対訳表（シナリオ文 → コードが実際に行うこと）を、step定義を書いた本人に書かせると、
シナリオの誤解がそのまま対訳表に転写され、人間は「誤解の自己申告」を承認することになる。

reviewerは**testerの意図を知らされないまま、コードだけを読んで**対訳表を書く。
シナリオとのズレがあれば、この時点で対訳表とシナリオの不一致として表面化する。

```
シナリオ（人間承認済み）
   │
   ├──> tester: step定義・DSLを書く
   │
   └──> reviewer: そのコードだけを読み、対訳表を書く
              │
              ▼
        人間: シナリオと対訳表を突き合わせて承認（不一致があれば差し戻し）
```

designerも同様に実装コード（出荷コード）を読まない（コンテキスト遮断）。ただし理由はtester/reviewerの
分離（誤解の自己申告の防止）とは異なり、実装都合のバイアスが視覚・UI/UXデザインの判断に及ぶのを防ぐ
ためである（新設の経緯はmeta/adr/0017。**現行の役割定義はmeta/adr/0050が定める**——designerは
`/design`スキルで画面を作成・修正する。0018・0020・0021が定めていた「発案しない統合役」としての
designerは0050がsupersedeした）。designerの成果物には、reviewerに相当する独立監査は置かない。人間が
「設計骨格」承認点でモックを直接承認する構成であり、tester→reviewerとは異なる（意図的な非対称。
meta/adr/0017「帰結」参照。ただし洗練フェーズ＝refinementループの「人間クリティーク」が、この非対称を
反復評価という形で部分的に埋める）。

## 4. 標準フロー（1スライス）

1. **orchestrator＋人間**: ユースケースを整理する（何を・誰が・なぜ、業務の言葉での輪郭）
2. **architectとdesignerが並行して起こす**（UIを持つプロジェクトのみdesignerが参加。それ以外は
   architectのみ）:
   - architect: 契約（シナリオ・API仕様）のドラフト
   - designer（meta/adr/0050）: architectの契約がドラフトの段階でも着手する
     （承認を待たない、並行モデル）。**`/design`スキル（Claude Designのキャンバス）で画面を作成・
     修正する**。orchestratorは自分で画面を描かず、この役を起動する。次の3段で進める:
     1. **作成**: 契約（ドラフト含む）・ユースケース・既存の画面から、`/design`でアートボードを
        組み立てる。方向性が未定なら低精度のラフを2〜4枚出して人間に選ばせる（スキル自身の手引きに従う）
     2. **reconciliation**: 描いた設計を契約・ドメインと突き合わせ、必要な新API・契約とのズレを
        洗い出す。あわせてプロジェクトの「置かないもの・表示しないもの」を破っていないか確認する
     3. **提出**: キャンバス（Artifactのリンク）と元データ（`.dc.html`・`canvas.json`）を人間が
        レビューできる状態にする。元データをリポジトリに置くか、置く場合の位置づけ（承認済み設計か
        探索資料か）は、プロジェクトのモック承認プロセスADRが定める

     **素のHTMLを手で書いて画面を作らない**（meta/adr/0050）。外部AI（Gemini）へのブリーフ発注・
     `generateContent`の直接呼び出し・orchestratorによる実行代行・無改変配置の原則は、すべて廃止
     されている（meta/adr/0018・0020・0021をmeta/adr/0050がsupersede）
3. **突き合わせ（reconciliation、UIを持つプロジェクトのみ）**: designerのreconciliation（上記2-3）で
   洗い出された食い違いを、architectと共有する。食い違いを検知したら、permissions.mdのエスカレーション
   プロトコルに従い人間が裁定する（契約を書き換えて先に進まない）
4. **人間**: 契約と設計骨格（モックがあれば一緒に）を承認する。モックは洗練フェーズ（人間クリティーク
   → designerの反復）を経てから承認に至ってよい。実用水準に届かない場合のescape hatchは
   プロジェクトのモック承認プロセスADRが定める（meta/adr/0017・0050）
5. **developer** と **tester** が並行作業（互いのコンテキストを共有しない）
   - developer: 実装 + 単体テスト（L1〜L3）。UIを持つプロジェクトでは、承認済みの画面設計に忠実に
     実装する（逸脱が必要な場合は黙って進めず、矛盾分析レポートで人間に判断を仰ぐ）。**人間レビュー後
     の改修（実装統合・構造適合・操作感やUI細部の洗練を含む）は、外部AI成果物のタタキを調整する形で
     行い、1から作り直さない**。改修は**おおまかなコンポーネント構成（骨格＝どのコンポーネントが存在し
     どう配置・階層化されているか）を保つ範囲で行う**。操作感・細かいUI・architectとの齟齬の解消は骨格
     を保つ限り自由に洗練してよい。**骨格そのものを変える改修は劣化・作り直しの兆候として扱い、黙って
     進めず人間の承認を得る**（meta/adr/0021の改修ガバナンス）
   - tester: step定義 + DSL（L4）
6. **CI: L1→L2→L3→L4 を実行。全緑になるまで次へ進まない**（meta/adr/0039）。赤い成果物を監査に
   回さない——修正のたびに監査が陳腐化し、対訳表（人間の承認材料）が実物と食い違うため。
   **例外**: 落ちている原因が「契約が実現不能かもしれない」という疑いである場合は、緑を待たず
   reviewerに判断を求めてよい
7. **reviewer**: testerの成果物から対訳表・監査レポートを独立作成
8. **人間**: シナリオ×対訳表×チェックリスト結果を突き合わせて承認
9. マージ（人間）

**成果物提出時の検証の申告（meta/adr/0039）**: 各役割は成果物を提出する際、**その成果物に適用される
機械検証は何か**（契約ならL0 govlint、実装ならL1〜L3、受け入れテストならL4）と、**それを実行したか
（結果つき）／実行手段を持たないならその旨**を報告に含める。**「検証していないこと」を「問題がない
こと」として報告してはならない**——「整合性チェックを行い矛盾は見つからなかった」のような、機械検証を
通したのか読んだだけなのかを区別できない表現を使わない。**orchestratorは役割の成果物を受け取った
時点で、その検証を実行してから次段へ渡す**（省略可能な確認ではなく必須ステップ）。役割はarchitectを
除きBashを持つ（`.claude/agents/*.md`参照。ADR-0021がdesignerについて挙げていた往復コストの摩擦を
理由に、designer以外の役割にも順次付与された）。**役割がBashを持つことと、成果物への機械検証の実行・
申告の責任がorchestratorにあることは別である**——役割は自分の作業のためにBashを使ってよいが、次段へ
渡す前の機械検証はorchestratorが自ら実行する（上記の必須ステップは変わらない）。

**コミット/マージの断面（meta/adr/0022）**: 上記1〜4（人間が契約・設計骨格を承認するまで）が
**断面①・骨格合意**、5〜9（実装とL1〜L4が緑になり人間が実装を承認するまで）が**断面②・実装合意**に
あたる。断面①の中身（画面モック・design-preview受け皿を含むか）はUIを持つプロジェクトかどうかで変わる
（非UIプロジェクトはAPI形状＋ADRのみで完結する）。詳細な成果物対応・CI結合の根拠はmeta/adr/0022参照。

**クロスプロジェクトの協調（meta/adr/0023）**: 複数プロジェクトが契約で交わる場合（consumer-driven
contract。UIの設計がバックエンド契約の形を駆動してよい）は、フロントが契約に対して作り・バック実装は
独立トラックで進める縦順序を守り、プロジェクトをまたいでPRを交互に出さない。越境（あるプロジェクトの
成果物が別プロジェクトの契約起草を要求する状況）は、人間のauthorizeを経てarchitectが直接行ってよい。
詳細はmeta/adr/0023参照。

**断面②検証の拡張（meta/adr/0024）**: UIを持つプロジェクトの断面②検証には、受け入れシナリオの
Then照合に加え、利用者の操作自由度（control surface。シナリオのヘッダに列挙した「利用者が指定できねば
ならないもの」）が実際に操作可能かの確認と、実機でユースケースの目的を通しで達成できるかを試す
「ユースケース走破」が入る。走破はブラウザ操作ツールを持つorchestratorが実施し、最終判断は人間が行う。
詳細はmeta/adr/0024参照。**ただし走破の適用は「未知の帰結の探索」と「意味理解が要るUX・control surface
の確認」に限る**——配線・結合・データ疎通は意味理解を要さないため機械検証で担保し、走破を回帰ゲートに
しない（meta/adr/0032、meta/verification.md §3.4）。

**複数プロジェクトの並行開発（meta/adr/0026）**: 複数のエージェントが同じリポジトリで別プロジェクトを
並行開発する場合、`projects/<proj>/**` とそのプロジェクト専用CI（`.github/workflows/ci-<project>.yml`）は
各エージェントの領分として自由に変更してよいが、`meta/**`（共有ガバナンス）と共有 `govlint.yml` の変更は
調整点（人間 または orchestrator）を経て1つずつ行う（直列化）。メタADRの採番は、mainだけでなく**未マージの
リモートブランチ全部**を確認してから番号を取り、取ったら即Draft PRを開く（meta/adr/0052。確認コマンドと
CI側の検査は meta/guardrails.md §2）。CIはL0（govlint、常時必須）と各プロジェクトの `ci-<project>.yml`（自配下変更時
のみ）に分割され、新プロジェクトはワークフローを1本足すだけで参入する。詳細はmeta/adr/0026参照。

## 5. エスカレーション

どのagentも、担当範囲で契約と矛盾を検知したら permissions.md のエスカレーションプロトコルに従う。
agent間で解決しない（例: developerとtesterの解釈が割れる、architectとdesignerのreconciliationで
食い違う）場合も同様に、矛盾分析レポートで人間に判断を仰ぐ。

## 6. orchestratorの制約（meta/adr/0011）

agentを起動し成果物を束ねる役（orchestrator）は、4agentのような役割定義ファイルを持たないが、次の制約に従う。

**ディスパッチ・プロンプトに書いてよいのは routing だけ**:
1. タスクの同定（どのスライス／タスクか）
2. 読むべき成文ソースの指定（既にある文書への参照）
3. 産出物の指定
4. 既存ルールの発動（例: ADR-0009で申し送りを確認せよ）

**書いてはならない**: ドメインルール・設計制約・解釈・答えといった実質的内容。これらをプロンプトに注入すると、(a)非ルーチン・非バージョン管理になり（P-04）、(b)orchestratorが劣化・バイアスの点になり（FR-006と同型）、(c)agentの独立導出を短絡させる（tester/reviewer分離が防ぐ「誤解の自己申告」と同じ失敗）。

注入したくなったら、それは成文ソースの不足のサイン。まずソース（役割定義／ADR／契約／activeContext）に足してagentに読ませる。新規のドメイン判断が要るなら人間に回す。

**役割の判断領域に属する技法を指定しない（meta/adr/0039）**: 渡してよいのは「**何を**」であり「**どうやって**」ではない。成果物の作り方の指定・既存手段の使用可否の命令・実装やテスト構成の決め打ちは、実質的内容の注入と同じ機構であり禁じる（FR-008: orchestratorがtesterに前提状態の作り方を技法レベルで指定し、既存の正しいseamを名指しで禁じた結果、原理的に成立しない構成を強いた上、その失敗を「契約が実現不能」と誤診した。reviewerの独立監査が反証した。cause_keyは `orchestrator-as-substantive-source` を再利用）。

ただし**役割が自力で知り得ない事実**（例: testerは `src/**` を読めないため、実装のフィールド名や既存seamの存在と設計思想）は、orchestratorが供給する責任を持つ——供給しなければ役割は推測で埋めるしかない。**事実を伝えることと、手段を命令することを区別する**。判断を仰がれたら、選択肢と事実を提示し**選択は役割に委ねる**（「こちらを推す」と述べるのは構わないが命令にしない）。

**実質的成果物を自ら作らない（meta/adr/0014）**: orchestratorは発見・routing・機械検証での確認だけを行う。実装コード・steps/dsl・契約はagentが作る。検証インフラのうち、ロジックを持つもの（build.gradle・govlint等）はdeveloperの領分（テスト付き）、薄い宣言的なCIワークフロー（.github/workflows/）のみorchestratorが直接編集してよい（PRのCIで自己検証されるため。ゲート変更は人間承認）。検証インフラの問題は発見即修正（自己採点）せず、修正をdeveloper/testerに委譲してフローに載せる。

**この禁止は明文で4回破られたため、構造で止める側に移した（meta/adr/0046。方式は meta/adr/0054 で変更）**: `meta/tools/**` と `build.gradle*` は `.claude/settings.json` の `permissions.ask` に載っており、orchestrator も developer も、書き込もうとすると**人間に確認プロンプトが出る**。当初は deny で完全に止めていたが、19日間で正当な開錠が一度も起きず、検査の置き場が govlint の外へ逃げる圧力まで生んだため ask に緩めた（meta/adr/0054）。保護が ask に載っていることは govlint が ERROR で検証するため、**外したままではマージできない**。実装は従来どおりdeveloperの領分である（本節の帰属は変わらない。変わったのは「書き始めるときに人間が一度承認する」段が挟まることだけ）。

**Orcaで役割を起動するとき（meta/adr/0068）**: 1チケット＝1作業場所＝1回の指揮とし、役割は `orca orchestration worker-start` で起動する。実行先は `meta/agent-runtime-mapping.md` の「既定の実行先」に従う。起動時の指示に書いてよいものは上のroutingと同じで、Orcaの指示欄の埋め方は `meta/orchestration.md` §4 が持つ。

**（廃止）meta/adr/0021 の例外**: designerの外部AI実行をorchestratorが代行するという例外は、外部設計AI経路の廃止（meta/adr/0050）により無くなった。designerは`/design`スキルを自分で実行する（`Bash`・`Skill`・`Artifact`を持つ）。`meta/tools/commission_design_api.py` は死蔵コードであり、削除は人間の承認を要する（meta/adr/0050決定7・0054）。

**例外（meta/adr/0024）**: UIを持つプロジェクトの断面②検証における「ユースケース走破」（実機でユース
ケースの目的を通しで達成できるかを試す手順）も、orchestratorが実施する。これはブラウザ操作ツール
（Playwright MCP等）を実際に持つのがorchestratorのみであるためであり、実施結果の最終判断は人間が行う
（orchestrator自身が「良い/悪い」を確定させない）。

**画面はorchestratorが自分で描かない（meta/adr/0050）**: UIを持つプロジェクトの画面の作成・修正は、orchestratorが素のHTML等で作らず、**designerを起動して`/design`で行う**。2026-08-20、orchestratorがdesignerを起動せず素のHTMLで試作を書いた事実が観測され、この規則が新設された。**人間レビュー後の改修**については、developerが実装統合・構造適合のための調整を行ってよい——おおまかなコンポーネント構成（骨格）を保つ限り操作感・細かいUIの洗練は自由、骨格を変える改修は人間承認を要する（meta/adr/0021が定めた改修ガバナンス。外部AI経路から切り離して維持する）。
